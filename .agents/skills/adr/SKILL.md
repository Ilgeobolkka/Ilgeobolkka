# ADR — 아키텍처 결정 기록

"왜 이렇게 만들었지?"에 답하는 기록. 결정 1개 = 파일 1개.
파일명은 `docs/adr/<상태>/<주제>/NNNN-영어-케밥-제목.md`
(한글 파일명은 NFD 이슈로 금지, 제목·본문은 한국어).

## 상태 폴더

| 폴더 | 허용 상태 | 용도 |
| --- | --- | --- |
| `active` | `제안됨`, `승인됨` | 현재 검토 중이거나 유효한 결정 |
| `superseded` | `대체됨` | 후속 ADR로 대체된 결정의 역사 |

- ADR의 상태 줄과 상태 폴더는 항상 일치시킨다.
- `superseded`는 삭제 후보나 작업 메모 보관소가 아니라 대체된 결정 기록을 영구 보존하는 영역이다.
- `docs/adr/evidence/`는 상태와 무관한 재현 자료를 보관하므로 상태 폴더 아래로 이동하지 않는다.

## 주제 폴더

| 폴더 | 대상 |
| --- | --- |
| `billing` | 열람 확정, 과금, 포인트 정책 |
| `content` | 페이지 이미지 변환·전달·저장 |
| `validation` | 콘텐츠 품질과 화면 가독성 검증 |
| `architecture` | 기술 스택, 패키지 구조, 주요 라이브러리 |
| `data` | 데이터베이스 설정, 데이터 모델, 스키마 |
| `api-auth` | API의 되돌리기 비싼 설계 원칙과 인증·인가 경계 |

- ADR은 주된 결정 하나를 기준으로 한 주제 폴더에만 둔다. 다른 주제와의 관계는 본문에서 관련 ADR 번호로 연결한다.
- 위 폴더는 현재 분류이며 고정 목록이 아니다. 새 ADR이 어느 폴더에도 맞지 않으면 주된 결정에 맞는 영문 케밥 표기 폴더를 `docs/adr/active/` 아래 만들고 이 표에 추가한다.
- 대체된 ADR을 이동할 때에만 필요한 `docs/adr/superseded/<주제>/`를 만들며 빈 주제 폴더는 미리 만들지 않는다.

## 작성 시점 — 하나라도 해당하면 쓴다

- 언어·프레임워크·주요 라이브러리·인프라의 선택 또는 교체
- 데이터 모델, 외부 API의 되돌리기 비싼 설계 원칙, 모듈 경계 등 되돌리기 비싼 구조 결정
- 트레이드오프가 있어 나중에 누군가(사람·AI)가 "왜?"라고 물을 선택
- 기존 ADR을 뒤집는 결정

전체 엔드포인트·요청/응답 필드·상태 코드 매핑은 `docs/api/api-contract.md`에 기록한다.
ADR에는 대안과 되돌림 비용이 있는 API 설계 선택과 그 근거만 기록한다.
변수명·파일 위치 같은 구현 디테일은 기록하지 않는다.

## 절차

1. `active`와 `superseded`의 모든 주제 폴더에서 가장 큰 ADR 번호를 찾고 그 번호에 1을 더한다 (0001부터 4자리, 폴더별로 번호를 다시 시작하지 않음).
2. `docs/adr/active/` 아래에서 주된 결정에 맞는 주제 폴더를 선택한다. 맞는 폴더가 없으면 위 규칙에 따라 새 주제 폴더를 만든다. 아래 템플릿으로 작성하고 상태는 `제안됨`으로 시작한다.
3. `docs/adr/README.md`의 현재 유효한 ADR 영역에 새 ADR을 추가한다. 새 주제 폴더라면 해당 주제의 제목과 표도 함께 만든다.
4. 결정이 확정되면 `승인됨`으로 바꾼다.
   합의 과정의 이견·소수 의견은 "고려한 대안"에 한 줄로 남긴다.
5. 승인된 ADR의 결정 내용은 고치지 않는다. 상태와 파일 위치는 관리 메타데이터로 갱신할 수 있으며,
   파일 이동으로 끊어진 내부 링크는 표시 문구와 의미를 바꾸지 않고 대상 경로만 수정할 수 있다.
6. 결정을 뒤집을 때는 새 ADR을 쓰고 후속 ADR이 승인된 시점에 기존 ADR의 상태를
   `대체됨 (→ NNNN[, NNNN...])`으로 바꾼다. 같은 변경에서 기존 파일을
   `active/<주제>/`에서 `superseded/<주제>/`로 이동하고 README와 저장소 내부 링크를 갱신한다.
7. AI 에이전트: 구조에 영향 주는 작업 전에 관련 ADR을 읽는다.
   ADR과 어긋나는 요청을 받으면 해당 ADR을 근거로 먼저 확인 질문한다.

### 기존 ADR 호환

- YAML frontmatter의 `status: accepted`와 번호 없는 제목을 쓰는 기존 ADR은 승인된 레거시 형식이다.
- `accepted`는 `승인됨`과 같은 상태로 해석하며, 형식 통일만을 위해 기존 본문을 수정하지 않는다.
- 새 ADR부터 아래 템플릿을 사용한다.

## 템플릿

```markdown
# NNNN. <결정 제목>

- 상태: 제안됨 | 승인됨 | 대체됨 (→ NNNN[, NNNN...])
- 날짜: YYYY-MM-DD

## 맥락

<결정이 필요해진 문제·제약. 2~5문장.>

## 고려한 대안

<`대안 — 이 프로젝트에서 기대되는 장점 / 선택하지 않은 구체적 이유` 형식으로 대안마다 한 줄. 실질 대안이 없었으면 "없음".>

## 결정

### 선택한 기술

<선택한 기술 또는 방식과 적용 범위를 "~을 사용한다" 단정형으로 쓴다.>

### 핵심 근거

<`비교 기준 — 선택한 기술과 대안의 차이 / 그 차이가 이 프로젝트에서 중요한 이유` 형식으로 구분해 쓴다. `고려한 대안`에 적은 각 대안을 최소 한 번 직접 비교하고, 요구사항·제약·팀 역량·운영 복잡도·비용·성능 등 실제 결정에 사용한 근거를 구체적으로 적는다. 확인한 수치·공식 문서·검증 결과가 있으면 함께 적고, "많이 사용된다", "성능이 좋다"처럼 프로젝트 맥락 없는 일반적인 장점만 나열하지 않는다.>

## 결과

<좋아지는 것 / 감수하는 것 / 되돌리려면 필요한 비용.>
```

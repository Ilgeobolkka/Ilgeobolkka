# 테스트 — Java/Spring 완료 기준

현재 프로젝트는 Java 21, Spring Boot, Gradle, MySQL을 사용한다. 실제로 존재하는 검증 명령만 실행하며
프런트엔드 등 아직 정해지지 않은 스택의 절차를 미리 추가하지 않는다.

## 실행 전 확인

- Compose 설정 문법: `docker compose config -q`
- Spring context·DB 통합 테스트가 필요하면 먼저 `docker compose up -d --wait`로 MySQL을 준비한다.
- DB 동작을 검증하는 테스트를 H2 같은 다른 데이터베이스로 대체하지 않는다.
- 현재 정적 분석 플러그인은 없다. `./gradlew check`를 린트라고 보고하지 않는다.

## 완료 체크리스트 (전부 통과해야 완료)

1. 변경 코드에 대응하는 테스트를 먼저 실행한다. 필요하면
   `./gradlew test --tests '<패키지.테스트클래스>'`로 범위를 좁힌다.
2. 전체 테스트 `./gradlew test`를 통과한다.
3. 전체 검사 `./gradlew check`를 통과한다.
4. 의존성·리소스·패키징에 영향을 줬으면 `./gradlew build`를 통과한다.
5. 실행 설정이나 시작 과정에 영향을 줬으면 `./gradlew bootRun`으로 정상 시작 로그를 확인한 뒤 종료한다.
6. 실행 명령, 통과/실패 테스트 수, 생략한 검증과 사유를 그대로 보고한다.

## 테스트 작성 — 커버리지 기준 (질적)

코드 작성·변경과 테스트 작성은 한 작업이다. **테스트 없는 코드는 미완료로 판정한다.**

- 새 기능 = 정상 경로 1개 + 실패/경계 경로 1개 이상을 JUnit 5로 작성한다.
- 변경·추가한 공개 함수/메서드와 조건 분기마다 대응 테스트를 둔다.
  판정 질문: "이 코드를 지우면 실패하는 테스트가 있는가?" — 없으면 테스트를 추가한다.
- 버그 수정 = 재현 테스트 먼저 작성 → 수정 → 통과 확인.
- 순수 도메인 규칙은 빠른 단위 테스트로, JPA·트랜잭션·동시성·고유 제약은 MySQL 통합 테스트로 검증한다.
- `@SpringBootTest`는 애플리케이션 context나 통합 경계를 확인할 때만 사용한다.
- 테스트가 곤란한 코드(외부 API, UI 렌더링 등)는 생략 사유와 수동 확인 절차를 보고한다.
  조용히 넘어가지 않는다.
- 새 테스트 라이브러리·정적 분석 플러그인이 필요하면 추가 전에 사용자에게 확인한다.

## 금지

- 통과를 위해 테스트를 약화(assertion 삭제, skip 처리)하지 않는다. 불가피하면 사유를 보고하고 승인받는다.

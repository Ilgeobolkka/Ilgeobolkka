# 0006. 백엔드 패키지를 도메인별로 구성한다

- 상태: 승인됨
- 날짜: 2026-07-22
- 결정자: 사용자

## 맥락

읽어볼까 백엔드는 독자, 도서, 열람, 포인트, 내 서재처럼 서로 다른 규칙을 구현해야 합니다. 모든
Controller, Service, Repository를 기술 계층별 최상위 패키지에 모으면 한 유스케이스를 수정할 때 관련
파일과 책임 경계를 찾기 어렵습니다. 반대로 구현 전부터 복잡한 모듈이나 추상 계층을 만들면 현재 MVP
규모에 비해 구조가 앞서갑니다.

## 고려한 대안

- 기술 계층 우선 패키지 — 초기 구조는 익숙하지만 기능이 늘수록 한 도메인의 변경 범위가 여러 최상위
  패키지로 흩어져 제외합니다.
- 도메인별 독립 Gradle 모듈 — 경계를 강하게 만들 수 있지만 현재 단일 Spring Boot MVP에는 빌드와
  의존성 관리 비용이 커 제외합니다.
- 도메인 우선 단일 모듈 — 관련 코드를 함께 찾을 수 있고 필요한 계층만 점진적으로 추가할 수 있어
  선택합니다.

## 결정

- `com.example.ilgeobolkka.<domain>` 아래에 도메인별 패키지를 둡니다.
- 각 도메인 안에서 필요한 코드만 `controller`, `service`, `repository`, `dto`, `entity`로 나눕니다.
- 여러 도메인이 실제로 공유하는 설정·예외·보안 코드는 `global`, 외부 시스템 연동 코드는 `infra`에
  둡니다.
- 한 도메인의 Service는 다른 도메인의 Repository를 직접 참조하지 않고 공개된 Service 메서드를 통해
  협력합니다.
- 아직 구현하지 않는 도메인이나 계층의 빈 패키지와 추상화는 만들지 않습니다.

## 결과

- 한 기능의 HTTP 경계, 유스케이스, 저장 코드를 도메인 패키지 안에서 함께 탐색할 수 있습니다.
- 도메인 간 협력 지점이 Service 경계에 드러나지만, 유스케이스가 복잡해지면 조정 책임을 별도로
  분리해야 할 수 있습니다.
- 멀티 모듈 수준의 컴파일 경계는 제공하지 않으므로 필요해질 때 별도 ADR로 전환 여부를 결정합니다.
- 세부 이름과 계층 책임은 [`docs/conventions.md`](../conventions.md)를 따릅니다.

# 0015. 서버 세션으로 웹 인증 상태를 관리한다

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

읽어볼까 MVP는 이메일·비밀번호 로그인을 사용하는 반응형 웹이며, 네이티브 앱이나 외부 API 소비자, 독립된 마이크로서비스 인증은 범위에 없습니다.
ADR-0008은 공개 API와 인증 필요 API를 구분했지만, 인증 상태를 쿠키·세션·토큰 중 어떤 방식으로 전달하고 유지할지는 후속 결정으로 남겼습니다.
현재 요구사항에서는 즉시 로그아웃과 서버 측 인증 무효화가 필요하고, JWT의 access token·refresh token 발급, 갱신, 폐기 절차를 도입할 이점은 작습니다.
또한 도메인의 `ReadingSession`과 로그인 상태를 유지하는 인증 세션을 명확히 분리해야 합니다.

## 고려한 대안

- 서버 세션과 불투명한 세션 ID 쿠키 — Spring Security의 기본 웹 인증 흐름을 활용하고 로그아웃 시 서버에서 즉시 무효화할 수 있어 현재 반응형 웹 MVP에 가장 단순합니다.
- access token·refresh token JWT와 `Authorization` 헤더 — 서버가 인증 상태를 저장하지 않고 여러 API 서버로 확장하기 쉽지만, 현재 필요하지 않은 토큰 갱신·회전·탈취 대응·강제 폐기 절차가 추가되어 제외합니다.
- JWT를 `HttpOnly` 쿠키로 전달 — JavaScript 노출은 줄일 수 있지만 쿠키가 자동 전송되는 요청의 CSRF 보호가 여전히 필요하고, 즉시 로그아웃을 보장하려면 별도 폐기 상태가 필요해 서버 세션보다 단순하지 않아 제외합니다.

## 결정

Spring Security와 서블릿 `HttpSession`을 사용해 인증 상태를 서버에서 관리합니다.
브라우저에는 사용자 정보나 JWT가 아니라 인증 세션을 찾기 위한 불투명한 세션 ID만 쿠키로 전달합니다.
로그인 성공 시 세션 ID를 교체하고, 로그아웃 시 서버 세션을 무효화하며 세션 쿠키를 삭제합니다.

세션 쿠키는 JavaScript에서 읽을 수 없도록 `HttpOnly`를 적용하고, 운영 HTTPS 환경에서는 `Secure`를 적용합니다.
프런트엔드와 API를 same-site로 배포할 때는 `SameSite=Lax`를 기본값으로 사용합니다.
프런트엔드 배포 토폴로지가 확정되기 전에는 쿠키의 `Domain`과 CORS 허용 출처를 고정하지 않습니다.
쿠키가 자동으로 전송되는 인증 방식이므로 Spring Security의 CSRF 보호를 끄지 않고, 상태를 변경하는 요청은 서버가 발급한 CSRF 토큰을 함께 검증합니다.

인증이 필요한 Controller는 인증된 `Principal`에서 `readerId`를 얻습니다.
요청 본문이나 경로로 전달된 사용자 식별자를 인증 근거로 신뢰하지 않으며, ADR-0008의 공개·인증 필요 엔드포인트 구분과 본인 자원 범위를 인가 기준으로 사용합니다.

로그인 인증 세션과 도메인의 `ReadingSession`은 서로 다른 수명과 책임을 갖습니다.
`HttpSession`은 로그인한 독자를 식별하고, `ReadingSession`의 `sessionToken`은 현재 뷰어와 페이지 과금 요청의 유효성만 검증합니다.
`sessionToken`을 로그인 자격 증명으로 사용하지 않으며, VIEW-002의 "사용자당 하나의 온라인 열람 세션"을 근거로 인증 세션 수를 하나로 제한하지 않습니다.

초기 구현은 서블릿 컨테이너의 세션 저장소를 사용합니다.
애플리케이션 다중 인스턴스 운영이나 재시작 후 로그인 유지가 필요해지면, 배포 방식과 함께 Spring Session JDBC 또는 Redis 같은 공유 세션 저장소를 별도로 결정합니다.

## 결과

- 이메일·비밀번호 로그인, 인증 유지, 로그아웃을 Spring Security의 서버 세션 흐름으로 단순하게 구현할 수 있습니다.
- 서버가 세션을 무효화하면 이후 요청이 즉시 인증되지 않으므로 JWT 폐기 목록이나 refresh token 회전 로직이 필요하지 않습니다.
- 인증된 `readerId`와 과금용 `sessionToken`의 책임이 분리되어, 로그인 여부와 열람 세션 교체 여부를 독립적으로 검증할 수 있습니다.
- 서버가 인증 상태를 보유하므로 인메모리 세션을 사용하는 동안 애플리케이션 재시작 시 사용자는 다시 로그인해야 합니다.
- 다중 인스턴스 운영에서는 공유 세션 저장소가 필요하며, 프런트엔드와 API가 cross-site로 배포되면 쿠키·CORS·CSRF 계약을 다시 검토해야 합니다.
- 네이티브 앱, 외부 API 소비자 또는 여러 독립 서비스 간 인증 전달이 필요해지면 JWT나 별도 인증 서버 도입을 새 ADR로 재검토합니다.

# 0016. Thymeleaf와 Bootstrap, Vanilla JavaScript로 프런트엔드를 구성한다

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

읽어볼까 MVP는 백엔드 구현과 페이지 과금 불변식 검증이 중심인 반응형 웹이며, 프런트엔드와 API를 별도 서비스로 운영할 요구사항이 없습니다.
ADR-0015는 Spring Security 서버 세션과 CSRF 보호를 사용하므로, 프런트엔드와 API를 같은 출처에서 제공하면 쿠키·CORS 설정을 단순하게 유지할 수 있습니다.
도서 탐색과 내역 조회는 서버 렌더링으로 충분하지만, 뷰어는 페이지 이동과 6초 후 열람 확정 요청, 실패 후 명시적 재시도를 처리할 브라우저 동작이 필요합니다.
기존 ADR-0008의 JSON API 계약과 ADR-0006의 도메인별 Facade 경계를 유지하면서 이 화면들을 구현할 프런트엔드 스택과 배포 단위를 결정해야 합니다.

## 고려한 대안

- React 또는 Vue와 Vite로 SPA 구성 — 복잡한 클라이언트 상태와 컴포넌트 생태계에는 유리하지만, 현재 MVP에는 Node.js 빌드·클라이언트 라우팅·상태 관리 비용이 더 큽니다.
- 정적 HTML과 Vanilla JavaScript만 사용 — 프레임워크 의존성은 없지만, 공통 레이아웃·서버 검증 오류·인증 화면의 마크업을 반복 관리해야 하므로 제외합니다.
- Thymeleaf와 HTMX 사용 — HTML 중심의 점진적 개선에는 유리하지만, 기존 JSON API 외에 HTML 조각 응답과 요청 이력·CSRF 처리 규칙이 추가되어 초기 범위를 넘어섭니다.
- 프런트엔드와 API를 별도 서버로 배포 — 독립 확장과 배포에는 유리하지만, 현재 단일 MVP에 CORS·쿠키 도메인·별도 배포 파이프라인을 추가할 이유가 없어 제외합니다.

## 결정

프런트엔드 화면은 Spring MVC와 Thymeleaf로 서버 렌더링합니다.
반응형 레이아웃과 기본 UI 컴포넌트에는 Bootstrap 5.3 계열과 필요한 최소한의 커스텀 CSS를 사용하며, 구현 시 선택한 패치 버전을 고정합니다.
브라우저 동작은 표준 JavaScript ES Modules와 `fetch`로 구현하고 React, Vue, HTMX 같은 추가 프런트엔드 프레임워크는 사용하지 않습니다.
초기 MVP에는 별도 Node.js, npm, Vite 빌드 단계를 도입하지 않습니다.

Thymeleaf 템플릿과 정적 자산은 API와 같은 Spring Boot 실행물에 포함해 같은 출처에서 제공합니다.
HTML을 반환하는 `@Controller`와 JSON을 반환하는 `@RestController`는 각각 같은 도메인의 Facade를 호출하며, 서로를 호출하거나 애플리케이션이 자기 API를 HTTP로 다시 호출하지 않습니다.
기존 ADR-0008의 `/api/**` JSON 계약은 유지하고, 뷰어처럼 브라우저 상태가 필요한 기능은 해당 API를 직접 호출합니다.
상태 변경 요청에는 ADR-0015에 따라 Spring Security가 발급한 CSRF 토큰을 포함합니다.

뷰어의 JavaScript는 페이지 이동 시 이전 타이머와 진행 중인 요청을 무효화하고, 서버가 반환한 `sessionToken`과 현재 페이지를 기준으로 열람 확정 요청을 구분합니다.
브라우저의 타이머는 확정 요청을 보낼 시점만 정하며, 6초 경과와 차감 가능 여부는 서버가 최종 판정합니다.
열람 확정 실패 후에는 자동으로 다시 요청하지 않고 사용자가 명시적으로 재시도할 때만 요청합니다.

## 결과

- 프런트엔드와 API를 하나의 Spring Boot 실행물로 빌드·배포하고 same-origin 세션 쿠키와 CSRF 보호를 사용할 수 있습니다.
- 별도 프런트엔드 서버, CORS 설정, Node.js 빌드 파이프라인 없이 백엔드 중심 MVP를 구현할 수 있습니다.
- 공통 레이아웃과 서버 검증 결과는 Thymeleaf로 재사용하고, 동적 상태가 필요한 뷰어에만 JavaScript 복잡도를 집중합니다.
- HTML Controller와 JSON Controller라는 두 표현 계층 어댑터를 유지해야 하지만, 비즈니스 로직은 같은 Facade 아래에서 공유합니다.
- 뷰어의 타이머·요청 무효화·재시도 동작은 별도의 브라우저 시나리오 검증이 필요합니다.
- 향후 독립 프런트엔드 팀, 네이티브 앱, 복잡한 클라이언트 상태가 필요해지면 SPA와 별도 배포를 새 ADR로 재검토해야 합니다.

# 0016. API 오류를 실패 성격에 따라 HTTP 상태로 구분한다

- 상태: 승인됨
- 날짜: 2026-07-24

## 맥락

프런트엔드는 실패 원인을 식별해 재로그인, 최신 상태 재조회, 포인트 부족 안내처럼 서로 다른 행동을
해야 합니다. 모든 도메인 실패를 같은 HTTP 상태로 반환하면 오류 바디를 해석하기 전에는 다음 행동을
결정할 수 없습니다. 이 결정은 승인된 ADR-0008에서 분리했으며, 상태별 적용 대상은
[`API 명세`](../../../api/api-contract.md)가 정본입니다.

## 고려한 대안

- 모든 클라이언트 오류를 `400 Bad Request`로 통일 — 매핑은 단순하지만 요청 형식 오류와 인증·상태
  충돌·비즈니스 규칙 거부를 구분하지 못합니다.
- 모든 도메인 실패를 `409 Conflict`로 통일 — 형식·인증 오류와는 구분되지만 최신 상태를 조회해
  재시도할 충돌과 현재 요청을 그대로 처리할 수 없는 경우를 구분하지 못합니다.
- 실패 성격별 HTTP 상태 사용 — 서버와 클라이언트가 상태 분류표를 함께 지켜야 하지만 HTTP 상태만으로
  실패의 큰 범주와 다음 행동을 판단할 수 있습니다.

## 결정

### 선택한 기술

API 오류는 요청 형식, 인증·인가, 리소스 부재, 현재 상태 충돌, 처리할 수 없는 비즈니스 규칙과 서버
오류를 구분해 `400`, `401`, `403`, `404`, `409`, `422`, `500` 상태로 반환합니다.

### 핵심 근거

- **클라이언트 행동 — 의미별 상태 vs 단일 상태**: 교체된 세션처럼 최신 상태를 확인한 뒤 다시
  시도할 수 있는 충돌은 `409`, 잔액 부족처럼 현재 요청을 그대로 다시 보내도 처리할 수 없는 경우는
  `422`로 구분합니다. 인증이 필요한 경우와 존재하지 않는 리소스도 각각 `401`·`404`로 구분해
  프런트엔드의 다음 행동을 좁힙니다.
- **HTTP 의미 — `409` vs `422`**:
  [RFC 9110의 409](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.10)는 대상 리소스의
  현재 상태와 충돌하는 경우를,
  [422](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.21)는 문법은 올바르지만 포함된
  지시를 처리할 수 없는 경우를 설명합니다. 잔액 부족을 `422`로 분류하는 것은 표준이 강제하는
  유일한 답이 아니라, 이 프로젝트가 실패 후 행동을 구분하기 위한 계약입니다.
- **세부 원인 — HTTP 상태 vs 오류 코드**: 같은 상태 안의 세부 원인은
  [`ADR-0018`](./0018-use-minimal-api-error-body.md)의 오류 코드로 구분합니다. 상태 코드는 큰 범주,
  오류 코드는 구체적인 규칙을 담당해 하나의 숫자 상태에 프로젝트 규칙을 모두 싣지 않습니다.

## 결과

- 클라이언트는 HTTP 상태로 실패 범주를 먼저 판단하고 오류 코드로 세부 원인을 확인합니다.
- 상태별 구체적인 엔드포인트와 오류 코드는 API 명세에서 관리하며 ADR에 목록을 반복하지 않습니다.
- 새로운 실패를 추가할 때 기존 분류로 표현할 수 없다면 상태를 임의로 재사용하지 않고 이 결정을
  재검토합니다.

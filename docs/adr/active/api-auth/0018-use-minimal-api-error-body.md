# 0018. API 오류 바디에 code와 message를 사용한다

- 상태: 승인됨
- 날짜: 2026-07-24

## 맥락

같은 HTTP 상태 안에서도 세션 교체, 확정 시간 미달처럼 클라이언트가 다르게 처리할 원인이 존재합니다.
클라이언트가 메시지 문구를 해석하지 않고 실패 규칙을 식별할 수 있는 공통 오류 바디가 필요합니다.
이 결정은 승인된 ADR-0008에서 분리했으며, 실제 오류 코드 목록은
[`API 명세`](../../../api/api-contract.md)가 정본입니다.

## 고려한 대안

- HTTP 상태와 문자열 메시지만 반환 — 필드는 가장 적지만 같은 상태 안의 원인을 안정적으로 구분하려면
  변경될 수 있는 사용자 메시지에 의존해야 합니다.
- RFC 9457 Problem Details와 확장 `code` 사용 — 표준 미디어 타입·필드와 확장 방법을 얻지만 현재
  자체 웹 프런트엔드만을 위해 별도의 표준 응답 형식을 함께 관리해야 합니다.
- 자체 `{code, message}` 바디 — 표준 Problem Details와 직접 호환되지 않지만 현재 클라이언트가
  실제로 사용하는 규칙 식별자와 사용자 메시지만 계약으로 고정합니다.

## 결정

### 선택한 기술

모든 API 오류는 안정적인 `code`와 사용자에게 표시할 수 있는 `message`를 JSON 최상위 필드로
반환합니다. `code`는 구현 예외 클래스명이 아니라 API 명세에 등록된 외부 계약입니다.

### 핵심 근거

- **클라이언트 분기 — `code` vs 메시지 해석**: `message`는 표현을 다듬거나 다국어를 적용할 때
  바뀔 수 있습니다. 프런트엔드는 변경되지 않는 `code`로 분기하고 `message`는 표시에만 사용합니다.
- **현재 소비자 — 최소 바디 vs RFC 9457**: RFC 9457은 문제 유형을 표현하고 확장 필드를 허용하는
  표준 형식입니다. 현재 MVP는 하나의 자체 웹 프런트엔드만 소비하므로 표준 상호운용성보다 프로젝트
  오류 코드를 직접 사용하는 작은 계약을 선택합니다.
  [Spring MVC가 RFC 9457을 지원](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html)하므로
  구현 난이도가 아니라 현재 소비자에게 필요한 계약 범위를 기준으로 선택합니다.
- **계약 크기 — 최소 필드 vs 선제적 확장**: 필드 단위 검증 오류가 실제로 필요해질 때만 별도 필드를
  추가합니다. 지금 `errors[]`까지 고정하는 대안보다 초기 계약이 작지만, 새 필드를 추가할 때
  클라이언트 호환성을 검토해야 하는 비용을 감수합니다.

## 결과

- 모든 오류가 같은 두 필드를 제공하고 클라이언트는 HTTP 상태와 `code`를 함께 사용합니다.
- `code`를 추가·변경할 때 API 명세를 함께 갱신하며 기존 코드의 의미를 다른 실패에 재사용하지 않습니다.
- 외부 소비자가 늘어 표준 문제 문서가 필요해지면
  [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html#section-3)로의 전환을
  새 ADR에서 검토합니다.

# 0028. 운영 관계형 데이터베이스로 Amazon RDS for MySQL을 사용한다

- 상태: 승인됨
- 날짜: 2026-07-25

## 맥락

잉크 잔액·내역과 페이지 대여는 한 트랜잭션으로 갱신되고 행 잠금과 고유 제약을 사용합니다.
소규모 팀은 데이터베이스 백업, 패치와 장애 복구를 직접 운영하는 대신 애플리케이션 구현과 과금 정확성 검증에 집중해야 합니다.

## 고려한 대안

- EC2에 MySQL 직접 설치 — 인스턴스 비용을 세밀하게 조절할 수 있지만 백업, 패치, 모니터링과 장애 복구를 팀이 직접 담당해야 합니다.
- Amazon Aurora MySQL-Compatible — 확장성과 고가용성 기능이 강하지만 초기 MVP 트래픽과 비용에 비해 과합니다.
- Amazon RDS for PostgreSQL — 같은 트랜잭션 요구를 충족할 수 있지만 기존 MySQL 8.4 마이그레이션·잠금 검증을 다시 작성해야 합니다.
- Amazon RDS for MySQL — 사용량이 없어도 비용이 들지만 현재 로컬 SQL과 InnoDB 잠금 동작을 유지하면서 관리 작업을 줄일 수 있습니다.

## 결정

### 선택한 기술

운영 데이터베이스는 Amazon RDS for MySQL 8.x를 사용하고 로컬 개발·통합 테스트는 Docker Compose의 MySQL 8.4를 사용합니다.
스키마는 Flyway로 관리하며 운영 Hibernate DDL 자동 변경을 사용하지 않습니다. 문자 집합은 `utf8mb4`, 애플리케이션 저장 시각은 UTC로 통일합니다.

### 핵심 근거

- **트랜잭션 동작 — 동일 MySQL 계열 vs 다른 DB**: 로컬과 운영에서 InnoDB의 행 잠금, 격리 수준과 고유 제약 동작을 같은 계열로 검증할 수 있습니다.
- **운영 부담 — RDS vs 자체 설치**: 자동 백업, 패치 창, 모니터링과 스냅샷 기능을 사용해 데이터베이스 서버 관리 범위를 줄입니다.
- **비용과 규모 — RDS MySQL vs Aurora**: 초기에는 한 애플리케이션과 작은 데이터베이스로 검증하며 읽기 복제본·서버리스 확장 기능이 필요하지 않습니다.
- **기존 자산 — MySQL vs PostgreSQL**: 현재 Flyway V1, 잠금 ADR과 통합 테스트가 MySQL을 기준으로 검증되어 있어 DB 교체는 제품 기능 없이 일정 위험만 늘립니다.

## 결과

- RDS는 공개 인터넷에 직접 노출하지 않고 애플리케이션 보안 그룹에서만 접근하게 하며 저장 암호화, 전송 TLS와 자동 백업을 활성화합니다.
- 접속 정보는 환경 변수 또는 AWS Secrets Manager로 주입하고 저장소에 기록하지 않습니다.
- 사용량이 적어도 AWS 비용이 발생하며 MVP에는 최소 사양과 단일 운영 환경을 사용합니다.
- 다중 AZ, 읽기 복제본, RDS Proxy와 Aurora는 실제 가용성·부하 요구가 생긴 뒤 재검토합니다.
- 이 결정은 Java·Spring Boot·RDS를 묶어 기록한 ADR-0004의 데이터베이스 결정을 대체합니다.

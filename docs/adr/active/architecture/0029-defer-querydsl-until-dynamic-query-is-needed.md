# 0029. 동적 조회 요구가 생길 때까지 QueryDSL 도입을 미룬다

- 상태: 승인됨
- 날짜: 2026-07-25

## 맥락

현재 도서 조회는 고정된 카테고리 정렬·페이지네이션과 하나의 검색어로 제목 또는 저자를 찾는 기능뿐입니다.
여러 선택 조건, 사용자 정렬 조합, 복잡한 조인이나 동적 필터가 없는 상태에서 Q타입 생성과 외부 QueryDSL 버전 관리를 계속 부담할 필요가 있는지 다시 판단했습니다.

## 고려한 대안

- Spring Data JPA 쿼리 메서드 — 단순 단일 조건은 의도가 분명하지만 제목 또는 저자 검색과 고정 정렬을 이름에 모두 넣으면 메서드명이 길어집니다.
- JPQL을 `EntityManager`로 직접 작성 — 의존성은 없지만 조회 코드와 페이지네이션 연결을 직접 관리해야 합니다.
- Spring Data JPA `@Query` — 문자열 쿼리의 필드 변경을 컴파일 때 잡지 못하지만 현재 검색 한 건을 짧게 표현하고 `Pageable`을 그대로 사용할 수 있습니다.
- Criteria API 또는 Specification — 외부 의존성은 없지만 현재 고정 조건에 비해 조합 코드가 장황합니다.
- OpenFeign QueryDSL — 타입 안전성과 복합 동적 조회 표현은 좋고 현재 7.5 호환 검사도 통과하지만 Q타입 생성·버전 관리 비용을 정당화할 동적 요구가 없습니다.

## 결정

### 선택한 기술

MVP 조회는 단순 식별자·고정 조건에 Spring Data JPA 쿼리 메서드를 사용하고,
제목 또는 저자 부분 일치와 카테고리 고정 정렬에는 필요한 최소 `@Query`를 사용합니다.
QueryDSL 의존성과 annotation processor는 후속 구현에서 제거합니다.
독립적인 선택 조건이 세 개 이상 조합되거나 다중 정렬·복잡한 조인이 실제 요구사항으로 확정될 때 다시 비교합니다.

### 핵심 근거

- **요구 적합성 — `@Query` vs QueryDSL**: 현재 검색은 `keyword` 하나가 제목 또는 저자에 포함되는 고정 논리라 런타임 조건 조립이 없습니다.
  타입 안전 빌더의 핵심 이점을 사용하지 않습니다.
- **빌드 복잡도 — 기본 JPA vs Q타입 생성**: QueryDSL은 별도 버전, annotation processor와 생성 소스 검증이 필요합니다.
  요청 기능을 지워도 동작하는 의존성은 단순함 원칙에 맞지 않습니다.
- **표현 길이 — `@Query` vs 긴 쿼리 메서드**: 검색 한 건은 명시적인 JPQL로 두어 `Or` 조건과 정렬이 긴 메서드명에 숨지 않게 합니다.
- **확장 시점 — 현재 제거 vs 영구 금지**: 복합 동적 검색이 생기면 Criteria보다 QueryDSL이 읽기 쉬울 수 있으므로 실제 조건 수와 조인 빈도를 근거로 다시 결정합니다.
- **호환성 — 필요성과 동작 가능성 분리**: 2026-07-25의 `./gradlew check`로 OpenFeign QueryDSL 7.5가 현재 Spring Boot 4.1.0 조합에서 동작함은 확인했습니다.
  제거 이유는 호환 실패가 아니라 현재 제품 요구에 필요하지 않기 때문입니다.

## 결과

- 후속 구현에서 `build.gradle`의 QueryDSL 의존성과 Q타입 검증용 테스트 fixture를 제거해야 현재 결정과 코드가 일치합니다.
- `@Query`가 늘어나거나 조건 조합이 복잡해지면 이 ADR의 재검토 조건에 도달한 것으로 봅니다.
- 이 결정은 OpenFeign QueryDSL 도입을 정한 ADR-0009를 대체합니다.

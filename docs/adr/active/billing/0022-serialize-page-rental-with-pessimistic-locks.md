# 0022. 페이지 대여를 비관적 잠금으로 직렬화한다

- 상태: 승인됨
- 날짜: 2026-07-25

## 맥락

같은 독자가 대여가 없거나 만료된 페이지를 동시에 여러 번 요청하면 각 요청이 잔액을 확인한 뒤 중복 차감할 수 있습니다.
서로 다른 페이지의 동시 요청도 하나의 잉크 잔액을 함께 변경하므로, 음수 잔액 방지와 잉크 차감·내역·대여의 원자성을 한 트랜잭션에서 보장해야 합니다.

## 고려한 대안

- 애플리케이션 선조회와 대여 고유 제약만 사용 — 간단하지만 재대여 이력을 여러 행으로 보존하면 시간 조건인 “유효한 대여 하나”를 일반 고유 제약으로 표현할 수 없습니다.
- `@Version` 낙관적 잠금 — 충돌이 적을 때 대기 시간을 줄이지만 충돌 응답과 재시도 정책이 필요하고 잉크 계정·세션·대여를 함께 다시 검증해야 합니다.
- 분산 락 — 여러 인스턴스에서도 동작하지만 별도 저장소와 장애 처리가 필요해 MySQL 하나를 사용하는 MVP에는 과합니다.
- 세션과 잉크 계정을 고정 순서로 비관적 잠금 — 같은 독자의 페이지 요청을 잠시 직렬화하지만 최신 대여와 잔액을 한 트랜잭션에서 단순하게 다시 확인할 수 있습니다.

## 결정

### 선택한 기술

Spring Data JPA의 `PESSIMISTIC_WRITE` 또는 동등한 MySQL InnoDB 잠금 읽기를 사용합니다.
페이지 열기 트랜잭션은 `ReadingSession`을 먼저 잠가 토큰·도서·페이지를 확인합니다.
새 세션을 만들 때는 `reader_id` 고유 키에 대한 MySQL upsert로 세션 행을 만들거나 갱신하면서 같은 행 잠금을 얻습니다.
그다음 `InkAccount`를 잠그고 같은 서버 시각으로 해당 페이지의 최신 `PageRental`을 다시 조회합니다.

유효한 대여가 있으면 차감 없이 마지막 위치만 갱신합니다.
유효한 대여가 없으면 잔액을 확인하여 1잉크 차감, `InkLedger`, `PageRental`, `LibraryEntry`를 같은 트랜잭션에 반영합니다.
잔액이 부족하거나 중간 단계가 실패하면 모두 롤백하고 페이지 콘텐츠를 제공하지 않습니다.

### 핵심 근거

- **중복 차감 — 잠금 후 재조회 vs 선조회**:
  두 요청이 같은 초기 상태를 보더라도 두 번째 요청은 계정 잠금을 얻은 뒤 첫 요청이 커밋한 대여를 확인하므로 다시 차감하지 않습니다.
- **잔액 보존 — 계정 행 잠금 vs 낙관적 재시도**:
  서로 다른 페이지 요청도 하나의 계정 행에서 순서대로 최신 잔액을 확인해 음수 잔액과 잃어버린 갱신을 막습니다.
- **세션 교체 — 세션 우선 잠금 vs 계정만 잠금**:
  새 뷰어가 기존 세션을 바꾸는 요청과 오래된 세션의 페이지 요청이 겹쳐도 유효한 세션만 차감하도록 검증부터 커밋까지 세션 상태를 고정합니다.
- **잠금 순서 — 세션 다음 계정**:
  모든 쓰기 흐름이 같은 순서를 사용하면 서로 반대 순서로 잠가 생기는 교착 가능성을 줄일 수 있습니다.
- **운영 복잡도 — 데이터베이스 잠금 vs 분산 락**:
  현재 단일 MySQL이 이미 트랜잭션 정본이므로 새 인프라 없이 필요한 범위를 보호합니다.

## 결과

- 같은 사용자의 페이지 열기 요청은 짧은 트랜잭션 동안 직렬화됩니다.
  MVP 트래픽에서는 정확성을 우선하며 실제 대기 시간이 문제가 될 때 낙관적 잠금이나 더 작은 잠금 범위를 다시 검토합니다.
- 외부 파일 저장소에서 페이지 콘텐츠를 읽는 작업은 잠금 시간을 늘리지 않도록 트랜잭션 커밋 뒤에 수행합니다.
- 세션 생성·페이지 이동·페이지 열기 경로에서 두 행을 함께 변경할 때는 `ReadingSession → InkAccount` 잠금 순서를 지켜야 합니다.
- 이 결정은 6초 열람 확정 트랜잭션을 다룬 ADR-0017을 대체합니다.

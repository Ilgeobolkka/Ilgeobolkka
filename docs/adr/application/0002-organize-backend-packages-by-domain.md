# 0002. 백엔드 패키지를 도메인별로 구성한다

- 상태: 승인됨
- 날짜: 2026-07-22

## 맥락

독자, 도서, 열람, 잉크, 대여와 소장은 서로 다른 규칙을 가집니다. Controller, Service, Repository를
기술 계층별 최상위 패키지에 모으면 한 유스케이스의 변경 범위와 도메인 경계를 찾기 어렵습니다.
반대로 초기 MVP부터 멀티 모듈과 추상 계층을 도입하면 구조 비용이 기능보다 커집니다.

## 고려한 대안

- 기술 계층 우선 패키지 — 익숙하지만 한 도메인의 코드가 여러 최상위 패키지로 흩어져 제외합니다.
- 도메인별 독립 Gradle 모듈 — 경계는 강하지만 단일 Spring Boot MVP에 빌드·의존성 비용이 커 제외합니다.
- Controller가 Service를 직접 조합 — 계층은 적지만 도메인 횡단 흐름과 트랜잭션 책임이 HTTP 계층으로 새어 나가 제외합니다.
- 도메인 우선 단일 모듈과 Facade — 관련 코드를 함께 찾고 유스케이스 경계를 한곳에 둘 수 있어 선택합니다.

## 결정

- `com.example.ilgeobolkka.<domain>` 아래에 도메인별 패키지를 둡니다.
- 각 도메인은 필요한 계층만 `controller`, `facade`, `service`, `repository`, `dto`, `entity`로 나눕니다.
- Controller는 같은 도메인의 Facade만 호출합니다.
- Facade는 유스케이스와 트랜잭션 경계를 소유하고 필요한 도메인 Service를 조합합니다.
- Service는 자기 도메인의 규칙과 Repository 접근을 담당합니다.
- 공통 설정·예외·보안은 `global`, 외부 시스템 연동은 `infra`에 둡니다.
- 세부 의존 방향과 이름은 [백엔드 구현 컨벤션](../../conventions.md)을 따릅니다.

## 결과

- 한 기능의 HTTP 경계, 유스케이스, 도메인 규칙과 저장 코드를 함께 탐색할 수 있습니다.
- 도메인 간 협력과 트랜잭션 경계가 Facade에 드러납니다.
- 단순 조회도 Facade를 거쳐 위임 코드가 늘 수 있습니다.
- 컴파일 수준의 모듈 경계가 필요해지면 멀티 모듈 전환을 별도 기술 결정으로 검토해야 합니다.

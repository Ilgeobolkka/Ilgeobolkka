# 0014. 페이지 열기 트랜잭션을 READ COMMITTED로 낮춘다

- 상태: 승인됨
- 날짜: 2026-07-30

## 맥락

`docs/prd/product-policy.md`의 "페이지 열기 처리 순서와 원자성" 4단계는 소장·활성 대여가 없어
보이면 `InkAccount`를 잠근 뒤 **소장과 활성 대여를 다시 확인**하라고 정한다. 같은 페이지 열기
요청이 동시에 들어와도 한 번만 차감하기 위한 장치이며 `docs/test-strategy.md`의 INV-002가 이를
불변식으로 못박는다.

이 저장소는 격리 수준을 따로 설정하지 않아 MySQL InnoDB 기본값인 REPEATABLE READ로 동작한다.
REPEATABLE READ에서 트랜잭션은 첫 읽기 시점에 일관된 스냅샷을 만들고, 이후 **일반 SELECT는 계속
그 스냅샷을 읽는다.** 소장 확인(`existsByReaderIdAndBookId`)과 활성 대여 확인은 모두 일반
SELECT다.

따라서 잠금 획득 뒤 같은 조회를 반복해도 그 사이 다른 트랜잭션이 커밋한 소장·대여 행이 보이지
않는다. `InkAccountRepository.findByReaderIdForUpdate`로 `ink_account` 행을 잠그는 것은 그
테이블에 대한 잠금 읽기일 뿐이며 다른 테이블의 스냅샷을 갱신하지 않는다. 재확인 코드는 작성되어
있으나 **아무 일도 하지 않는 상태**가 되고, 컴파일·단위 테스트·대여 행을 미리 커밋해 두는 통합
테스트는 모두 통과한다. 즉 정책 4단계가 막으려는 중복 차감이 조용히 남는다.

이 결정은 잉크 차감을 실제로 수행하는 후속 작업과 소장 결제·페이지 열기 교차 경합에도 그대로
상속된다.

## 고려한 대안

- 재확인 조회를 잠금 읽기로 만든다(`book_ownership`·`page_rental` 존재 확인에
  `@Lock(PESSIMISTIC_WRITE)` 전용 메서드 추가) — 기존 `InkAccountRepository`,
  `InkPurchaseRepository` 패턴과 일관되고 트랜잭션 격리 의미를 건드리지 않는다 /
  두 테이블에 잠금 읽기 메서드를 새로 만들어야 하고, 재확인 경로마다 일반 조회와 잠금 조회를
  구분해 호출해야 해서 호출 규약이 늘어난다. 잠금 대상이 늘어나 교착 가능성을 다시 따져야 한다.
- 애플리케이션 전체 기본 격리 수준을 READ COMMITTED로 바꾼다 — 설정 한 줄 /
  페이지 열기와 무관한 기존 트랜잭션의 읽기 의미까지 함께 바뀌어 영향 범위가 과하다.
- 새 인프라(분산 락, 메시지 브로커)로 직렬화한다 — 스냅샷 문제를 우회한다 /
  `docs/conventions.md`가 행 잠금·재확인·고유 제약으로 해결하라고 정하고 있어 채택하지 않는다.

## 결정

페이지 열기 유스케이스 진입점(`ReadingFacade.openPage`)의 트랜잭션만
`@Transactional(isolation = READ_COMMITTED)`로 낮춘다. 잠금 획득 이후의 재확인 조회가 항상 최신
커밋 데이터를 읽게 하는 것이 목적이며, 잠금 순서는 기존과 동일하게 `InkAccount`를 먼저 잠근다.
`ink_account` 잠금 쿼리는 계속 `findByReaderIdForUpdate` 하나만 쓴다.

애플리케이션 기본 격리 수준은 바꾸지 않는다. 이 유스케이스에만 적용한다.

## 결과

좋아지는 것: 정책 4단계 재확인이 실제로 동작한다. 재확인 조회를 위해 새 잠금 쿼리를 만들지
않아 잠금 대상이 늘지 않고 교착 위험이 그대로다. 후속 차감 구현도 같은 트랜잭션 경계를 그대로
쓴다.

감수하는 것: 이 트랜잭션 안에서는 같은 조회를 반복할 때 결과가 달라질 수 있다(non-repeatable
read). 페이지 열기 경로는 재확인이 목적이므로 문제가 되지 않지만, 이 트랜잭션에 코드를 추가할
때 "한 트랜잭션 안에서 읽은 값은 변하지 않는다"고 가정하면 안 된다. 팬텀 읽기도 허용된다.
또한 격리 수준이 유스케이스마다 다르므로 트랜잭션 경계를 읽을 때 격리 속성을 함께 봐야 한다.

주의: 이 격리 속성은 **새 트랜잭션을 시작할 때만** 적용된다. 이미 트랜잭션이 열려 있으면
(예: 클래스에 `@Transactional`이 붙은 테스트) Spring 기본 설정에서는 격리 속성이 조용히
무시되고 바깥 트랜잭션의 격리 수준을 따른다. 재확인 동작을 검증하는 테스트는 트랜잭션 없이
실제 커밋 상태로 확인해야 한다.

되돌리려면: REPEATABLE READ로 돌아가는 순간 재확인이 다시 무효가 되므로, 위 첫 번째 대안대로
`book_ownership`·`page_rental` 잠금 읽기 메서드를 추가하고 재확인 경로 전체를 그 메서드로
바꿔야 한다. 설정 한 줄을 되돌리는 것으로 끝나지 않는다.

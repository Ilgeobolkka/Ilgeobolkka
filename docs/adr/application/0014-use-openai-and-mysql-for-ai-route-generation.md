# 0014. OpenAI와 MySQL로 AI 잉크 경로를 생성한다

- 상태: 대체됨 — [ADR-0015](./0015-harden-openai-ai-route-generation.md)
- 날짜: 2026-08-04

## 맥락

AI 잉크 경로는 한 권의 페이지에서 목적 관련 후보를 찾고 선수 개념, 중복과 순서를 고려한 구조화된 경로를
10초 목표로 생성해야 합니다. 소설을 제외한 시연 도서는 권당 48~72페이지이므로 한 요청에서 비교할 벡터가
작습니다. 기존 시스템은 단일 Spring Boot 애플리케이션과 MySQL을 운영하며 별도 AI·벡터 검색 인프라가
없습니다.

외부 공급자 전송은 실제 출판 콘텐츠의 권리와 데이터 보관 정책을 확인해야 하며, 공급자나 임베딩 모델을
바꾸면 전체 분석 벡터 재생성과 품질 회귀 검증이 필요합니다. 별도 벡터 데이터베이스 도입은 검색 기능을
주지만 현재 규모에서는 새 배포·장애·백업 경계를 만듭니다.

OpenAI API는 사용자가 데이터 공유를 별도로 선택하지 않는 한 API 입력을 모델 학습에 사용하지 않지만,
기본 악용 모니터링 로그에는 고객 콘텐츠가 최대 30일 보관될 수 있습니다. Responses API는 기본값이나
`store=true`에서 응답 애플리케이션 상태를 최소 30일 보관하므로 `store=false`를 사용합니다. 다만 이
설정은 응답 상태 저장만 끄며 악용 모니터링과 프롬프트 캐시를 끄지 않습니다. GPT-5.6의 비-ZDR 요청에서는
원문이 아닌 입력 파생 key/value tensor가 GPU 로컬 스토리지에 최대 24시간 애플리케이션 상태로 남을 수
있고 `prompt_cache_options.ttl`은 최소 캐시 수명이지 최대 보관 제한이 아닙니다. Modified Abuse
Monitoring은 고객 콘텐츠를 악용 모니터링 로그에서 제외하지만 이 파생 캐시 보관을 제거하지 않으며, Zero
Data Retention은 적격 엔드포인트의 고객 콘텐츠 애플리케이션 상태 보관을 제거합니다. 두 데이터 제어는 사전
승인이 필요합니다. 구체적인 현재 조건은
[OpenAI 데이터 제어 문서](https://developers.openai.com/api/docs/guides/your-data#storage-requirements-and-retention-controls-per-endpoint)와
[프롬프트 캐시 보관 문서](https://developers.openai.com/api/docs/guides/prompt-caching#prompt-cache-retention)를
따릅니다.

OpenAI 데이터 제어는
[조직과 프로젝트에서 따로 설정](https://developers.openai.com/api/docs/guides/your-data#configuring-data-retention-controls)할
수 있고 배포 밖의 관리 작업으로 바뀔 수 있습니다.
따라서 콘텐츠 메타데이터와 애플리케이션 환경설정만 비교해서는 실제 API 키가 속한 프로젝트의 실효 정책을
증명할 수 없습니다. 공식 Admin API와 Terraform 프로젝트 제어는 데이터 보관 정책의 원격 상태와 drift를
확인할 수 있지만, 학습용 데이터 공유 참여 상태는 같은 방식으로 읽을 수 있는 필드를 제공하지 않습니다.
검증할 수 없는 값을 자동 정책 해시에 섞으면 1시간 원격 증명 계약을 구현할 수 없습니다. 또한 품질 평가는
특정 모델·추론 설정·프롬프트와 서버 경로 정책으로 실행되므로,
평가 증거를 설정값이나 수동 버전과만 결합하면 구현 코드를 바꾸고 버전을 올리지 않은 실행물이 같은 해시로
`PUBLIC` 콘텐츠를 호출할 수 있습니다. 따라서 평가한 실행물과 공개 서버의 바이트 동일성도 증명해야 합니다.

## 고려한 대안

- 온디바이스 또는 자체 호스팅 모델 — 콘텐츠 통제는 강하지만 2차 MVP에 모델 운영·GPU·품질 튜닝 범위가 커 제외합니다.
- 외부 AI와 별도 벡터 데이터베이스 — 대규모 근사 검색에는 적합하지만 한 번에 최대 72개 벡터만 비교하는 현재 범위에 인프라가 과해 제외합니다.
- 외부 AI와 요청 시 전체 페이지 직접 전달 — 사전 적재는 단순하지만 지연·토큰 비용·본문 외부 전송량이 커 제외합니다.
- OpenAI 임베딩·구조화 생성과 MySQL 벡터 저장 — 기존 운영 경계를 유지하면서 후보 검색과 경로 구성을 분리할 수 있어 선택합니다.
- 배포 체크리스트만으로 생성 설정과 OpenAI 프로젝트 정책 확인 — 구현은 단순하지만 환경설정·API 키 교체와
  원격 정책 drift 뒤에도 기존 `PUBLIC` 상태가 남으므로 제외합니다.
- 후보 선택·서버 경로 정책의 수동 버전만 `generationConfigHash`에 포함 — 버전 갱신을 빠뜨린 코드 변경을
  탐지할 수 없으므로 제외합니다. 평가에 사용한 패키징 JAR의 SHA-256을 함께 결합합니다.
- 학습용 데이터 공유 비활성 여부를 `openAiPolicyHash`에 포함 — 공식 관리 인터페이스로 원격 갱신할 수 없어
  자동 증명과 정확한 만료를 구현할 수 없으므로 제외합니다. 조직 관리자 확인 증거를 별도 출시 게이트로
  관리합니다.
- Modified Abuse Monitoring과 GPT-5.6 `prompt_cache_options.mode=explicit`, 명시적 breakpoint 없음 —
  [프롬프트 캐시 가이드](https://developers.openai.com/api/docs/guides/prompt-caching#prompt-cache-breakpoints)는
  이 요청이 캐시를 사용하지 않는다고 설명하지만 데이터 제어 문서는 비-ZDR 요청의 extended prompt
  caching을 더 넓게 설명합니다. 고객 콘텐츠 애플리케이션 상태 보관 금지 계약에 문서 해석 차이를 남기지
  않기 위해 2차 MVP에서는 채택하지 않고 Zero Data Retention만 허용합니다. 두 공식 계약이 일치하고 통합
  검증으로 무보관을 증명할 수 있을 때 새 결정으로 다시 검토합니다.

## 결정

- AI 공급자는 OpenAI로 정하고 외부 연동은 `infra` 경계 뒤의 교체 가능한 애플리케이션 인터페이스로 격리합니다.
- 페이지 분석 임베딩의 기본 모델은 `text-embedding-3-small`입니다.
- 경로 구성의 기본 모델은 `gpt-5.6-terra`이며 `/v1/responses`의 구조화된 응답을 한 번의 요청 단위로
  사용합니다. `store=false`를 항상 보내고 Conversations·Background mode·호스팅 도구는 사용하지 않습니다.
- 경로 모델 ID, 추론 mode·effort, 프롬프트·구조화 출력 스키마, 후보 선택·서버 경로 정책 버전과 평가에
  사용한 패키징 JAR 바이트의 SHA-256 `generationArtifactHash`를 정규화해
  `generationConfigHash`를 만듭니다. 평가는 이후 공개 서버에 배포할 바로 그 JAR로 실행하고, 배포는 해당
  JAR을 다시 빌드하지 않고 바이트 그대로 사용합니다. 공개 서버는 시작과 외부 호출 전에 자신의
  `generationArtifactHash`를 포함해 현재 해시를 다시 계산합니다. JAR이 한 바이트라도 다르면 설정 버전이
  같아도 실패 폐쇄하며 새 코퍼스 평가와 공개 승인을 요구합니다.
- 콘텐츠 적재 단계에서 외부 전송 권리와 데이터 보관 조건을 확인한 모든 지원 페이지의 비공개 분석 텍스트를
  Embeddings API에 보내 페이지 임베딩을 생성합니다. 적재 요청과 런타임 요청의 입력을 섞지 않습니다.
- 페이지 임베딩은 기존 MySQL에 저장합니다. 경로 생성 요청마다 정규화한 독서 목적을 페이지 임베딩과 같은
  모델·차원으로 Embeddings API에 보내 임베딩하고, 요청한 책의 페이지 벡터만 애플리케이션으로 읽어
  cosine 유사도를 계산합니다. 콘텐츠 버전에는 임베딩 모델과 차원을 함께 묶어 다른 프로필의 벡터를
  비교하지 않습니다.
- 콘텐츠 적재는 도서·콘텐츠 버전별 선수 관계를 `선수 페이지 -> 의존 페이지` 방향 그래프로 검증합니다.
  존재하지 않는 페이지·다른 도서나 콘텐츠 버전 참조, 자기 참조와 방향 순환이 하나라도 있으면 외부 호출과
  DB 변경 전에 전체 적재를 실패시킵니다.
- 목적 임베딩과 Responses API 호출은 한 번의 20초 전체 제한과 같은 외부 API 실패 처리 안에서 실행합니다.
- 런타임 Embeddings API에는 사용자 목적만, Responses API에는 목적과 검색된 후보 페이지 분석 텍스트만
  보내며 이메일, 예산·잉크·결제·권한과 세션 정보는 보내지 않습니다. 서버가 관리하는 고정 지시문과 구조화
  출력 스키마는 정규화한 목적의 별도 사용자 입력 블록과 분리하고, 목적 문자열을 시스템·개발자 지시문에
  이어 붙이지 않습니다.
- Responses API는 사용자별 비용을 모르는 상태에서 목적 관련도, 선수 관계와 읽기 순서를 반영한 후보 경로를
  반환합니다. 서버는 현재 대여·소장을 외부에 보내지 않고 검수된 선수 관계를 기준으로 후보 경로를
  순회합니다. 비소장 도서는 선수 페이지가 모두 포함되고 누적 추가 비용이 예산 안인 페이지만 선택하며,
  소장 도서는 같은 선수 조건에서 선택한 깊이의 페이지 수 상한까지만 포함합니다. 비용 때문에 선수를
  제외하면 그 선수에 의존하는 페이지도 제외하고, 상한을 채우려고 무관한 페이지를 추가하지 않습니다.
- 2차 MVP의 공개 AI 시연 콘텐츠에는 기본 악용 모니터링의 최대 30일과 비-ZDR 프롬프트 파생 캐시의 최대
  24시간 보관을 수용합니다. 실제 출판 콘텐츠는 외부 전송 권리를 명시적으로 확보하고 적용할 데이터 제어와
  파생 캐시 허용 조건을 함께 확인해야 합니다. 기본 제어는 최대 30일 악용 모니터링과 최대 24시간 파생
  캐시를 모두 허용할 때, Modified Abuse Monitoring은 악용 모니터링에서 고객 콘텐츠를 제외하되 최대
  24시간 파생 캐시를 허용할 때만 사용할 수 있습니다. 공급자 측 고객 콘텐츠 애플리케이션 상태 보관을
  허용하지 않는 콘텐츠는 Zero Data Retention 프로젝트에서만 지원합니다. 위에서 검토한 explicit
  no-breakpoint 방식은 공식 문서 표현이 일치하기 전까지 무보관 근거로 사용하지 않습니다.
- 콘텐츠 적재·평가·일반 생성은 같은 전용 OpenAI 프로젝트와 프로젝트 소속 서비스 계정 API 키를 사용합니다.
  배포 전 원격 상태를 갱신해 프로젝트 ID, 실효 데이터 제어와 그 제어에서 파생한 프롬프트 캐시 허용 정책을
  검증하고, 공식 관리 인터페이스에서 읽을 수 있는 안정 필드를 정규화한 SHA-256 `openAiPolicyHash`로
  만듭니다. 확인 시각과 서비스 계정·키 추적 ID는 배포 증거에 별도로 남기며 API 키 원문은 남기지 않습니다.
  원격 증명은 확인 시각부터 1시간만 유효하고 해시의 안정 필드에는 유효기간을 넣지 않습니다.
- 학습용 데이터 공유 비활성은 `openAiPolicyHash`에 넣지 않습니다. 조직 관리자가 OpenAI Platform의 조직
  데이터 제어 화면에서 전용 프로젝트가 학습용 공유 대상이 아님을 콘텐츠 적재·평가·공개 서버 시작과 API 키
  교체 전에 확인하고, 조직·프로젝트 ID, 확인 시각과 확인자를 비민감 `dataSharingDisabledEvidence`로
  남깁니다. 증거가 없거나 대상 프로젝트가 다르거나 공유가 켜져 있으면 해당 배포 단계와 외부 호출을
  중단합니다. 데이터 공유 설정 변경은 먼저 AI 경로를 비활성화한 뒤 검토된 관리 절차에서만 수행하고 새
  증거가 있기 전에는 다시 활성화하지 않습니다. 공식 기계 판독 인터페이스가 제공되면 새 결정으로 자동
  원격 증명 편입을 검토합니다.
- OpenAI 프로젝트 정책은 검토된 배포 경로에서만 변경합니다. 콘텐츠 적재, 평가, 공개 서버 시작과 API 키
  교체 직전에 Admin API 또는 원격 상태를 갱신하는 구성 관리 도구로 drift를 검사합니다. drift, 다른 프로젝트
  소속 키나 정책 불일치가 있으면 원격 정책 증명을 발급하지 않고 외부 API를 호출하지 않습니다. 구성 관리
  도구는
  [원격 상태 갱신과 drift 판정](https://developers.openai.com/api/docs/guides/terraform/project-controls#detect-changes-outside-terraform)을
  수행해야 합니다. 공개 서버에는 별도 비웹 정책 증명 작업이 1시간 안에 원격 증명을 갱신하며, 갱신 실패·
  drift·정확한 만료 시각부터 일반 생성은 실패 폐쇄됩니다. 관리 자격증명은 웹 애플리케이션에 제공하지
  않습니다.
- 외부 AI 출력은 페이지 번호, 정성적 관련도, 선수 개념 여부와 역할 열거값만 받습니다. 서버가 도서·페이지
  범위, 중복, 순서와 예산을 검증하며 모델이 만든 자유 문구는 저장하거나 사용자에게 제공하지 않습니다.
- AI 페이지 가이드는 사람 검수를 통과한 페이지별 공개 주제와 역할을 서버의 고정 템플릿에 넣어 만듭니다.
  비공개 분석 텍스트와 외부 AI 응답은 가이드 문구의 직접 입력으로 사용하지 않습니다.
- 도서·콘텐츠 버전별 AI 경로 상태를 `UNSUPPORTED`, `EVALUATABLE`, `PUBLIC`으로 영속화합니다. 공개 후보
  DB를 복제한 접근 제한 평가 DB에서만 비웹 평가를 실행하고, 두 DB의 콘텐츠·스키마 지문을
  `evaluationSourceHash`로 대조합니다. 평가 데이터가 든 DB는 공개하지 않습니다. 콘텐츠·평가 데이터·품질
  수치와 공개 전환 순서는 각각 [AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)와
  [AI 잉크 경로 PRD](../../prd/ai-ink-route.md)의 정본을 따릅니다.
- 비웹 평가는 공개 배포 대상 JAR 자체로 운영 후보 검색·경로 구성·서버 검증을 실행합니다. 정제 평가 증거는
  평가 계약 파일의 `evaluationGitRevision`, `evaluationSourceHash`, `generationArtifactHash`, JAR 바이트를
  포함한 `generationConfigHash`와 `openAiPolicyHash`를 기록합니다. 공개 전환은 이 리비전과 네 해시를 각각
  다시 검증하고, 공개 서버에는 평가한 JAR 바이트를 다시 빌드하지 않고 그대로 배포합니다.
- 콘텐츠 적재는 외부 호출 전에 현재 `openAiPolicyHash`와 유효한 원격 증명이 콘텐츠 요구 조건에 일치하는지
  확인합니다. 평가는 두 해시를 고정해 증거에 남깁니다. 일반 생성은 현재 두 해시가 공개 승인값과 일치하고
  원격 증명이 유효한지 확인하며, `PUBLIC`이어도 하나가 없거나 다르거나 증명이 만료됐으면 실패 폐쇄하고
  OpenAI를 호출하지 않습니다.
- 같은 프로젝트 ID와 `generationConfigHash`를 유지한 채 실효 데이터 제어 또는 캐시 정책만 바꾸면 현재
  `openAiPolicyHash`와 공개 승인값의 불일치로 일반 생성을 먼저 실패 폐쇄합니다. 별도 비웹 정책 재승인
  작업은 새 정책의 유효한 원격 증명과 `dataSharingDisabledEvidence`를 확인하고 모든 `PUBLIC` 콘텐츠의
  외부 전송 권리·보관 조건을 새 정책에 다시 검증합니다. 전체가 통과하고 현재 `generationConfigHash`가
  기존 공개 승인값과 같은 경우에만 한 DB 트랜잭션에서 승인 `openAiPolicyHash`를 새 값으로 교체하고 이전·
  새 해시, 변경 이유와 증거 식별자를 배포 증거에 남깁니다. 하나라도 실패하면 승인값과 `PUBLIC` 상태를
  바꾸지 않고 실패 폐쇄를 유지합니다.
- 생성 설정·JAR 바이트 변경이나 OpenAI 프로젝트 ID 변경은 정책만 재승인하는 절차를 사용할 수 없습니다.
  앞의 두 변경은 코퍼스 재평가와 새 공개 승인을, 프로젝트 변경은 새 프로젝트의 콘텐츠 적재까지 요구합니다.
  같은 프로젝트의 서비스 계정 API 키 교체는 프로젝트 ID와 두 해시가 같으면 새 원격 증명과 데이터 공유
  비활성 확인만 요구합니다.
- 계정·멱등 키별 생성 상태, 정상 결과 슬롯과 외부 실행 시도 슬롯은 MySQL에 보관합니다. 정확한 보존 기간과
  횟수는 [AI 잉크 경로 PRD](../../prd/ai-ink-route.md)의 제품 정책을 따릅니다. 각 실행에는 단조 증가하는
  `attemptVersion`을 부여하고 상태와 버전이 모두 일치할 때만 결과 전이를 허용합니다. 중단 예약을 복구한 뒤
  도착한 이전 버전의 성공·실패는 멱등 상태, 경로와 슬롯을 변경하지 못합니다. 실패 재실행은 정상 결과 슬롯을
  다시 예약한 뒤 새 버전으로 시작합니다.
- 멱등 입력 비교값은 배포 비밀키와 키 버전을 사용한 HMAC-SHA-256으로 만듭니다. 정규화와 길이 접두 필드
  직렬화는 [AI 잉크 경로 PRD의 저장과 생명주기](../../prd/ai-ink-route.md#저장과-생명주기)를 따르고, 키
  버전을 멱등 상태와 함께 저장합니다. 원문을 제거한 뒤에도 이 값을 일반 SHA-256 대용으로 사용하지 않으며,
  멱등 상태와 함께 삭제합니다. 키 교체 시 참조 중인 멱등 상태가 모두 삭제될 때까지 이전 키를 보존합니다.
- 검증된 임시 경로는 서버에 보관하고 클라이언트에는 불투명한 생성 ID만 제공합니다. 임시 결과의 조회·저장과
  저장 경로의 목록·상세·현재 지정·삭제·진행·피드백은 인증 소유자로 제한하고 같은 독자·도서의 변경을
  직렬화합니다. 정확한 상태 전이는 PRD를 따릅니다.
- 모델·설정·프롬프트·스키마가 그대로여도 JAR을 바꾸면 `generationConfigHash`가 달라집니다. 변경된 JAR은
  정답 코퍼스 회귀 평가와 공개 승인을 다시 통과해야 합니다.

## 결과

- 새 벡터 검색 인프라 없이 기존 Spring Boot·MySQL 배포 경계를 유지합니다.
- 한 권 단위의 작은 후보군에서는 정확 검색으로 충분하며 구현과 장애 처리가 단순합니다.
- 외부 AI 비용·지연·가용성과 OpenAI 데이터 처리 조건에 의존합니다. Modified Abuse Monitoring만으로는
  비-ZDR 프롬프트 파생 캐시를 제거하지 못하므로 이를 허용하지 않는 실제 콘텐츠는 Zero Data Retention
  프로젝트 없이는 지원할 수 없습니다.
- GPT-5.6의 explicit no-breakpoint 캐시 비활성화 가능성을 당장 사용하지 않아 지원 범위는 좁지만, 공식
  데이터 보관 계약의 해석 차이가 고객 콘텐츠 권리 경계로 전파되지 않습니다.
- 서버 템플릿 가이드는 자유 생성 문구보다 표현력이 제한되지만 원문·결론의 선노출을 구조적으로 막습니다.
- 멱등 요청 상태, 임시 결과와 두 종류의 생성 슬롯을 MySQL에 보관하므로 UTC 날짜가 지난 상태와 만료 결과
  정리, 중단된 정상 결과 예약 복구가 필요합니다.
- 공개 후보 DB를 복제한 평가 DB와 `evaluationSourceHash` 검증이 필요하지만, 공개 후보 DB에는 평가용 금융·
  권한 기록과 런타임 상태가 생기지 않으며 잉크 원장 불변식에 삭제 예외를 만들지 않습니다. 평가 DB는 정제
  증거 보존 뒤 환경 전체를 폐기하므로 애플리케이션에 원장 삭제 경로를 추가하지 않습니다.
- `evaluationGitRevision`은 정답 데이터·평가 규칙·품질 임계값을, `generationConfigHash`는 평가한 전체
  실행 JAR을 결합합니다. 저장소의 무관한 변경은 평가한 JAR을 그대로 배포할 때만 기존 승인을 유지하며,
  변경 뒤 JAR을 다시 빌드하면 기능 관련성에 관계없이 재평가가 필요합니다.
- 공개 승인값과 런타임의 실행 JAR·생성 설정·OpenAI 프로젝트 정책이 다르면 AI 경로가 실패 폐쇄되므로
  미평가 코드·설정과 미승인 보관 정책으로 외부 호출하는 것을 막습니다. 대신 배포와 키 교체마다 아티팩트
  대조, 원격 drift 검사와 증거 갱신이 필요합니다.
- 같은 프로젝트의 정책만 바뀌면 모든 공개 콘텐츠의 허용 조건을 다시 검증한 원자적 정책 재승인으로 품질
  평가를 반복하지 않고 복구할 수 있습니다. 프로젝트 자체를 바꾸면 콘텐츠 적재와 품질 평가를 다시 수행해야
  합니다.
- 학습용 데이터 공유 참여 상태는 공식 기계 판독 관리 인터페이스가 없어 런타임의 1시간 원격 증명에 포함하지
  못합니다. 별도 조직 관리자 증거와 변경 전 AI 비활성화 절차가 필요하며, 이 수동 운영 경계는 배포 증거에
  명시적으로 남습니다.
- MySQL은 범용 벡터 검색 기능을 맡지 않으므로 여러 책을 가로지르거나 페이지 수가 크게 늘면 애플리케이션
  메모리와 계산 비용을 다시 측정해야 합니다.
- 공급자·임베딩 모델 변경에는 연동 코드 전환, 전체 임베딩 재생성, 저장 데이터 마이그레이션과 품질 회귀
  검증이 필요합니다.
- 실제 측정에서 병목이 확인되면 별도 벡터 검색 인프라를 새 기술 결정으로 검토합니다.

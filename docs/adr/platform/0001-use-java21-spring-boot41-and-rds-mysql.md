# 0001. Java 21과 Spring Boot 4.1, Amazon RDS for MySQL을 사용한다

- 상태: 승인됨
- 날짜: 2026-07-22

## 맥락

핵심 도메인은 잉크 잔액·내역, 페이지 대여와 도서 소장을 하나의 트랜잭션으로 일관되게 처리해야 하며,
중복·동시 요청에서도 불변식을 지키려면 관계형 데이터베이스의 잠금과 고유 제약이 필요합니다.
읽어볼까는 기존 시스템과의 런타임 호환 부담이 없는 단일 Spring Boot MVP이고 운영 실행 환경은 아직
결정되지 않았으므로, 최신 기능 자체보다 검증된 생태계와 배포 선택 폭을 우선합니다. Spring Boot 4.1은
[Java 17부터 26까지 지원](https://docs.spring.io/spring-boot/4.1.0/system-requirements.html)하므로 Java LTS와
Spring Boot 안정 계열을 비교하고, 운영 데이터베이스의 백업·패치·장애 복구는 관리형 서비스에 맡깁니다.

## 고려한 대안

- Java 17 — Spring Boot 4.1의 최소 버전이고 지원 가능한 런타임 범위가 넓지만, 이전 런타임과의 호환
  요구가 없는 신규 프로젝트를 더 오래된 LTS 기준에 묶으며 Java 21에서 정식화된 가상 스레드, record
  pattern과 pattern matching `switch` 등을 사용할 수 없어 제외합니다.
- Java 25 — 최신 LTS라 지원 여유와 새 런타임 기능이 가장 크지만, 현재 요구사항에는 Java 25 전용 기능이
  없고 언어·바이트코드 기준을 25로 올리면 운영 런타임도 25 이상으로 제한됩니다. 기존 Java 21 기준의
  IDE·CI·annotation processor·애플리케이션 실행을 다시 검증할 제품상 이익이 없어 제외합니다.
- Spring Boot 3.5.x — 마지막 3.x 계열로 생태계가 성숙하고 장기 상용 지원을 선택할 수 있지만, 기존 3.x
  호환 요구가 없는 프로젝트를 Spring Framework 6 기반에서 시작해 이후 4.x 메이저 전환 비용을 만들므로
  제외합니다.
- Spring Boot 4.0.x — 패치가 누적된 이전 4.x 계열이지만, 결정 시점의 4.1.0은
  [4.0.7까지의 버그·문서·보안 수정을 포함](https://spring.io/blog/2026/06/10/spring-boot-4/)하고 더 긴
  지원 기간을 제공합니다. 4.0에 남아야 할 호환 제약이 없어 제외합니다.
- EC2 자체 관리 MySQL — 비용을 세밀하게 조절할 수 있지만 백업·패치·모니터링 책임이 커 제외합니다.
- Amazon Aurora MySQL-Compatible — 확장성과 고가용성은 강하지만 초기 MVP 규모와 비용에 비해 과해 제외합니다.
- PostgreSQL — 현재 MVP가 요구하는 트랜잭션, 행 잠금과 관계형 제약을 구현할 수 있어 MySQL과 비교해
  제품 요구사항을 좌우할 만큼 큰 기능 차이는 없습니다. 프로젝트에 익숙한 MySQL 대신 PostgreSQL을
  선택해 얻는 이익이 학습, 스키마·SQL 조정, 동시성·운영 검증 비용을 정당화하지 못해 제외합니다.
- 인메모리 데이터베이스 — MySQL의 잠금·인덱스·제약·SQL 차이를 검증할 수 없어 최종 통합 검증 수단에서 제외합니다.

## 결정

- Java 언어·바이트코드, Gradle toolchain과 개발·CI·운영 실행의 검증 기준은 Java 21로 통일합니다.
- Spring Boot 4.1 계열을 사용하고 최초 구현 버전은 4.1.0으로 시작합니다. 4.1 계열의 정식 패치 릴리스는
  회귀 테스트 후 반영하며 패치 갱신만으로 이 ADR을 변경하지 않습니다.
- 데이터베이스 엔진은 현재 요구사항 충족 여부뿐 아니라 프로젝트의 기존 경험과 전환·검증 비용을 함께
  고려해 MySQL 8.x를 사용하고, 운영 데이터베이스는 Amazon RDS for MySQL을 사용합니다.
- 로컬 개발과 통합 테스트도 MySQL 8.x를 사용합니다.
- 연결은 Spring Boot가 관리하는 MySQL Connector/J와 HikariCP를 사용합니다.
- 문자 집합은 `utf8mb4`, 애플리케이션과 데이터베이스의 기준 시간대는 UTC로 통일합니다.
- RDS는 비공개 네트워크에 두고 TLS, 저장 데이터 암호화와 자동 백업을 적용합니다.
- 스키마 변경 방식은
  [ADR-0005](./0005-manage-schema-with-flyway-not-ddl-auto.md)을 따릅니다.

## 결과

- 운영과 가까운 데이터베이스 동작을 로컬·통합 테스트에서 검증할 수 있습니다.
- 익숙한 MySQL을 유지해 새 데이터베이스 엔진의 학습과 스키마·SQL·운영 재검증 비용을 줄이는 대신,
  PostgreSQL을 도입하며 얻을 수 있는 기능과 경험은 포기합니다. PostgreSQL이 필요한 구체적인 요구사항이나
  MySQL의 한계가 확인되면 전환 비용과 함께 데이터베이스 엔진을 다시 비교합니다.
- Java 17보다 현대적인 언어·런타임 기능과 충분히 축적된 Java 21 생태계를 사용하면서, Java 25 전용
  기능과 더 긴 지원 여유는 포기합니다. 운영 플랫폼이 Java 25를 표준으로 채택하거나 25 전용 기능이
  필요해지면 전환을 다시 검토합니다.
- Spring Boot 4.1이 관리하는 Spring Framework 7과 관련 라이브러리를 기준으로 호환성을 확인하고,
  [Spring 지원 정책](https://spring.io/support-policy)에 따라 지원되는 4.1 패치를 유지해야 합니다.
- RDS 비용과 연결 수 제한이 생기며 실제 부하에 맞춰 HikariCP 풀을 조정해야 합니다.
- Java 기준 버전, Spring Boot 메이저·마이너 또는 데이터베이스 엔진을 바꾸면 annotation processing,
  전체 테스트, 패키징과 실제 애플리케이션·MySQL 실행을 다시 검증해야 합니다.

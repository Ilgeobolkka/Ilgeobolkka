# 0005. 스키마 변경은 Flyway로만 관리하고 Hibernate는 검증만 한다

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

로컬과 운영이 같은 스키마 이력을 사용해야 하며, JPA Entity 변경이 운영 데이터베이스를 예측하지 못한
방식으로 바꾸면 안 됩니다. 동시에 Entity와 실제 스키마의 불일치는 애플리케이션 시작 단계에서 발견할
안전망이 필요합니다.

## 고려한 대안

- `ddl-auto=update` — 초기 개발은 빠르지만 운영 스키마 변경이 리뷰 가능한 이력에서 벗어나 제외합니다.
- `ddl-auto=create` 또는 `create-drop` — 테스트 격리에는 유용하지만 데이터를 잃고 운영과 달라 제외합니다.
- Flyway와 `ddl-auto=update` 병행 — 두 도구가 모두 스키마를 변경해 실제 상태가 어긋날 수 있어 제외합니다.
- Flyway와 `ddl-auto=none` — 자동 변경은 막지만 Entity와 스키마 불일치를 시작 시점에 찾지 못해 제외합니다.
- Flyway와 `ddl-auto=validate` — 변경 주체와 검증 주체를 분리할 수 있어 선택합니다.

## 결정

- Flyway를 스키마 변경의 유일한 수단으로 사용합니다.
- 테이블·컬럼·인덱스·제약 변경은 버전 마이그레이션 파일로 남깁니다.
- 공유·시연·운영 데이터베이스에 적용한 마이그레이션은 수정하지 않고 새 마이그레이션으로 보정합니다.
- 도메인 구현과 공유 데이터 생성 전에는 보존할 데이터가 없음을 확인한 경우에만 초기 기준선을 한 번에
  재작성할 수 있습니다. 이때 로컬 개발·테스트 스키마와 migration 테스트도 같은 변경에서 다시 만듭니다.
- `spring.jpa.hibernate.ddl-auto`는 로컬과 운영 모두 `validate`로 유지합니다.
- 테스트 전용 Entity처럼 Flyway 관리 대상이 아닌 픽스처에만 검증 비활성화를 제한적으로 허용합니다.
- 환경별 연결 방식은 [배포 가이드](../../deployment.md), 목표 모델은 [ERD](../../erd.md)를 따릅니다.

## 결과

- 모든 운영 스키마 변경이 리뷰 가능한 파일로 남습니다.
- Entity와 스키마가 어긋나면 애플리케이션 시작이 실패해 누락을 빠르게 발견합니다.
- Entity 변경에는 대응 마이그레이션이 항상 필요합니다.
- 마이그레이션 체계 전환은 전체 배포·롤백 절차와 기존 데이터 검증을 요구합니다.

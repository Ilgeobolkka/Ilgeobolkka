# 0012. PortOne V2 테스트 채널로 결제 경계를 통합한다

- 상태: 승인됨
- 날짜: 2026-07-26

## 맥락

MVP는 페이지 이용권과 온라인 소장이라는 두 원화 결제를 검증해야 합니다. 브라우저의 성공 응답만으로
잉크나 소장 권한을 부여하면 응답 조작, 네트워크 단절과 중복 요청에 취약하므로 서버 재조회와 웹훅을
포함한 하나의 결제 경계가 필요합니다.

학습 범위는 실제 결제 연동 흐름이지만 운영 실결제를 열 계획은 없습니다. 하위 PG사의 전용 기능에
애플리케이션을 결합하지 않고 테스트 채널에서 준비, 결제창, 서버 검증, 웹훅과 멱등 완료를 검증해야
합니다. 다른 결제 제공자로 되돌리면 브라우저 SDK, 서버 Client, 웹훅 검증과 결제 상태 처리 전체를
바꿔야 하므로 ADR로 기록합니다.

## 고려한 대안

- 로컬 가짜 결제 시뮬레이터 — 빠르지만 실제 SDK·서버 조회·웹훅 경계를 학습하고 검증할 수 없어 제외합니다.
- 하위 PG사 API 직접 연동 — 제공자 고유 기능은 쓰기 쉽지만 PG 변경 시 애플리케이션 결합 범위가 커 제외합니다.
- PortOne V1 — 기존 예제는 많지만 새 연동 계약을 V2로 통일하기 위해 제외합니다.
- PortOne V2 테스트 채널 — 공통 결제 API와 실제 검증 흐름을 운영 실결제 없이 확인할 수 있어 선택합니다.

## 결정

- 페이지 이용권과 온라인 소장 결제의 외부 연동은 PortOne V2 테스트 채널만 사용합니다.
- 하위 PG는 코드에 고정하지 않고 환경별 채널 설정으로 선택하며 공통 결제 필드만 사용합니다.
- 브라우저는 별도 Node.js 빌드 없이 PortOne V2 공식 ESM CDN 모듈을 불러옵니다.
- 서버 구현을 시작할 때 공식 JVM SDK를 의존성으로 추가해 결제 재조회와 웹훅 서명 검증에 사용합니다.
- 브라우저 완료 요청과 서명 검증된 웹훅은 같은 멱등 완료 유스케이스로 수렴하며 도착 순서를 가정하지
  않습니다.
- 서버가 PortOne에서 결제 상태·식별자·금액·통화를 다시 확인하기 전에는 잉크나 온라인 소장을
  부여하지 않습니다.
- `Transaction.Paid`는 서버 재조회로 검증한 첫 성공만 `PAID`와 도메인 효과를 함께 기록합니다.
  `Transaction.Failed`는 재조회로 최종 실패를 확인한 경우만 `FAILED`로 기록합니다.
- 금액·통화·식별자 불일치는 `FAILED`로 기록하지만, 조회 일시 장애와 미완료 상태는 `PENDING`을
  유지합니다.
- 서명 누락·불일치 웹훅은 `400`, 정상 서명의 지원하지 않는 이벤트는 상태를 바꾸지 않고 `200`,
  재시도 가능한 PortOne·내부 일시 오류는 `5xx`로 응답합니다.
- 운영 실결제 채널과 취소·환불·분쟁 처리는 MVP 범위에서 비활성화합니다.

## 결과

- 실제 결제 SDK, 서버 검증, 웹훅과 중복 이벤트 처리까지 테스트 채널에서 검증할 수 있습니다.
- 잉크 이용권과 소장 결제는 도메인 API와 기록을 분리하면서 PortOne 연동 코드만 공유할 수 있습니다.
- 결제 화면은 PortOne CDN 가용성에 의존하므로 CDN 실패 시 결제 기능만 오류 안내와 함께 중단해야 합니다.
- 콘텐츠 보안 정책에서 PortOne CDN 연결을 허용해야 하며 결제 secret은 서버 환경에만 보관해야 합니다.
- 운영 실결제를 열려면 운영 채널, 취소·환불·분쟁, 모니터링과 운영 보안 검토를 별도로 완료해야 합니다.
- 공급자를 바꾸려면 브라우저 SDK, 서버 Client, 웹훅 검증과 결제 상태 통합 테스트를 교체해야 합니다.

# 0007. 서버 세션으로 웹 인증 상태를 관리한다

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

MVP는 이메일·비밀번호 로그인을 사용하는 same-origin 데스크톱 웹이며 모바일·네이티브 앱, 외부 API 소비자와
독립 마이크로서비스 인증은 범위에 없습니다. 로그아웃 즉시 서버에서 인증을 무효화해야 하며 도메인의
현재 열람 세션과 로그인 인증 상태를 분리해야 합니다.

페이지 접근 권한은 로그인 여부만으로 결정되지 않습니다. 현재 뷰어가 교체됐는지, 요청 페이지가 현재
열람 위치인지, 도서를 온라인 소장했거나 페이지 대여가 유효한지를 요청 시점에 함께 확인해야 합니다.
이 상태는 대여 만료·소장 결제·새 뷰어 생성으로 바뀌므로 인증 수단에 넣은 오래된 권한 정보가 아니라
서버의 현재 상태를 기준으로 판단해야 합니다.

선택 기준은 현재 클라이언트·배포 구조와 권한 변경 반영, 즉시 무효화, 브라우저 보관 위험, 구현·운영
복잡도입니다. 화면 캡처처럼 브라우저에 표시된 콘텐츠의 복제를 막는 것은 세션과 JWT 어느 쪽도 해결하지
못하므로 인증 방식의 선택 기준으로 삼지 않습니다.

## 고려한 대안

- 서버 세션과 불투명한 세션 ID 쿠키 — Spring Security 웹 인증을 활용하고 즉시 무효화할 수 있어 선택합니다.
- access·refresh token JWT — 네이티브 앱·외부 API·독립 서비스에는 유리하지만 현재는 권한을 매 요청 다시
  조회해야 하고 갱신·회전·폐기·서명 키 관리가 추가되어 제외합니다.
- JWT를 `HttpOnly` 쿠키로 전달 — JavaScript의 토큰 직접 접근은 막지만 CSRF 방어가 필요하고 즉시
  무효화하려면 서버 상태가 다시 필요해 서버 세션보다 단순하지 않아 제외합니다.
- JWT를 브라우저 Web Storage에 보관 — 쿠키의 자동 전송은 피하지만 JavaScript가 읽을 수 있어 XSS로
  토큰을 탈취당할 수 있고 refresh token 수명 관리도 필요해 제외합니다.

## 결정

- Spring Security와 서블릿 `HttpSession`으로 인증 상태를 서버에서 관리합니다.
- 브라우저에는 인증 세션을 찾는 불투명한 ID만 쿠키로 전달합니다.
- 로그인 성공 시 세션 ID를 교체하고 로그아웃 시 서버 세션과 쿠키를 무효화합니다.
- 쿠키는 `HttpOnly`, 운영 HTTPS에서는 `Secure`, same-origin 배포에서는 `SameSite=Lax`를 사용합니다.
- Spring Security의 CSRF 보호를 유지합니다.
- 인증 독자는 `Principal`에서 식별하고 요청의 사용자 ID를 인증 근거로 사용하지 않습니다.
- `HttpSession`은 로그인한 독자를 식별하고, 도메인 `ReadingSession`은 독자당 현재 뷰어와 페이지를
  식별합니다. `ReadingSession.viewerSessionId`는 인증 자격 증명이 아니며 단독으로 접근을 허용하지 않습니다.
- 서버는 새 뷰어마다 UUID `viewerSessionId`를 발급하고 브라우저는 탭별 `sessionStorage`에 보관해
  `X-Viewer-Session-Id` 헤더로 전달합니다.
- 페이지 콘텐츠 요청마다 `Principal`의 독자, 그 독자의 현재 `ReadingSession`, 뷰어 세션 ID와 현재 페이지,
  온라인 소장 또는 활성 대여를 함께 검증합니다. 권한 정보를 `HttpSession`이나 JWT에 저장해 현재 DB
  상태 확인을 대신하지 않습니다.
- 인증 세션이 만료되면 `ReadingSession` 행이 남아 있더라도 모든 보호된 뷰어 요청을 거부합니다. 새 뷰어를
  열 때 `viewerSessionId`를 교체하고, 로그아웃할 때 인증 세션과 현재 `ReadingSession`을 함께 무효화합니다.
- 로그인 세션 ID와 `ReadingSession.viewerSessionId`는 URL·로그·오류 응답에 남기지 않습니다.
- 비밀번호와 세션 수명 세부는
  [ADR-0009](./0009-complete-password-and-session-security.md)을 따릅니다.

## 결과

- 인증 유지와 즉시 로그아웃을 별도 토큰 폐기 목록 없이 구현할 수 있습니다.
- 대여 만료·온라인 소장·현재 뷰어 교체가 다음 콘텐츠 요청의 인가에 즉시 반영됩니다.
- 인증 방식과 뷰어 상태를 분리해 로그인 기기 수 정책과 독자당 현재 뷰어 하나 정책을 독립적으로 변경할
  수 있습니다.
- 쿠키가 자동 전송되므로 모든 상태 변경 요청에서 CSRF 검증을 유지해야 합니다.
- 인메모리 세션을 사용하는 동안 애플리케이션 재시작 시 다시 로그인해야 합니다.
- 다중 인스턴스에서는 우선 Spring Session JDBC나 Redis 같은 공유 저장소를 사용합니다. 인스턴스 수가
  늘어나는 사실만으로 JWT로 전환하지 않습니다.
- 네이티브 앱·외부 API 소비자·독립 인증 서버와 여러 리소스 서버가 실제 범위에 들어오면 OAuth 2.0·OIDC
  기반 access token을 다시 검토합니다.
- 서버가 인가한 콘텐츠도 사용자 브라우저에 표시된 뒤의 캡처·복제까지 막지는 못합니다. 원본 저장소를
  비공개로 두고 현재 한 페이지의 권한을 매 요청 검증하는 콘텐츠 전달 경계가 별도로 필요합니다.

# 0009. 적응형 비밀번호 해시와 CSRF 보호를 사용한다

- 상태: 승인됨
- 날짜: 2026-07-23

## 맥락

서버 세션 인증을 구현하려면 비밀번호 저장 방식, 세션 고정 공격 방지, CSRF 전달과 인증 오류 노출
경계를 함께 정해야 합니다. 비밀번호 저장 형식은 계정 데이터가 쌓인 뒤 바꾸려면 재해시 전략이 필요하고,
쿠키 기반 인증의 CSRF 방식을 바꾸면 모든 상태 변경 화면과 API가 영향을 받습니다.

## 고려한 대안

- 평문 또는 빠른 단방향 해시 — 유출 시 대입 공격에 취약해 제외합니다.
- Argon2 전용 인코더 — 메모리 기반 방어에 유리하지만 현재 MVP에 추가 암호화 의존성이 필요해 제외합니다.
- Remember Me — 장기 자격 증명 수명과 탈취 대응이 추가되어 제외합니다.
- 로그인 오류에서 이메일 존재 여부를 구분 — 계정 탐색을 허용해 제외합니다.

## 결정

- Spring Security `DelegatingPasswordEncoder`를 사용하고 신규 비밀번호는 BCrypt 형식으로 저장합니다.
- 비밀번호 원문은 정규화하거나 자르지 않으며 DB, 로그, 이벤트와 오류 응답에 남기지 않습니다.
- 로그인 성공 시 세션 ID를 교체하고 비활성 세션 만료를 적용합니다.
- 로그아웃 시 로그인 세션과 도메인 `ReadingSession`을 함께 무효화합니다.
- 회원가입은 독자와 0잉크 계좌만 만들고 로그인 세션을 만들지 않으며, 사용자는 별도로 로그인합니다.
- 회원가입·로그인·로그아웃을 포함한 상태 변경 요청에 CSRF 보호를 적용합니다.
- Thymeleaf 폼은 hidden field, JavaScript `fetch`는 페이지의 `_csrf`, `_csrf_header` meta 태그에서 읽은
  토큰을 해당 헤더로 전송합니다. 로그인·로그아웃 뒤에는 새 페이지를 렌더링하며 별도 CSRF 토큰 API는
  만들지 않습니다.
- 로그인 실패는 이메일 존재 여부와 관계없이 같은 공개 오류로 응답합니다.
- 현재 입력값·만료 시간·오류 코드의 정본은 [제품 정책](../../prd/product-policy.md)과
  [API 계약](../../api-spec.md)입니다.

## 결과

- 비밀번호 원문과 계정 존재 여부 노출을 줄이고 쿠키 기반 요청을 CSRF로부터 보호합니다.
- 해시 비용이나 알고리즘을 바꿀 때 기존 비밀번호의 점진적 재해시 전략이 필요합니다.
- 로그인 제한과 계정 잠금은 별도 운영 보안 결정이 필요합니다.
- 모든 상태 변경 화면과 API가 CSRF 토큰 전달 규칙을 지켜야 합니다.

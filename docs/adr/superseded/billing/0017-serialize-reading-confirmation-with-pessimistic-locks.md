# 0017. 열람 확정은 비관적 잠금으로 직렬화한다

- 상태: 대체됨 (→ 0022)
- 날짜: 2026-07-24

## 맥락

열람 확정과 동시에 페이지 이동이나 새 세션 생성 요청이 도착하면, 검증 직후 세션이 바뀌어 이전 페이지를 잘못 확정할 수 있습니다.
같은 페이지의 중복 확정과 서로 다른 페이지의 동시 차감에서도 최초 1회 차감, 음수 잔액 금지와 원자성을 함께 지켜야 합니다.
데이터 모델과 고유 제약은 [`ADR-0007`](../data/0007-define-core-domain-erd.md), 외부 응답 계약은 [`API 명세`](../../../api/api-contract.md)를 따릅니다.
이 결정은 승인된 ADR-0008에서 분리했으며, 이 ADR은 동시성 제어 전략만 결정합니다.

## 고려한 대안

- 애플리케이션 선조회와 고유 제약 예외 처리 — 잠금 코드는 줄지만 JPA 영속성 예외가 발생한 트랜잭션을 성공 응답으로 복구하기 어렵고, 세션이 검증 뒤 교체되는 경합은 해결하지 못합니다.
- `@Version` 낙관적 잠금 — 충돌이 적을 때 대기 시간을 줄일 수 있지만 세션과 포인트 계정의 충돌 감지·재시도 정책을 각각 설계해야 하고,
  사용자가 결과를 기다리는 짧은 차감 트랜잭션에는 복잡도가 더 큽니다.
- 포인트 계정만 비관적 잠금 — 동시 차감으로 인한 음수 잔액은 막지만 페이지 이동·세션 교체와 확정 검증 사이의 경합은 막지 못합니다.
- 세션과 포인트 계정을 고정된 순서로 비관적 잠금 — 같은 독자의 상태 변경을 기다리게 하지만 세션 검증과 잔액 갱신을 한 트랜잭션 안에서 직렬화할 수 있습니다.

## 결정

### 선택한 기술

Spring Data JPA의 `@Lock(PESSIMISTIC_WRITE)` 또는 동등한 잠금 쿼리와 MySQL InnoDB의 `SELECT ... FOR UPDATE`를 사용합니다.
열람 확정 트랜잭션은 항상 `ReadingSession`을 먼저 잠그고 현재 세션·도서·페이지·6초 경과를 검증합니다.
신규 확정이면 `PointAccount`를 잠근 뒤 `ConfirmedPage`를 전체 유니크 키로 잠금 읽기해 다시 확인하고,
아직 확정되지 않았을 때만 차감·내역·열람 확정·마지막 위치를 같은 트랜잭션에서 반영합니다.

### 핵심 근거

- **세션 경합 — 세션 잠금 vs 계정 잠금만 사용**: 페이지 이동과 새 세션 생성도 같은 `ReadingSession` 행을 변경합니다.
  확정 요청이 이 행을 먼저 잠그면 검증부터 커밋까지 세션 교체가 기다리므로, 계정만 잠그는 대안이 남기는 이전 페이지·이전 토큰 경합을 닫을 수 있습니다.
- **잔액 경합 — 계정 잠금 vs 낙관적 재시도**: 같은 독자의 서로 다른 페이지 확정도 하나의 `PointAccount` 잔액을 변경합니다.
  짧은 MVP 트랜잭션에서는 행 잠금 뒤 잔액을 다시 확인하는 방식이 버전 충돌을 응답과 재시도로 바꾸는 낙관적 잠금보다 흐름이 단순합니다.
- **중복 확인 — 잠금 읽기 vs 일반 재조회**: [MySQL InnoDB의 기본 `REPEATABLE READ`](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)에서 일반 조회는 같은 스냅샷을 계속 볼 수 있습니다.
  최신 커밋 상태가 필요한 재확인은 [MySQL 잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)를 사용하고, 고유 제약은 예상하지 못한 경로까지 막는 최종 안전망으로 둡니다.
- **예외 복구 — 사전 직렬화 vs 고유 제약 예외 처리**: [Jakarta Persistence의 `PersistenceException`](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/persistenceexception)은
  일부 예외를 제외하고 참여 중인 트랜잭션을 롤백 대상으로 표시합니다.
  따라서 같은 트랜잭션에서 고유 제약 예외를 잡아 정상 성공으로 바꾸는 흐름을 주된 전략으로 사용하지 않습니다.
- **교착·시간 초과 — 고정 순서와 전체 롤백 정책**: 모든 경로가 세션 → 계정 순서로 잠그면 서로 반대 순서로 기다리는 가능성을 낮출 수 있지만 교착을 제거하지는 못합니다.
  InnoDB는 교착 시 트랜잭션 전체를 롤백하지만 잠금 대기 시간 초과는 기본적으로 현재 SQL 문만 롤백할 수 있습니다.([MySQL 오류 처리](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html))
  두 예외 모두 잡아서 정상 흐름을 계속하지 않고 트랜잭션 경계 밖으로 전파해 [Spring의 롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html)으로 전체 작업을 롤백한 뒤 명시적 재시도를 허용합니다.

## 결과

- 같은 독자의 열람 확정·페이지 이동·세션 교체·포인트 차감은 필요한 행 잠금에서 대기할 수 있습니다.
- 이미 확정된 페이지는 세션 검증 뒤 차감 없이 반환해 포인트 계정 잠금을 얻지 않습니다.
- 잠금 순서를 고정해도 교착과 시간 초과 가능성은 남습니다. 관련 예외를 트랜잭션 밖으로 전파해 부분 성공 없이 전체 롤백하고 클라이언트의 명시적 재시도 계약을 유지합니다.
- 구현 완료 전 MySQL 통합 테스트로 같은 요청 반복, 서로 다른 페이지 동시 확정, 페이지 이동과 확정의 경합, 이전 세션 지연 요청, 잠금 대기 시간 초과 뒤 부분 반영이 없는지를 검증합니다.
- 잠금 쿼리가 실제로 `FOR UPDATE`를 생성하고 전체 유니크 인덱스를 사용하는지 확인하며,
  일반 조회 이후 다른 트랜잭션이 커밋한 확정 행을 두 번째 잠금 읽기가 확인하는 시나리오를 검증합니다.
- ADR-0007의 데이터 모델·고유 제약 결정은 유지하며, 열람 확정 처리 순서와 잠금 방식은 이 ADR을 최신 정본으로 사용합니다.

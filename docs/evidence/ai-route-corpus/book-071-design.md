# book-071 「요청과 응답: 서버 처리의 구조」 설계·검수 근거

SCRUM-485 90권 확장 중 기술 카테고리 첫 번째 도서입니다. 현재 다른 도서 작업과 공유
`manifest.json`·`evaluation.json`에서 충돌하지 않도록 단일 도서 fragment로 작성했습니다.

## 대상 도서

| 필드 | 값 | 처리 |
| --- | --- | --- |
| `bookId` | 71 | 유지 |
| `category` | 기술 | 유지 |
| `title` | 요청과 응답: 서버 처리의 구조 | 카테고리 톤에 맞게 갱신 |
| `author` | 가상 작가 071 | 유지 |
| `description` | 가상 서비스 요청이 처리되는 과정을 설명하는 기술서입니다. | 유지 |
| `totalPageCount` | 5 → **50** | 재제작 |

저자·카테고리·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지했습니다. 제목은 기술
카테고리 제목 갱신에 따른 새 값이며 정본은 `ai-route-v2` manifest의 `books[].title`입니다.
`books.json`은 `initial-v1` 동결 fixture이므로 고치지 않습니다.

## 개념 범위와 독자 수준

[`tech-category-plan.md`](./tech-category-plan.md)가 book-071에 배정한 요청-응답 처리 흐름,
라우팅, 동시 요청 처리, 무상태 원칙을 핵심 주제로 사용했습니다. 같은 카테고리의 다른 도서에 배정된
데이터 검증, 함수·모듈 구조, 로그 수집, 테스트, 데이터베이스 조회 성능, 접근성, 배포 절차는 핵심
개념으로 확장하지 않았습니다.

특정 실존 회사·제품·프레임워크·언어 이름을 쓰지 않고 `클라이언트`, `서버`, `요청`, `처리자`,
`저장소`처럼 일반적인 용어를 사용했습니다. 초보 독자가 코드를 몰라도 이해할 수 있도록 서버의
정의에서 시작해 메시지 구조, 라우팅, 처리, 동시성, 무상태 순으로 개념을 확장했습니다. 초안 검수 뒤
서사적으로 보일 수 있는 비유와 질문형 제목을 제거하고, 정의·책임 범위·처리 절차·실패 조건을 직접
설명하는 기술 교재형 문체로 개정했습니다.

## 장 구성

50페이지는 목차 1페이지와 본문 49페이지로 구성합니다.

| 장 | 페이지 | 중심 역할 | 내용 |
| --- | --- | --- | --- |
| 1장 서버와 요청-응답 모델 | 2~8 | `PREREQUISITE`·`CORE` | 서버 경계, 클라이언트, 요청-응답 대응 관계 |
| 2장 요청 메시지의 구성 | 9~15 | `PREREQUISITE`·`CORE` | 동작, 경로, 헤더, 본문으로 이루어진 요청 구조 |
| 3장 라우팅과 처리자 선택 | 16~22 | `CORE`·`COUNTERPOINT` | 경로표, 동작·경로 일치, 동적 구간과 라우팅 실패 |
| 4장 요청 처리와 응답 생성 | 23~29 | `CORE`·`COUNTERPOINT` | 요청 맥락, 업무 결과, 상태와 본문의 응답 계약 |
| 5장 동시 요청 처리와 자원 관리 | 30~36 | `CORE`·`EXAMPLE` | 작업자, 대기열, 요청 격리와 과부하 경계 |
| 6장 무상태 서버와 상태 관리 | 37~43 | `CORE`·`COUNTERPOINT` | 무상태 원칙, 외부 상태, 서버 교체와 수평 확장 |
| 7장 전체 요청 처리 흐름 | 44~50 | `EXAMPLE`·`CONCLUSION` | 성공·실패·동시 요청의 전체 흐름과 점검 항목 |

TEXT 본문 45페이지는 모두 3문단이며 501~666자, 평균 568.3자입니다. 개념 정의 뒤에 오해나
경계 조건을 별도 반례로 배치하고, 마지막 장에서는 앞선 개념을 성공·실패·동시 처리 사례에 다시
적용했습니다.

## 구조 메타데이터

- 내용 역할 5종을 모두 사용했습니다. `FRONT_MATTER`는 목차 1페이지에만 사용합니다.
- 목차만 `aiRouteCandidatePage=false`이고 나머지 49페이지는 모두 `true`입니다.
- 선수 관계 49개는 절 식별자로 설계한 뒤 최종 페이지 번호로 계산했으며, 자기 참조·범위 밖 참조·
  순환이 없습니다.
- 대표 경로는 `[3, 11, 18, 26, 33, 39, 44, 48]`로 비연속 배치했습니다.
- `request-response-contract` 중복 그룹은 4페이지의 요청-응답 대응 설명과 26페이지의 응답 계약
  재진술만 연결합니다.
- `aiPublicGuideTopic`은 원문 결론·수치·사례 결과를 옮기지 않은 별도 공개 안내 문장입니다.

## 평가 케이스: 비소장·예산 10

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-071` |
| `purpose` | 사용자가 보낸 메시지가 어느 입구를 지나 결과로 돌아오는지, 여러 메시지가 겹칠 때도 서로 섞이지 않는 이유와 실행 공간을 교체해도 업무가 이어지는 원리를 함께 이해하고 싶다 |

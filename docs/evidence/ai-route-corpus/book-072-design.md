# book-072 「데이터 검증과 스키마 경계」 설계

[기술 카테고리 계획](./tech-category-plan.md)의 72번을 만든 근거다. 정책·검증 계약은
[AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)를 따르고, 이 문서는 그 계약 안에서 내린
선택과 이유만 적는다.

## 대상 도서

- `bookId` 72, 카테고리 기술. 저자·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지한다.
- 제목은 `ai-route-v2` manifest의 `books[].title`이 정본이며 계획 문서의 제목과 같다.
- 실존 회사·제품·프레임워크·언어 이름을 쓰지 않는다. 검증 규칙도 특정 표기법에 매이지 않게 '값의
  범위', '필수와 선택'처럼 뜻으로만 적었고, 사례의 자료도 주문 목록이라는 일반 업무로만 두었다.

계획이 정한 범위(입력 검증, 데이터 정제, 스키마와 타입 경계, 데이터 파이프라인 단계)가 모두
들어갔다. 평가 시나리오도 계획대로 「비소장 · 예산 0」이다.

## 개념 범위

이 책의 축은 **이 값은 어디서 왔고, 조건을 만족한다고 누가 책임지는가**다. 첫 물음이 신뢰 경계를
정하고 둘째 물음이 검증할 자리를 정한다. 형식과 뜻의 구분(1.3), 검증 자리의 이원 배치(3.1),
정제와 검증의 구분(4.2)이 모두 이 두 물음에서 갈라져 나온다.

계획이 지정한 카테고리 내부 경계를 지켰다.

- 71(요청 처리 흐름)이 요청이 오가는 흐름 자체를 다루는 데 비해 72는 그 위에서 자료가 올바른지를
  다룬다. 요청·응답·라우팅은 개념으로 등장하지 않는다.
- 74(함수와 모듈)와 겹치지 않도록 경계 개념을 코드 구조가 아니라 **자료의 신뢰 경계**로만 썼다.
  74가 다룬 결합도·응집도·모듈 분해는 나오지 않고, 5장의 단계 나누기도 자료 상태를 기준으로 한다.
- 77(테스트 전략)과 겹치지 않도록 검증을 자동 확인 절차가 아니라 **들어오는 자료를 막는 자리**로만
  다뤘다. 시험 자료를 만들거나 확인 코드를 작성하는 방법은 나오지 않는다.
- 73(디버깅)·75(로그)·76(기본값)·78(쿼리 성능)·79(접근성)·80(배포)의 소재는 등장하지 않는다.
  3.7과 6.7의 검증 기록은 규칙이 실제와 맞는지 보는 자료로만 쓰고 로그 수집 구조는 다루지 않는다.

## 장 구성 (50페이지, 목차 1 + 본문 49)

```
1장 바깥에서 들어오는 데이터  p2–8    PREREQUISITE       외부 자료·신뢰 경계·형식과 의미·통로
2장 스키마와 타입 경계        p9–15   CORE·COUNTERPOINT  스키마·타입·필수와 선택·값 규칙·변경
3장 검증의 자리와 순서        p16–22  CORE·COUNTERPOINT  검증 위치·시점·순서·중복·층 분리·기록
4장 정제와 변환               p23–29  CORE·COUNTERPOINT  정제·표기 통일·결측·정보 손실·원본 보존
5장 데이터 파이프라인의 단계  p30–36  CORE               단계 계약·실패 처리·재실행·중간 결과·출력
6장 한 자료가 지나간 길       p37–43  EXAMPLE            받은 목록 하나를 단계별로 따라간 기록
7장 검증 설계 판단            p44–50  COUNTERPOINT·CONCLUSION  과도한 검증·차단 범위·점검 항목
```

절은 장마다 일곱 개이고 절 하나가 페이지 하나다. 1.3이 이 권의 매듭이다. 값 하나만 보고 판단할 수
있는 조건과 다른 자료를 함께 보아야 하는 조건을 가른 뒤, 그 구분이 3.1의 두 층 배치, 2.7의 스키마
한계, 3.3의 단계 순서, 6.5의 업무 위반 사례로 이어진다.

이미지 4개: p7(데이터가 들어오는 자리), p18(검증 단계의 순서), p26(정제 전후의 자료),
p33(파이프라인 단계와 자료 상태). 생성 스크립트는 [`figures072.py`](./tools/figures072.py)다.

이 권의 도표 문장 틀은 "제목 아래에 '…'라고 한 줄이 적혀 있다"로 시작하고 "그림 맨 아래 줄에는
'…'가 적혀 있다"로 끝난다. 074가 쓴 "제목 밑에 '…'라는 짧은 말이 붙어 있다"와 겹치지 않게 권마다
다른 문장을 쓴다. 도표에는 건수와 비율을 눈금으로 넣지 않았다 — 자료의 분포는 시스템마다 달라
숫자를 넣으면 본문에 없는 기준이 생긴다.

중복 그룹 1개: `unchecked-values-travel` = [5, 45]. "확인하지 않은 값은 들어온 자리에서 멈추지 않고
사본으로 퍼져 원인을 가리기 어렵게 만든다"를 1.4에서 문제로 세우고 7.2에서 차단 범위를 정하는
근거로 다시 쓴다. 5의 폐쇄는 [2, 3, 5]이고 45의 폐쇄는 [2, 4, 9, 16, 44, 45]라 서로를 지나지 않으며,
1.4를 선수로 삼는 절이 없어 두 페이지를 함께 담는 후보도 없다.

## 선수 관계 설계

1.1이 뿌리이고 1.2·1.3·1.5가 곧바로 붙는다. 2장은 1.3 → 2.1에서, 3장은 2.1 → 3.1에서, 4장은
3.1 → 4.1에서, 5장은 4.1 → 5.1에서 시작한다. 개념이 자료의 출처 → 약속 → 확인 → 교정 → 단계로
이어지는 한 줄기라 각 장의 첫 절만 앞 장에 붙이고 나머지는 장 안에서 갈라지게 했다.

6장은 5.1에 붙였고, 7장은 각 절이 요약하는 장에 직접 붙였다(7.1·7.2는 3.1, 7.3은 2.6, 7.4는 3.5,
7.5는 4.6, 7.6은 5.5, 7.7은 7.2).

- 어느 후보 페이지도 선수 폐쇄가 12페이지를 넘지 않는다.
- 폐쇄 5페이지 이하인 후보 페이지가 다섯 개 장을 덮는다 (기준 3개 장).
- 후보 페이지 49개 전부가 폐쇄 15페이지 이하다 (기준 75%).

## 검증

`corpus_lib.validate_book()` → `validate_fragment.py` → `merge_fragments.py` → `validate_manifest.py`를
차례로 통과했다.

- 50페이지(48~72), 7개 장(최소 6), 내용 역할 5종 모두 사용
- `TEXT` 본문 45페이지가 349~414자(평균 383자, 합계 17,260자)
- `estimatedReadingSeconds`에 60초로 눌린 페이지가 하나도 없음 (본문 65~75초, 목차 40초)
- `FRONT_MATTER`(목차 p1)와 `aiRouteCandidatePage=false`가 정확히 일치
- PDF 페이지 50개, 텍스트 46개, 이미지 4개(p7,18,26,33) — `pdfcheck.py`로 확인
- PDF 실제 SHA-256이 manifest의 `pdfSha256`과 일치 (664,517 bytes)
- 다른 권과 겹치는 일곱 어절이 하나도 없다

## 평가 케이스: 비소장·예산 0 시나리오

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-072` |
| `purpose` | 이미 대여해 둔 페이지만으로, 바깥에서 받은 자료를 어느 자리에서 확인하고 어떤 단계를 지나 안으로 들이는지 뼈대를 잡고 싶다 |
| `owned` / `maxAdditionalInk` / `depth` | `false` / `0` / `null` |
| `activeRentalPageNumbers` | 2, 4, 9, 16, 23, 30 |
| `requiredConcepts` | 외부 데이터, 스키마, 입력 검증, 데이터 정제, 데이터 파이프라인 |
| `helpfulConcepts` | 형식과 의미, 신뢰 경계, 타입 경계, 검증 시점 |
| `referencePageNumbers` | 2, 4, 9, 16, 23, 30 |
| `allowedAlternativePageNumbers` | 3, 5, 6, 10, 11, 17, 24 |
| `irrelevantPageNumbers` | 34·35(재실행·중간 결과), 38·40·42(원자료 관찰·정제 적용·재접수) |

예산 0이므로 **정답 경로가 곧 대여 목록**이다. 폐쇄가 대여 목록과 정확히 같아 추가 차감이 0이 된다.
경로는 1.1 → 1.3 → 2.1 → 3.1 → 4.1 → 5.1의 한 줄기 사슬이고, 각 장의 첫 절만 이어 붙인 형태다.
필수 개념 다섯이 이 여섯 페이지 가운데 다섯 페이지의 primary다.

**폐쇄를 여섯으로 얕게 잡았다.** 예산 0 사례는 대여 목록이 곧 상한이라 폐쇄가 깊으면 대여 목록이
비현실적으로 길어진다. 각 장의 첫 절을 한 줄기로 이어 폐쇄를 장 수와 같게 두면, 대여 목록이 "각 장의
도입부만 빌려 둔 독자"라는 자연스러운 상태가 된다.

대체 일곱은 모두 폐쇄가 여섯 이하라 대여 목록 안에서 갈아 끼울 수 있다. 넷은 정답의 짝이고(3·5·6은
1장, 10·11은 2장), 17과 24는 검증 시점과 정제의 판단으로 들어가는 첫 페이지다.

무관은 절 단위로 골랐다. 5.5·5.6은 파이프라인을 운영하며 다시 돌리고 중간 결과를 남기는 문제이고, 6장의 셋은 특정 자료의 진행 기록이다. 이 목적은 뼈대를 잡는
것이라 다섯 다 목적 밖이고, 필수·도움 개념을 primary로 달지 않으며, 정답·대체 어느 페이지도 이들을 선수로 거치지 않는다.

## 재현 조건

1. `python3 build072.py` — 원고와 조각 생성 (PDF SHA 없이 실행하면 자리표시자를 넣는다)
2. `python3 figures072.py pdfbuild072` — 도표 4개 SVG 생성
3. Chrome Headless로 각 SVG를 794×1123 PNG로 렌더링
4. `python3 build_pdf_generic.py 72 7,18,26,33 pdfbuild072` — 조판 HTML 생성
5. Chrome Headless `--print-to-pdf`로 PDF 출력, `pdfcheck.py`로 구성 확인
6. PDF를 `fixtures/content/ai-route-v2/pdfs/`에 두고 SHA-256을 인자로 `build072.py` 재실행
7. `merge_fragments.py 72`로 정본에 병합. 이미 병합한 뒤에 다시 만들 때는
   [도구 README의 되돌리기 절차](./tools/README.md#이미-병합한-도서를-다시-만들-때)를 먼저 따른다

## 검수

- 도표 네 장을 PNG로 렌더링해 눈으로 모두 확인했고 p26을 고쳤다. 두 줄짜리 설명이 **위아래 순서가
  뒤집혀** "것만 옮긴다 / 되돌릴 수 있는"으로 그려져 있었고, 오른쪽 칸의 막대가 변경 표시 점과 닿아
  막대 길이를 줄였다.
- 초고에서 074와 일곱 어절이 겹치는 자리가 둘 나왔다. 도표 도입 문장 틀과 7.4의 점검 항목 마무리
  문장이다. 도표 틀은 이 권 전용 문장으로 바꾸고 점검 문장은 다시 썼다. 도표 틀은 권마다 다르게
  두는 것이 기존 관례(036·038·039)와도 맞는다.
- 본문 수정 뒤 PDF를 다시 출력하고 SHA-256과 조각을 함께 갱신했다.
- 공개 가이드 주제와 비공개 분석 텍스트를 서로 다른 문장으로 적었고, 주제문에 숫자를 쓰지 않았다.
  50개 주제문과 50개 분석 텍스트에 중복이 없다.
- 본문·도표·평가 데이터에 실존 인물·작품·단체·제품이 등장하지 않는다. 사례의 연락처·주문 번호는
  값을 적지 않고 항목 이름으로만 서술했다.
- **리뷰 뒤 무관 페이지를 다시 골랐다.** 초고는 아홉 권이 모두 6장의 같은 다섯 페이지를
  무관으로 적어 평가 데이터가 권마다 구분되지 않았다. 이 권은 5장의 두 절과 6장의 세 절로
  바꿔 카테고리 안에서 겹치지 않는 세트가 되게 했다. 원고와 PDF는 바뀌지 않았다.
- 리뷰 뒤 도움 개념의 `단계 계약`을 `검증 시점`으로 바꿨다. 단계 계약을 담은 5.2는 폐쇄가 일곱이라
  대여 여섯 페이지 안에서 고를 수 없어 이 사례에서는 닿지 않는 개념이었다.
- 리뷰 뒤 7.3·7.4·7.7의 공개 주제문을 이 권의 것으로 바꿨다. 초고의 세 문장이 각각 074·075·전 권과
  겹쳐 공개 안내가 책을 구분해 주지 못했다.
- `ContentBatchConverterTest`의 코퍼스 재고 단언을 갱신했다. 도서 52→53, 페이지 2191→2241,
  이미지 251→255다.

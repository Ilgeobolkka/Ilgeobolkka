# book-074 「함수와 모듈: 인터페이스 설계」 설계

[기술 카테고리 계획](./tech-category-plan.md)의 74번을 만든 근거다. 정책·검증 계약은
[AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)를 따르고, 이 문서는 그 계약 안에서 내린
선택과 이유만 적는다.

## 대상 도서

- `bookId` 74, 카테고리 기술. 저자·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지한다.
- 제목은 `ai-route-v2` manifest의 `books[].title`이 정본이며 계획 문서의 제목과 같다.
  `books.json`은 동결된 `initial-v1` fixture라 고치지 않는다.
- 실존 회사·제품·프레임워크·언어 이름을 쓰지 않는다. 함수·모듈·호출부·인터페이스·계약처럼
  특정 스택에 매이지 않는 용어로만 서술하고, 예로 드는 업무도 주문·재고·배송·알림 같은 일반 명사로만
  적었다. 문체는 같은 카테고리의 book-071과 같은 기술 교재형이다.

계획이 정한 범위(함수 분해, 인터페이스와 계약, 결합도·응집도, 모듈 경계)가 모두 들어갔다. 평가
시나리오도 계획대로 「비소장 · 예산 15」다.

## 개념 범위

이 책의 축은 **무엇을 경계 밖에 두고 무엇을 안쪽에 감출 것인가**다. 함수에서는 이름·입력·결과가
경계이고 모듈에서는 공개한 함수 목록과 그 계약이 경계이며, 규모가 달라도 판단 방법이 같다는 것을
1장과 5장에서 같은 물음으로 되풀이한다.

계획이 지정한 카테고리 내부 경계를 지켰다.

- 71(요청 처리 흐름)이 시스템 경계를 다루는 데 비해 74는 코드 내부의 조직 원리를 다룬다. 이 책에는
  요청·응답·라우팅·동시 처리·무상태가 개념으로 등장하지 않는다.
- 72(데이터 검증)와 겹치지 않도록 5장에서 경계의 검증 책임을 다루지 않고 **경계의 안정성과 오가는
  값의 형태**만 다뤘다. 2.3의 사전 조건은 값의 유효성 규칙이 아니라 책임 귀속의 문제로 서술했다.
- 77(테스트 전략)과 겹치지 않도록 확인 방법 자체는 다루지 않는다. 6.6에서 분리 후 확인을 절차의
  한 단계로만 적고 무엇을 어떻게 검증하는지는 적지 않았다.
- 73(디버깅)·75(로그)·78(쿼리 성능)·79(접근성)·80(배포)의 소재는 등장하지 않는다.

## 장 구성 (50페이지, 목차 1 + 본문 49)

```
1장 함수와 책임            p2–8    PREREQUISITE·CORE  함수·책임·이름·분해·입출력·부수 효과
2장 인터페이스와 계약      p9–15   CORE               인터페이스·계약·사전 조건·실패 표현·구현 교체
3장 결합도와 의존 방향     p16–22  CORE·COUNTERPOINT  결합도·의존 방향·결합의 종류·순환·완화
4장 응집도와 모듈 구성     p23–29  CORE·COUNTERPOINT  응집도·변경 이유·묶는 기준·모듈 크기
5장 모듈 경계와 공개 범위  p30–36  CORE·EXAMPLE       경계·공개 범위·경계 데이터·안정성·결정 순서
6장 경계를 다시 그린 사례  p37–43  EXAMPLE            한 모듈을 나눈 과정 전체
7장 설계 판단 기준         p44–50  COUNTERPOINT·CONCLUSION  과도한 분해·점검 항목·기록·요약
```

절은 장마다 일곱 개이고 절 하나가 페이지 하나다. 4.2가 이 권의 매듭이다. 무엇을 한자리에 둘지는
코드의 생김새가 아니라 **함께 고쳐지는가**로 정한다는 기준이 4장 전체의 줄기이고, 6장의 사례에서
분리 대상을 고르는 근거로 다시 쓰이며, 7.4의 점검 항목 첫 줄이 된다.

6장은 앞 다섯 장의 개념을 한 사례에 순서대로 적용하는 장이다. 결과가 아니라 각 단계에서 무엇을 보고
무엇을 정했는지를 적었고, 6.7에서 남긴 결합과 그 이유까지 적어 한 번의 분리로 끝나지 않는다는 것을
드러냈다.

이미지 4개: p7(함수 분해 전후 구조), p20(의존 방향과 순환), p28(변경 이유로 묶은 모듈),
p41(분리 절차와 확인 지점). 생성 스크립트는 [`figures074.py`](./tools/figures074.py)다.

이 권 전용 도표 문장 틀을 쓴다. 첫 문장은 "제목 밑에 '…'라는 짧은 말이 붙어 있다"로, 끝 문장은
"그림 맨 아래 줄에는 '…'가 적혀 있다"로 고정했다. 도표에는 수치 눈금을 넣지 않았다 — 이 책의 판단
기준은 양이 아니라 무엇이 어디에 놓였는지이고, 숫자를 넣으면 본문에 없는 기준이 생긴다.

중복 그룹 1개: `contract-outlives-implementation` = [14, 33]. "계약이 그대로면 안쪽을 바꿔도 바깥이
흔들리지 않는다"를 2.6에서 함수·모듈 공통의 원리로 세우고 5.4에서 경계 위치를 고르는 기준으로 다시
쓴다. 14의 폐쇄는 [2, 9, 10, 14]이고 33의 폐쇄는 [2, 9, 16, 23, 30, 31, 33]이라 서로를 지나지
않으며, 두 페이지를 함께 폐쇄에 담는 후보 페이지도 없다.

## 선수 관계 설계

1.1이 뿌리이고 1.2·1.5·2.1이 곧바로 거기 붙는다. 2장은 2.1 → 2.2에서 2.3·2.4·2.6이 갈라지고
2.5·2.7이 2.3에 붙는다. 3장은 2.1 → 3.1에서 시작해 3.2·3.3으로 갈라지며, 4장은 3.1 → 4.1에서,
5장은 4.1 → 5.1에서 시작한다. 개념 순서가 함수 → 인터페이스 → 결합 → 응집 → 경계로 한 줄기를
이루므로 각 장의 첫 절만 앞 장에 붙이고 나머지는 장 안에서 갈라지게 했다.

6장은 5.1에 붙여 사례가 경계 개념 하나만 전제하게 했고, 7장은 각 절이 요약하는 장에 직접 붙였다
(7.1·7.2는 1.4, 7.3은 2.6, 7.4·7.6은 4.5, 7.5는 5.1, 7.7은 7.2).

- 어느 후보 페이지도 선수 폐쇄가 11페이지를 넘지 않는다.
- 폐쇄 5페이지 이하인 후보 페이지가 여섯 개 장을 덮는다 (기준 3개 장).
- 후보 페이지 49개 전부가 폐쇄 15페이지 이하다 (기준 75%).

## 검증

`corpus_lib.validate_book()` → `validate_fragment.py` → `merge_fragments.py` → `validate_manifest.py`를
차례로 통과했다.

- 50페이지(48~72), 7개 장(최소 6), 내용 역할 5종 모두 사용
- `TEXT` 본문 45페이지가 371~471자(평균 415자, 합계 18,709자)

- 선수 관계가 후보 제외 페이지를 가리키지 않음, 위상 정렬로 50페이지 전체 방문

- PDF 실제 SHA-256이 manifest의 `pdfSha256`과 일치 (690,047 bytes)

## 평가 케이스: 비소장·예산 15 시나리오

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-074` |
| `purpose` | 코드를 함수와 모듈로 어떻게 나누고 그 사이의 약속을 어떻게 정할지, 구조를 판단하는 기준을 넓게 정리하고 싶다 |
| `owned` / `maxAdditionalInk` / `depth` | `false` / `15` / `null` |
| `requiredConcepts` | 함수 분해, 인터페이스, 계약, 결합도, 응집도, 모듈 경계 |
| `helpfulConcepts` | 함수의 책임, 사전 조건, 의존 방향, 결합 완화, 공개 범위 |
| `referencePageNumbers` | 2, 3, 5, 9, 10, 11, 16, 17, 18, 22, 23, 27, 30, 31, 47 |
| `allowedAlternativePageNumbers` | 4, 6, 12, 14, 21, 24, 29, 32, 36 |
| `irrelevantPageNumbers` | 37·38·39(사례의 배경·의존 파악·분리 지점), 42·43(분리 후 확인·남은 결합) |

정답 경로는 선수 전이 폐쇄와 같고 15페이지여서 예산 15를 정확히 채운다. 대여가 없는 사례이므로
폐쇄 전체가 곧 차감량이다.

**폐쇄를 상한과 같게 잡았다.** 71번은 예산 10에 경로 8페이지여서 여유가 있었고, 74번은 다섯 갈래를
모두 담아 상한을 정확히 쓰는 쪽을 골랐다. 넓은 예산을 준 시나리오가 실제로 넓은 경로를 요구하는지
검증하려면 상한을 채우는 사례가 하나는 있어야 한다.

경로는 함수(2) → 책임(3) → 분해(5)의 1장 사슬에서 시작해, 인터페이스(9) → 계약(10) → 사전
조건(11)의 2장 사슬, 결합도(16)에서 갈라지는 의존 방향(17)과 결합의 종류(18) → 완화(22), 응집도(23)
→ 응집도와 결합도(27) → 점검 항목(47), 모듈 경계(30) → 공개 범위(31)로 이어진다. 필수 개념 여섯이
각각 이 다섯 갈래의 첫 페이지다.

대체 아홉 가운데 넷은 정답의 짝이고(4·6은 1장, 12·14는 2장, 21은 3장) 나머지는 정답이 다루지 않은
다른 각도의 첫 페이지다(24 변경 이유, 29 모듈 크기, 32 경계 데이터, 36 경계 결정 순서). 아홉 모두
폐쇄가 7페이지 이하라 예산 안에서 갈아 끼울 수 있다.

무관은 절 단위로 골랐다. 6장의 다섯 페이지는 특정 사례의 진행 단계이고, 이 목적은 사례가 아니라
판단 기준을 넓게 정리하는 것이다. 다섯 다 필수·도움 개념을 primary로 달지 않는다. 6.4(인터페이스
선행 정의)와 6.5(분리 절차)는 원리에 가까워 무관에서 뺐다.

## 재현 조건

1. `python3 build074.py` — 원고와 조각 생성 (PDF SHA 없이 실행하면 자리표시자를 넣는다)
2. `python3 figures074.py pdfbuild074` — 도표 4개 SVG 생성
3. Chrome Headless로 각 SVG를 794×1123 PNG로 렌더링
4. `python3 build_pdf_generic.py 74 7,20,28,41 pdfbuild074` — 조판 HTML 생성
5. Chrome Headless `--print-to-pdf`로 PDF 출력, `pdfcheck.py`로 구성 확인
6. PDF를 `fixtures/content/ai-route-v2/pdfs/`에 두고 SHA-256을 인자로 `build074.py` 재실행
7. `merge_fragments.py 74`로 정본에 병합

PDF는 Chrome Headless 출력이므로 다시 만들면 바이트와 SHA-256이 달라진다. 재생성하면 manifest의
`pdfSha256`과 이 문서의 값을 함께 갱신한다.

## 검수

- 도표 네 장을 PNG로 렌더링해 눈으로 모두 확인했고 넷 다 고쳤다. p07은 아래 줄 맨 오른쪽 화살표가
  좌표 계산 실수로 **반대 방향으로 그려져** 있어 네모 폭과 간격을 줄이고 화살표를 상대 좌표로
  다시 잡았다. p20은 오른쪽 순환 그림이 페이지 오른쪽 끝에 닿아 세 네모를 왼쪽으로 옮겼다. p28은
  네모 셋의 오른쪽 끝이 머리글 선(105~689)을 넘어가 폭과 간격을 줄였다. p41은 네모 다섯이 같은
  이유로 넘쳐 폭을 줄였고, 맨 아래 줄과 뜻이 겹치는 설명 한 줄을 지웠다.
- 도표를 고치면서 본문의 도표 설명 네 곳도 그림에 맞춰 다시 적었다. p20은 세 네모의 위치를
  왼쪽·오른쪽까지 밝혔고, p28은 설명 문구가 줄 오른쪽이 아니라 줄 아래 오른쪽 끝에 있다고 고쳤다.
- 본문 페이지 밀도는 같은 카테고리의 book-071(501~666자)보다 낮은 371~471자다. 조판 결과를 원본
  크기로 확인해 두 권의 지면 채움이 비슷한 범위임을 보고 그대로 두었다.
- 다른 권과 겹치는 일곱 어절이 하나도 없다. 원고 전체를 어절 단위로 대조해 확인했다.
- 공개 가이드 주제와 비공개 분석 텍스트를 서로 다른 문장으로 적었고, 주제문에 숫자를 쓰지 않았다.
  50개 주제문과 50개 분석 텍스트에 중복이 없다.
- 본문·도표·평가 데이터에 실존 인물·작품·단체·제품이 등장하지 않는다.
- `ContentBatchConverterTest`의 코퍼스 재고 단언을 갱신했다. 도서 51→52, 페이지 2141→2191,
  이미지 247→251이다.

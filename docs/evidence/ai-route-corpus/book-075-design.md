# book-075 「로그 설계와 수집 파이프라인」 설계

[기술 카테고리 계획](./tech-category-plan.md)의 75번을 만든 근거다. 정책·검증 계약은
[AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)를 따르고, 이 문서는 그 계약 안에서 내린
선택과 이유만 적는다.

## 대상 도서

- `bookId` 75, 카테고리 기술. 저자·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지한다.
- 제목은 `ai-route-v2` manifest의 `books[].title`이 정본이며 계획 문서의 제목과 같다.
- 실존 회사·제품·수집 도구 이름을 쓰지 않는다. 수집기·저장소·집계처럼 역할 이름으로만 적었다.

계획이 정한 범위(로그 레벨, 구조화된 로그, 로그 수집·집계 파이프라인)가 모두 들어갔다. 평가
시나리오도 계획대로 「소장 · QUICK」이다.

## 개념 범위

이 책의 축은 **나중에 누가 무엇을 물을 것인가**다. 남길 것(1.2), 레벨(2.2), 항목(3.2), 보관
기간(4.5)이 모두 이 물음에서 역산된다. 5.2의 네 질의 유형이 이 축을 명시적인 점검 도구로 바꾸고,
6장의 사례가 그 도구로 재설계를 진행한다.

계획이 지정한 카테고리 내부 경계를 지켰다.

- 73(디버깅)이 문제를 재현하고 좁히는 사람의 절차를 다루는 데 비해 75는 기록이 만들어져 모이고
  분석되는 기계적 과정을 다룬다. 재현·최소 사례·이분 탐색은 나오지 않고, 5.1의 추적도 로그 구조가
  가능하게 하는 조회 방식으로만 서술한다.
- 72(데이터 검증)와 겹치지 않도록 3장의 항목 이름을 스키마 검증이 아니라 **조회 가능성**의 문제로
  다뤘다. 값의 유효성 규칙이나 위반 차단은 나오지 않는다.
- 76(기본값과 실패 경계)과 겹치지 않도록 4.7의 적체를 실패 경계 설계가 아니라 수집 단계의 관찰
  문제로만 적었다.
- 71·74·77·78·79·80의 소재는 등장하지 않는다.

## 장 구성 (50페이지, 목차 1 + 본문 49)

```
1장 로그가 하는 일             p2–8    PREREQUISITE·COUNTERPOINT  로그·기록 대상·금지 대상·독자
2장 로그 레벨                  p9–15   CORE·COUNTERPOINT  레벨 기준·오류와 경고·대응·붕괴
3장 구조화된 로그              p16–22  CORE·COUNTERPOINT  항목 이름·값 형태·추적 식별자·항목 난립
4장 수집과 집계 파이프라인     p23–29  CORE·COUNTERPOINT  수집 단계·전송 손실·집계·보관·적체
5장 로그로 무엇을 보는가       p30–36  CORE·COUNTERPOINT  흐름 추적·질의 유형·한계·표본
6장 로그를 다시 설계한 기록    p37–43  EXAMPLE            한 서비스의 로그를 다시 설계한 과정
7장 로그 설계 판단             p44–50  COUNTERPOINT·CONCLUSION  기록량·우선순위·점검·수단 배치
```

절은 장마다 일곱 개이고 절 하나가 페이지 하나다. 1.5가 이 권의 매듭이다. 로그는 남기는 사람이 아니라
나중에 묻는 사람을 위한 것이라는 규정이 2.2의 행동 기준, 3.4의 문장과 항목 분리, 5.7의 화면 설계,
7.2의 개선 순서로 이어진다.

이미지 4개: p7(한 줄의 로그가 담는 것), p14(레벨이 무너지는 방식), p26(수집 파이프라인의 단계),
p33(흩어진 기록을 잇는 방법). 생성 스크립트는 [`figures075.py`](./tools/figures075.py)다.

이 권의 도표 문장 틀은 "제목 아래 '…'라는 말이 한 줄 붙어 있다"로 시작하고 "그림의 맨 아래 줄은
'…'다"로 끝난다. 072·073·074와 각각 다른 문장을 쓴다. 도표에는 건수와 용량을 눈금으로 넣지 않았다 —
서비스마다 자릿수가 달라 숫자를 넣으면 본문에 없는 기준이 생긴다.

중복 그룹 1개: `logs-answer-questions` = [6, 45]. "로그는 남기는 사람이 아니라 나중에 묻는 사람을
위한 것이다"를 1.5에서 독자의 처지로 세우고 7.2에서 개선 순서를 정하는 기준으로 다시 쓴다. 6의
폐쇄는 [2, 6]이고 45의 폐쇄는 [2, 3, 44, 45]라 서로를 지나지 않으며, 1.5를 선수로 삼는 절이 없어
둘을 함께 담는 후보도 없다.

## 선수 관계 설계

1.1이 뿌리이고 1.2·1.4·1.5가 곧바로 붙는다. 2장은 1.1 → 2.1에서, 3장은 2.1 → 3.1에서, 4장은
3.1 → 4.1에서, 5장은 4.1 → 5.1에서 시작한다. 개념이 로그 → 레벨 → 구조 → 수집 → 조회로 이어지는
한 줄기라 각 장의 첫 절만 앞 장에 붙였다.

6장은 4.1에 붙였고, 7장은 각 절이 요약하는 장에 직접 붙였다(7.1·7.2는 1.2, 7.3은 2.7, 7.4는 3.2,
7.5는 4.7, 7.6은 1.4, 7.7은 7.2).

- 어느 후보 페이지도 선수 폐쇄가 11페이지를 넘지 않는다.
- 폐쇄 5페이지 이하인 후보 페이지가 일곱 개 장을 모두 덮는다 (기준 3개 장).
- 후보 페이지 49개 전부가 폐쇄 15페이지 이하다 (기준 75%).

## 검증

`corpus_lib.validate_book()` → `validate_fragment.py` → `merge_fragments.py` → `validate_manifest.py`를
차례로 통과했다.

- 50페이지(48~72), 7개 장(최소 6), 내용 역할 5종 모두 사용
- `TEXT` 본문 45페이지가 344~388자(평균 363자, 합계 16,343자)
- `estimatedReadingSeconds`에 60초로 눌린 페이지가 하나도 없음
- `FRONT_MATTER`(목차 p1)와 `aiRouteCandidatePage=false`가 정확히 일치
- PDF 페이지 50개, 텍스트 46개, 이미지 4개(p7,14,26,33) — `pdfcheck.py`로 확인
- PDF 실제 SHA-256이 manifest의 `pdfSha256`과 일치 (644,029 bytes)
- 다른 권과 겹치는 일곱 어절이 하나도 없다

## 평가 케이스: 소장·QUICK 시나리오

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-075` |
| `purpose` | 이 책을 소장하고 있는데, 로그를 왜 어떤 형태로 남기고 어디로 모으는지 핵심만 빠르게 훑고 싶다 |
| `owned` / `maxAdditionalInk` / `depth` | `true` / `null` / `QUICK` |
| `requiredConcepts` | 로그, 로그 레벨, 구조화된 로그, 로그 수집, 흐름 추적 |
| `helpfulConcepts` | 기록 대상, 레벨 기준, 항목 이름, 집계 |
| `referencePageNumbers` | 2, 9, 16, 23, 30 |
| `allowedAlternativePageNumbers` | 3, 5, 6, 10, 11, 17, 20, 24, 25 |
| `irrelevantPageNumbers` | 32·35(로그의 한계·표본 기록), 39·41·43(레벨 재정의·수집 개선·재확인) |

정답 경로는 선수 폐쇄와 같고 다섯 페이지여서 QUICK 상한 5를 정확히 채운다. 각 장의 첫 절만 이어
붙인 사슬이고, 필수 개념 다섯이 다섯 페이지의 primary와 하나씩 대응한다.

**같은 상한을 073과 다른 방식으로 채웠다.** 073은 예산 5(비소장)에서 다섯 페이지를 썼고 075는
QUICK(소장)에서 다섯 페이지를 쓴다. 상한 값이 같아도 소장 여부에 따라 경로 판정 경로가 다르므로,
두 사례가 같은 길이의 경로를 서로 다른 판정으로 통과하는 짝이 된다.

대체 아홉은 모두 폐쇄가 다섯 이하다. 셋은 정답의 짝이고(3·5·6은 1장의 다른 절), 10·11은 레벨 기준과
오류·경고 판정, 17·20은 항목 이름과 추적 식별자, 24·25는 전송 손실과 집계로 들어가는 첫 페이지다.

무관은 절 단위로 골랐다. 5.3·5.6은 로그의 한계와 표본 선택이라는 운영 판단이고 6장의 셋은 한 서비스의 재설계 진행 기록이다. 이 목적은 핵심을 빠르게 훑는 것이라
다섯 다 목적 밖이고, 필수·도움 개념을 primary로 달지 않으며, 정답·대체 어느 페이지도 이들을 선수로 거치지 않는다.

## 재현 조건

1. `python3 build075.py` — 원고와 조각 생성 (PDF SHA 없이 실행하면 자리표시자를 넣는다)
2. `python3 figures075.py pdfbuild075` — 도표 4개 SVG 생성
3. Chrome Headless로 각 SVG를 794×1123 PNG로 렌더링
4. `python3 build_pdf_generic.py 75 7,14,26,33 pdfbuild075` — 조판 HTML 생성
5. Chrome Headless `--print-to-pdf`로 PDF 출력, `pdfcheck.py`로 구성 확인
6. PDF를 `fixtures/content/ai-route-v2/pdfs/`에 두고 SHA-256을 인자로 `build075.py` 재실행
7. `merge_fragments.py 75`로 정본에 병합. 이미 병합한 뒤에 다시 만들 때는
   [도구 README의 되돌리기 절차](./tools/README.md#이미-병합한-도서를-다시-만들-때)를 먼저 따른다

## 검수

- 초고 45쪽 가운데 서른일곱 쪽이 344자에 못 미쳐 `estimatedReadingSeconds`가 60초로 눌렸다. 각 쪽
  마지막 문단에 한 문장씩 더해 344~388자로 맞췄다.
- **문장을 덧붙이는 스크립트가 닫는 따옴표를 잘못 옮겨 원고 파일이 한 번 깨졌다.** 삽입 위치를
  잘못 계산해 문자열 리터럴이 열린 채 남았고, 같은 패턴을 되돌리는 방식으로 복구했다. 이후 삽입은
  절 제목으로 위치를 찾아 리터럴 경계에 넣는 방식으로 바꿨다.
- 5.1에서 다른 권을 가리키던 문장("앞 권에서 다룬 좁히기")을 지웠다. 각 권은 독립적으로 읽혀야 하고
  정본도 선수 관계를 같은 도서 안으로만 허용한다.
- 도표 네 장을 PNG로 렌더링해 눈으로 모두 확인했고 고칠 자리는 없었다.
- 초고에서 072·073·074와 일곱 어절이 겹치는 자리가 둘 나왔다. 도표 도입 문장과 점검 항목 마무리
  문장이다. 둘 다 이 권 전용 표현으로 다시 썼다.
- 공개 가이드 주제와 비공개 분석 텍스트를 서로 다른 문장으로 적었고, 주제문에 숫자를 쓰지 않았다.
  50개 주제문과 50개 분석 텍스트에 중복이 없다.
- 본문·도표·평가 데이터에 실존 인물·작품·단체·제품이 등장하지 않는다.
- **리뷰 뒤 무관 페이지를 다시 골랐다.** 초고는 아홉 권이 모두 6장의 같은 다섯 페이지를
  무관으로 적어 평가 데이터가 권마다 구분되지 않았다. 이 권은 5장의 두 절과 6장의 세 절로
  바꿔 카테고리 안에서 겹치지 않는 세트가 되게 했다. 원고와 PDF는 바뀌지 않았다.
- 리뷰 뒤 대체 페이지에 25(4.3 모아서 세는 일)를 더했다. 도움 개념 `집계`를 담은 유일한 페이지인데
  빠져 있어 이 사례에서 닿지 않았다. 폐쇄가 다섯이라 QUICK 상한 안에 든다.
- 리뷰 뒤 7.4·7.7의 공개 주제문을 이 권의 것으로 바꿨다. 초고의 두 문장이 다른 권과 겹쳤다.
- `ContentBatchConverterTest`의 코퍼스 재고 단언을 갱신했다. 도서 54→55, 페이지 2291→2341,
  이미지 259→263이다.

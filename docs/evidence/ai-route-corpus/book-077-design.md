# book-077 「테스트 전략과 계약 검증」 설계

[기술 카테고리 계획](./tech-category-plan.md)의 77번을 만든 근거다. 정책·검증 계약은
[AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)를 따르고, 이 문서는 그 계약 안에서 내린
선택과 이유만 적는다.

## 대상 도서

- `bookId` 77, 카테고리 기술. 저자·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지한다.
- 제목은 `ai-route-v2` manifest의 `books[].title`이 정본이며 계획 문서의 제목과 같다.
- 실존 시험 도구와 프레임워크 이름을 쓰지 않는다. '확인', '대체물', '계약'처럼 도구에 매이지 않는
  말로만 적었고, 6장 사례의 기능도 일반 업무 용어로만 서술했다.

계획이 정한 범위(단위·통합 테스트, 테스트 대체물, 계약 검증, 회귀 방지)가 모두 들어갔다. 평가
시나리오도 계획대로 「소장 · DEEP」이다.

## 개념 범위

이 책의 축은 **이 확인은 어떤 기대를 지켜 주는가**와 **그 기대는 어느 층에서 가장 싸게 지켜지는가**다.
앞의 물음이 확인의 내용을 정하고(1장, 2장) 뒤의 물음이 배치를 정한다(3장, 4장). 5장은 배치가 시간이
지나며 흐트러지는 문제를 다루고, 6장은 확인이 거의 없던 기능 하나를 감싼 기록이다.

계획이 지정한 카테고리 내부 경계를 지켰다.

- 74(함수와 모듈)가 무엇을 어떻게 나누는가를 다루는 데 비해 77은 그 구조가 계속 맞는지 확인하는
  절차를 다룬다. 결합도·응집도·모듈 분해는 개념으로 등장하지 않고, 5.7에서 확인의 난도를 구조 신호로
  읽는 자리에서만 스친다.
- 72(데이터 검증)와 겹치지 않도록 확인을 실행 중의 값 차단이 아니라 **개발 중의 기대 검증**으로만
  다뤘다. 7.6에서 두 장치가 맡을 자리를 명시적으로 나눈다.
- 73(디버깅)과 겹치지 않도록 5.2의 재현 확인을 결함 조사 절차가 아니라 회귀 방지 장치로만 적었다.
- 76(기본값과 실패 경계)과 겹치지 않도록 실패 처리 설계는 다루지 않고, 4.7에서 상대의 계약 위반이
  확인이 아닌 실행 시 경계의 몫임을 밝히는 데 그쳤다.
- 71·75·78·79·80의 소재는 등장하지 않는다.

## 장 구성 (50페이지, 목차 1 + 본문 49)

```
1장 확인의 목적                     p2–8    PREREQUISITE·COUNTERPOINT  대상·효용·층·통과의 의미
2장 단위 확인                       p9–15   CORE·COUNTERPOINT  단위 범위·구조·단일 물음·취약 확인
3장 대체물                          p16–22  CORE·COUNTERPOINT  종류·대체 대상·착각·축소·노후
4장 통합 확인과 계약                p23–29  CORE·COUNTERPOINT  통합 자리·계약 검증·공유·범위
5장 회귀 방지                       p30–36  CORE·COUNTERPOINT  회귀·재현 확인·축적·시간·흔들림
6장 한 기능을 확인으로 감싼 기록    p37–43  EXAMPLE            기대 수집에서 변경 수행까지
7장 확인 전략 판단                  p44–50  COUNTERPOINT·CONCLUSION  분량·통과 해석·재배분·점검
```

절은 장마다 일곱 개이고 절 하나가 페이지 하나다. 1.1이 이 권의 매듭이다. 확인의 대상을 적힌 기대로
한정하고 구현 절차를 대상에서 뺀 규정이 2.7의 취약한 확인, 3.3의 대체 범위, 5.2의 증상 기준 확인,
7.1의 분량 판단으로 이어진다.

3.7이 3장과 4장을 잇는 자리다. 대체물이 낡는 문제는 대체물 안에서 풀 수 없고 계약 검증이 필요하다는
결론이 4장의 도입이 된다. 두 장을 개념으로 이어 붙인 자리이므로 선수 관계도 3.1 → 4.1로 두었다.

이미지 4개: p7(확인의 층과 범위), p13(확인 하나의 구조), p20(대체물이 놓이는 자리),
p26(계약을 사이에 둔 두 확인). 생성 스크립트는 [`figures077.py`](./tools/figures077.py)다.

이 권의 도표 문장 틀은 "제목 다음 줄에 '…'가 놓여 있다"로 시작하고 "그림 아래 마지막 줄은 '…'라고
되어 있다"로 끝난다. 072·073·074·075·076·078과 각각 다른 문장을 쓴다. 도표에는 확인의 개수와 시간을
눈금으로 넣지 않았다 — 알맞은 수는 코드마다 달라 숫자를 넣으면 본문에 없는 기준이 생긴다.

중복 그룹 1개: `green-is-not-proof` = [5, 45]. "확인이 모두 통과했다는 말은 적어 둔 기대가 지켜졌다는
뜻이지 코드에 문제가 없다는 뜻이 아니다"를 1.4에서 경고로 세우고 7.2에서 배포 판단의 기준으로 다시
쓴다. 5의 폐쇄는 [2, 3, 5]이고 45의 폐쇄는 [2, 3, 44, 45]라 서로를 지나지 않으며, 1.4를 선수로 삼는
절이 없어 둘을 함께 담는 후보도 없다.

## 선수 관계 설계

1.1이 뿌리이고 1.2·1.3이 곧바로 붙는다. 2장은 1.3 → 2.1에서, 3장은 2.1 → 3.1에서, 4장은
3.1 → 4.1에서, 5장과 6장은 4.1에서 시작한다. 확인의 층 → 단위 → 대체물 → 통합으로 이어지는 한 줄기가
이 권의 개념 순서 그대로다.

7장은 각 절이 요약하는 장에 직접 붙였다(7.1·7.2는 1.2, 7.3은 1.7, 7.4·7.6은 4.3과 4.7, 7.5는 5.5,
7.7은 7.2).

- 어느 후보 페이지도 선수 폐쇄가 11페이지를 넘지 않는다.
- 폐쇄 5페이지 이하인 후보 페이지가 다섯 개 장을 덮는다 (기준 3개 장).
- 후보 페이지 49개 전부가 폐쇄 15페이지 이하다 (기준 75%).

## 검증

`corpus_lib.validate_book()` → `validate_fragment.py` → `merge_fragments.py` → `validate_manifest.py`를
차례로 통과했다.

- 50페이지(48~72), 7개 장(최소 6), 내용 역할 5종 모두 사용
- `TEXT` 본문 45페이지가 344~393자(평균 362자, 합계 16,319자)
- `estimatedReadingSeconds`에 60초로 눌린 페이지가 하나도 없음
- `FRONT_MATTER`(목차 p1)와 `aiRouteCandidatePage=false`가 정확히 일치
- PDF 페이지 50개, 텍스트 46개, 이미지 4개(p7,13,20,26) — `pdfcheck.py`로 확인
- PDF 실제 SHA-256이 manifest의 `pdfSha256`과 일치 (652,246 bytes)
- 다른 권과 겹치는 일곱 어절이 하나도 없다

## 평가 케이스: 소장·DEEP 시나리오

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-077` |
| `purpose` | 이 책을 소장하고 있는데, 무엇을 어느 층에서 확인하고 주고받는 약속을 어떻게 검증할지 깊이 정리하고 싶다 |
| `owned` / `maxAdditionalInk` / `depth` | `true` / `null` / `DEEP` |
| `requiredConcepts` | 확인의 층, 단위 확인, 테스트 대체물, 통합 확인, 계약 검증, 회귀 |
| `helpfulConcepts` | 확인의 효용, 단위 범위, 대체물 종류, 계약 공유, 재현 확인 |
| `referencePageNumbers` | 2, 3, 4, 9, 10, 11, 16, 17, 18, 23, 24, 25, 30, 31, 32 |
| `allowedAlternativePageNumbers` | 5, 6, 8, 12, 14, 19, 26, 33 |
| `irrelevantPageNumbers` | 34·36(불안정 확인·설계 신호), 38·40·42(기대 정리·대체물 구성·발견 사항) |

정답 경로는 선수 폐쇄와 같고 열다섯 페이지여서 DEEP 상한 15를 정확히 채운다. 1장의 도입 셋에서
2장(단위 확인 → 단위 범위 → 구조), 3장(대체물 → 종류 → 대상), 4장(통합 → 계약 → 공유),
5장(회귀 → 재현 확인 → 축적)으로 각각 세 페이지씩 갈라지는 모양이다.

**이 권이 카테고리에서 가장 넓은 경로다.** 계획이 77에 DEEP을 배정한 것은 이 주제가 층·대체물·계약·
회귀라는 네 갈래를 모두 짚어야 이해되기 때문이다. 각 갈래에 세 페이지씩 배분해 상한 15를 채우면
DEEP이 실제로 넓은 경로를 요구하는 시나리오라는 것이 이 사례에서 드러난다.

대체 여덟은 모두 폐쇄가 여덟 이하다. 셋은 정답의 짝이고(5·6·8은 1장의 다른 절), 12·14는 단일 물음과
확인 이름, 19는 대체 착각, 26은 계약 도표, 33은 실행 시간으로 들어가는 첫 페이지다.

무관은 절 단위로 골랐다. 5.5·5.7은 확인 묶음을 운영하며 겪는 문제와 설계 되먹임이고 6장의 셋은 한 기능의 감싸기 진행 기록이다. 이 목적은 층 배치와 계약 검증을
깊이 정리하는 것이라 다섯 다 목적 밖이고, 필수·도움 개념을 primary로 달지 않으며, 정답·대체 어느 페이지도 이들을 선수로 거치지 않는다.

## 재현 조건

1. `python3 build077.py` — 원고와 조각 생성 (PDF SHA 없이 실행하면 자리표시자를 넣는다)
2. `python3 figures077.py pdfbuild077` — 도표 4개 SVG 생성
3. Chrome Headless로 각 SVG를 794×1123 PNG로 렌더링
4. `python3 build_pdf_generic.py 77 7,13,20,26 pdfbuild077` — 조판 HTML 생성
5. Chrome Headless `--print-to-pdf`로 PDF 출력, `pdfcheck.py`로 구성 확인
6. PDF를 `fixtures/content/ai-route-v2/pdfs/`에 두고 SHA-256을 인자로 `build077.py` 재실행
7. `merge_fragments.py 77`로 정본에 병합

## 검수

- 초고 45쪽 가운데 서른아홉 쪽이 344자에 못 미쳐 세 차례에 나눠 마지막 문단에 문장을 더했다.
- 도표 네 장을 PNG로 렌더링해 눈으로 모두 확인했고 p26을 고쳤다. 두 줄짜리 이름표가 **위아래 순서가
  뒤집혀** "본다 / 같은 것을"로 그려져 있었다. 072에서도 같은 실수를 했으므로 두 줄 이름표는 y 값을
  올려 가며 적는다는 것을 기억해 둘 자리다.
- **도표 명세 자체가 어긋난 자리를 하나 고쳤다.** p20의 원고에서 둘째 벌과 셋째 벌의 채움이 같아져
  두 벌을 구분할 수 없었다. 둘째 벌을 '업무 규칙'과 '저장 접근'만 채우는 것으로 바꿔 세 벌이 각각 다른
  범위를 보이게 했다.
- 초고에서 076과 일곱 어절이 겹치는 자리가 둘 나왔다. 1.4의 실패 은폐 문장과 7.4의 점검 마무리
  문장이다. 앞의 것은 이 권의 주제(확인의 수와 기대의 수)에 맞는 문장으로 바꿨고 뒤의 것은 다시 썼다.
- 본문 수정 뒤 PDF를 다시 출력하고 SHA-256과 조각을 함께 갱신했다.
- 공개 가이드 주제와 비공개 분석 텍스트를 서로 다른 문장으로 적었고, 주제문에 숫자를 쓰지 않았다.
  50개 주제문과 50개 분석 텍스트에 중복이 없다.
- 본문·도표·평가 데이터에 실존 인물·작품·단체·제품이 등장하지 않는다.
- **리뷰 뒤 무관 페이지를 다시 골랐다.** 초고는 아홉 권이 모두 6장의 같은 다섯 페이지를
  무관으로 적어 평가 데이터가 권마다 구분되지 않았다. 이 권은 5장의 두 절과 6장의 세 절로
  바꿔 카테고리 안에서 겹치지 않는 세트가 되게 했다. 원고와 PDF는 바뀌지 않았다.
- 리뷰 뒤 7.4·7.7의 공개 주제문을 이 권의 것으로 바꿨다. 초고의 두 문장이 다른 권과 겹쳤다.
- `ContentBatchConverterTest`의 코퍼스 재고 단언을 갱신했다. 도서 57→58, 페이지 2441→2491,
  이미지 272→276이다.

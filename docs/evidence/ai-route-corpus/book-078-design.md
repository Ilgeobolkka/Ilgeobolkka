# book-078 「색인과 실행 계획: 쿼리 성능 진단」 설계

[기술 카테고리 계획](./tech-category-plan.md)의 78번을 만든 근거다. 정책·검증 계약은
[AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)를 따르고, 이 문서는 그 계약 안에서 내린
선택과 이유만 적는다.

## 대상 도서

- `bookId` 78, 카테고리 기술. 저자·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지한다.
- 제목은 `ai-route-v2` manifest의 `books[].title`이 정본이며 계획 문서의 제목과 같다.
- 실존 데이터베이스 제품과 질의 문법을 쓰지 않는다. 저장소·조회·색인·실행 계획처럼 어느 제품에서나
  통하는 말로만 적었고, 6장 사례의 화면과 항목도 일반 업무 용어로만 서술했다.

계획이 정한 범위(색인, 조회 실행 계획, 반복 조회 문제, 데이터 접근 패턴 관찰)가 모두 들어갔다. 평가
시나리오도 계획대로 「비소장 · 예산 10」이다.

## 개념 범위

이 책의 축은 **이 시간이 어디에 쓰이는가**와 **자료가 늘면 어떻게 되는가**다. 앞의 물음이 지금 볼
자리를 정하고(1.3, 3.2, 7.4) 뒤의 물음이 언제 손댈지를 정한다(2.1, 5.5, 7.1). 1.4에서 조회 한 건과
화면 한 장을 가른 것이 4장의 반복 조회 문제로 이어지는 것이 이 권의 뼈대다.

계획이 지정한 카테고리 내부 경계를 지켰다.

- 73(디버깅)이 문제 종류를 가리지 않는 일반 절차를 다루는 데 비해 78은 저장소 조회라는 한 영역에
  한정한다. 재현·최소 사례·이분 탐색은 나오지 않고, 좁히기도 시간 배분과 계획 판독으로만 한다.
- 75(로그)와 겹치지 않도록 5장의 관찰을 로그 설계가 아니라 **느린 조회 수집과 횟수 계측**이라는
  성능 전용 장치로만 다뤘다. 레벨·항목 이름·수집 파이프라인은 나오지 않는다.
- 72(데이터 검증)와 겹치지 않도록 자료의 올바름은 다루지 않고 접근 방식만 다룬다.
- 71·74·76·77·79·80의 소재는 등장하지 않는다.

## 장 구성 (50페이지, 목차 1 + 본문 49)

```
1장 조회가 느리다는 말           p2–8    PREREQUISITE·COUNTERPOINT  응답 시간·분포·시간 배분
2장 저장된 자료를 찾는 방법      p9–15   CORE·COUNTERPOINT  전체 훑기·색인·복합 색인·색인 비용
3장 실행 계획 읽기               p16–22  CORE·COUNTERPOINT  실행 계획·판독·추정 오차·계획 변동
4장 반복 조회 문제               p23–29  CORE·COUNTERPOINT  반복 조회·일괄 조회·캐시 판단·계수
5장 접근 패턴 관찰               p30–36  CORE·COUNTERPOINT  접근 패턴·느린 조회 수집·빈도·환경 차이
6장 느린 화면 하나를 고친 기록   p37–43  EXAMPLE            측정에서 색인 결정까지의 진단 기록
7장 성능 판단 기준               p44–50  COUNTERPOINT·CONCLUSION  우선순위·측정 원칙·점검·균형
```

절은 장마다 일곱 개이고 절 하나가 페이지 하나다. 1.4가 이 권의 매듭이다. 조회 한 건의 성능과 화면 한
장의 성능을 가른 뒤, 그 구분이 4.1의 반복 조회, 4.7의 횟수 계수, 6.2의 진단 전환, 7.4의 점검 첫
항목으로 이어진다.

6장은 앞 다섯 장의 절차를 한 화면에 순서대로 적용한다. 느린 조회 목록에 오르지 않던 문제를 횟수
계측으로 찾아내고, 남은 조회의 계획을 읽어 색인을 정하고, 마지막에는 저장소가 아니라 요구 범위를
조정해 목표를 맞추는 과정을 그대로 적었다.

이미지 5개: p7(시간이 흩어지는 자리), p14(훑기와 색인 찾기), p20(같은 조회의 두 계획),
p26(반복 조회가 늘어나는 모양), p33(조회의 두 갈래 분포). 생성 스크립트는
[`figures078.py`](./tools/figures078.py)다. 이 권만 도표가 다섯인 이유는 성능 개념이 대비 구조로
설명되기 때문이다 — 훑기와 색인, 두 계획, 두 조회 구조, 두 갈래 분포가 모두 짝으로 읽힌다.

이 권의 도표 문장 틀은 "제목 밑에 '…'가 작게 적혀 있다"로 시작하고 "맨 아래 줄에 '…'가 놓여 있다"로
끝난다. 072·073·074·075와 각각 다른 문장을 쓴다. 도표에는 시간과 건수를 눈금으로 넣지 않았다 —
저장소와 자료 크기에 따라 자릿수가 달라 숫자를 넣으면 본문에 없는 기준이 생긴다.

중복 그룹 1개: `measure-before-tuning` = [6, 45]. "재지 않고 고치면 좋아졌는지 알 수 없다"를 1.5에서
진단 절차의 출발로 세우고 7.2에서 성능 작업의 원칙으로 다시 쓴다. 6의 폐쇄는 [2, 4, 6]이고 45의
폐쇄는 [2, 44, 45]라 서로를 지나지 않으며, 1.5를 선수로 삼는 절이 없어 둘을 함께 담는 후보도 없다.

## 선수 관계 설계

1.1이 뿌리이고 1.2·1.3이 곧바로 붙는다. 2장은 1.3 → 2.1에서, 3장은 2.2 → 3.1에서, 4장은
3.1 → 4.1에서, 5장은 4.1 → 5.1에서 시작한다. 3장을 2.1이 아니라 2.2(색인)에 붙인 것은 실행 계획을
읽을 때 색인 개념이 이미 서 있어야 하기 때문이다.

6장은 4.1에 붙였고, 7장은 각 절이 요약하는 장에 직접 붙였다(7.1·7.2는 1.1, 7.3은 2.7, 7.4는 3.2,
7.5는 4.6, 7.6은 1.7, 7.7은 7.2).

- 어느 후보 페이지도 선수 폐쇄가 13페이지를 넘지 않는다.
- 폐쇄 5페이지 이하인 후보 페이지가 네 개 장을 덮는다 (기준 3개 장).
- 후보 페이지 49개 전부가 폐쇄 15페이지 이하다 (기준 75%).

## 검증

`corpus_lib.validate_book()` → `validate_fragment.py` → `merge_fragments.py` → `validate_manifest.py`를
차례로 통과했다.

- 50페이지(48~72), 7개 장(최소 6), 내용 역할 5종 모두 사용
- `TEXT` 본문 44페이지가 345~406자(평균 363자, 합계 16,015자)
- `estimatedReadingSeconds`에 60초로 눌린 페이지가 하나도 없음
- `FRONT_MATTER`(목차 p1)와 `aiRouteCandidatePage=false`가 정확히 일치
- PDF 페이지 50개, 텍스트 45개, 이미지 5개(p7,14,20,26,33) — `pdfcheck.py`로 확인
- PDF 실제 SHA-256이 manifest의 `pdfSha256`과 일치 (704,571 bytes)
- 다른 권과 겹치는 일곱 어절이 하나도 없다

## 평가 케이스: 비소장·예산 10 시나리오

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-078` |
| `purpose` | 조회가 느린 원인을 어디서부터 봐야 할지 몰라서, 색인과 실행 계획과 반복 조회를 넓게 훑어보고 싶다 |
| `owned` / `maxAdditionalInk` / `depth` | `false` / `10` / `null` |
| `requiredConcepts` | 응답 시간, 전체 훑기, 색인, 실행 계획, 반복 조회, 접근 패턴 |
| `helpfulConcepts` | 시간 배분, 색인 구조, 계획 판독, 목록 조회 |
| `referencePageNumbers` | 2, 4, 9, 10, 11, 16, 17, 23, 24, 30 |
| `allowedAlternativePageNumbers` | 3, 5, 6, 12, 13, 18, 25, 31 |
| `irrelevantPageNumbers` | 38·39·40(횟수 측정·반복 제거·계획 확인), 42·43(개선 확인·후속 관찰) |

정답 경로는 선수 폐쇄와 같고 열 페이지여서 예산 10을 정확히 채운다. 1.1 → 1.3의 도입에서 2장(전체
훑기 → 색인 → 색인 구조), 3장(실행 계획 → 계획 판독), 4장(반복 조회 → 목록 조회), 5장(접근 패턴)으로
갈라지는 모양이다. 필수 개념 여섯이 각 갈래의 첫 페이지에 하나씩 놓인다.

**같은 예산 10을 071과 다른 모양으로 채웠다.** 071은 여덟 페이지를 골라 여유를 남겼고 078은 열
페이지로 상한을 채운다. 예산이 같아도 경로를 여유 있게 잡을 때와 꽉 채울 때 대체 페이지의 폐쇄
상한이 어떻게 달라지는지가 두 사례에서 나란히 드러난다.

대체 여덟은 모두 폐쇄가 여덟 이하라 예산 안에서 갈아 끼울 수 있다. 셋은 정답의 짝이고(3·5·6은
1장의 다른 절), 12·13은 색인 미사용과 복합 색인, 18은 추정 오차, 25는 일괄 조회, 31은 느린 조회
수집으로 들어가는 첫 페이지다.

무관은 절 단위로 골랐다. 6장의 다섯 페이지는 한 화면의 진단 진행 기록이고, 이 목적은 사례가 아니라
넓게 훑는 것이다. 다섯 다 필수·도움 개념을 primary로 달지 않고, 정답·대체 어느 페이지도 이들을
선수로 거치지 않는다. 6.1(느린 화면의 증상)과 6.5(색인을 정한 과정)는 개념 설명 비중이 커 무관에서
뺐다.

## 재현 조건

1. `python3 build078.py` — 원고와 조각 생성 (PDF SHA 없이 실행하면 자리표시자를 넣는다)
2. `python3 figures078.py pdfbuild078` — 도표 5개 SVG 생성
3. Chrome Headless로 각 SVG를 794×1123 PNG로 렌더링
4. `python3 build_pdf_generic.py 78 7,14,20,26,33 pdfbuild078` — 조판 HTML 생성
5. Chrome Headless `--print-to-pdf`로 PDF 출력, `pdfcheck.py`로 구성 확인
6. PDF를 `fixtures/content/ai-route-v2/pdfs/`에 두고 SHA-256을 인자로 `build078.py` 재실행
7. `merge_fragments.py 78`로 정본에 병합

## 검수

- 초고 44쪽 가운데 마흔한 쪽이 344자에 못 미쳐 `estimatedReadingSeconds`가 60초로 눌렸다. 두 차례에
  나눠 각 쪽 마지막 문단에 한 문장씩 더해 345~406자로 맞췄다.
- 도표 다섯 장을 PNG로 렌더링해 눈으로 모두 확인했고 p33을 고쳤다. '느리지만 드물다' 이름표가 오른쪽
  아래 동그라미들과 겹쳐 위로 옮겼다.
- 도표에 맞춰 본문 설명 한 곳을 고쳤다. p20은 막대가 상자 '옆'이 아니라 '아래'에 붙는다.
- 초고에서 075와 일곱 어절이 겹치는 자리가 하나 나왔다. 점검 항목의 마무리 문장이라 다시 썼다.
- 본문 수정 뒤 PDF를 다시 출력하고 SHA-256과 조각을 함께 갱신했다.
- 공개 가이드 주제와 비공개 분석 텍스트를 서로 다른 문장으로 적었고, 주제문에 숫자를 쓰지 않았다.
  50개 주제문과 50개 분석 텍스트에 중복이 없다.
- 본문·도표·평가 데이터에 실존 인물·작품·단체·제품이 등장하지 않는다.
- `ContentBatchConverterTest`의 코퍼스 재고 단언을 갱신했다. 도서 55→56, 페이지 2341→2391,
  이미지 263→268이다(이 권은 도표가 다섯이라 넷이 아니라 다섯이 는다).

# book-080 「배포 절차와 단계적 릴리스」 설계

[기술 카테고리 계획](./tech-category-plan.md)의 80번을 만든 근거다. 정책·검증 계약은
[AI 경로 콘텐츠 코퍼스](../../ai-route-content-corpus.md)를 따르고, 이 문서는 그 계약 안에서 내린
선택과 이유만 적는다. 기술 카테고리의 마지막 권이다.

## 대상 도서

- `bookId` 80, 카테고리 기술. 저자·소개는 `src/main/resources/demo/books.json`의 기존 값을 유지한다.
- 제목은 `ai-route-v2` manifest의 `books[].title`이 정본이며 계획 문서의 제목과 같다.
- 실존 배포 도구·서비스 이름을 쓰지 않는다. '내보내기', '점검표', '되돌리기'처럼 절차 이름으로만
  적었고, 6장 사례의 변경도 일반 업무 용어로만 서술했다.

계획이 정한 범위(배포 전 점검 항목, 단계적 배포, 상태 확인, 배포 후 관찰 준비)가 모두 들어갔다.
평가 시나리오도 계획대로 「소장 · DEEP」이다.

## 개념 범위

이 책의 축은 **이번에 무엇이 바뀌는가**와 **잘못되면 어떻게 되돌리는가**다. 앞의 물음이 절차의 무게를
정하고(1.2, 1.3) 뒤의 물음이 나눌 자리를 정한다(2.4, 3.1, 7.1). 되돌릴 수 있는 상태를 유지하는 것이
점검·단계·확인·관찰 네 장을 관통하는 하나의 원칙이고, 7.2가 그것을 명시한다.

계획이 지정한 카테고리 내부 경계를 지켰다.

- 76(기본값과 실패 경계)이 코드 안의 실패 경계를 다루는 데 비해 80은 배포라는 조직적 절차의 점검
  항목을 다룬다. 상한·재시도·점진적 저하는 나오지 않고, 3장의 단계 나누기도 실행 중 부하가 아니라
  공개 범위의 문제다.
- 77(테스트)과 겹치지 않도록 배포 전 확인을 시험 전략이 아니라 **점검표의 항목**으로만 다뤘다.
  2.3에서 기계 확인을 언급하되 그 내용은 다루지 않는다.
- 75(로그)와 겹치지 않도록 5장의 관찰을 로그 설계가 아니라 배포 판단에 쓰는 지표와 기록으로만
  적었다.
- 71·72·73·74·78·79의 소재는 등장하지 않는다.

## 장 구성 (50페이지, 목차 1 + 본문 49)

```
1장 배포라는 일                    p2–8    PREREQUISITE·COUNTERPOINT  변경 범위·되돌리기·단위·빈도
2장 배포 전 점검                   p9–15   CORE·COUNTERPOINT  점검표 구성·확인 주체·복구 계획·형식화
3장 단계적 배포                    p16–22  CORE·COUNTERPOINT  부분 공개·병행 운영·기능 전환·롤백
4장 상태 확인                      p23–29  CORE·COUNTERPOINT  상태 점검·준비와 생존·성공과 실패 기준
5장 배포 뒤 관찰                   p30–36  CORE·COUNTERPOINT  관찰 준비·기간·배포 표시·지연 발현
6장 한 배포를 나눠 진행한 기록     p37–43  EXAMPLE            저장 구조 변경을 세 단계로 나눈 기록
7장 배포 판단                      p44–50  COUNTERPOINT·CONCLUSION  분할 정도·복구 가능성·점검·절차
```

절은 장마다 일곱 개이고 절 하나가 페이지 하나다. 1.3이 이 권의 매듭이다. 되돌릴 수 있는지가 절차의
무게를 정한다는 규정이 2.4의 복구 계획, 2.6의 저장 구조 순서, 3.1의 단계 나누기, 7.1의 분할 정도로
이어진다.

6장은 앞 다섯 장의 절차를 한 배포에 적용한다. 저장 구조를 먼저 올리고, 코드를 꺼진 채로 올리고,
일부에게 켠 뒤 기준에 걸려 되돌리고, 자료를 채운 뒤 다시 켜고, 관찰 중에 주기 처리에서 문제를 찾는
과정을 그대로 적었다.

이미지 4개: p7(한 번의 배포가 지나는 단계), p13(배포 전 점검표), p20(단계적 배포의 진행),
p26(배포 직후에 보는 것들). 생성 스크립트는 [`figures080.py`](./tools/figures080.py)다.

이 권의 도표 문장 틀은 "제목 밑 한 줄에 '…'가 있다"로 시작하고 "그림의 맨 아래에는 '…'가 적혀 있다"로
끝난다. 072·073·074·075·076·077·078·079와 각각 다른 문장을 쓴다. 도표에는 시간과 비율을 눈금으로
넣지 않았다 — 알맞은 값은 서비스마다 달라 숫자를 넣으면 본문에 없는 기준이 생긴다.

중복 그룹 1개: `rollback-is-the-plan` = [21, 45]. "되돌리기는 실패가 아니라 준비된 선택이다"를
3.6에서 절차의 일부로 세우고 7.2에서 책 전체의 원칙으로 다시 쓴다. 21의 폐쇄는 [2, 4, 9, 16, 18, 21]
이고 45의 폐쇄는 [2, 4, 9, 16, 44, 45]라 서로를 지나지 않으며, 3.6을 선수로 삼는 절이 없어 둘을 함께
담는 후보도 없다.

## 선수 관계 설계

1.1이 뿌리이고 1.2·1.3이 곧바로 붙는다. 2장은 1.3 → 2.1에서, 3장은 2.1 → 3.1에서, 4장은
3.1 → 4.1에서, 5장은 4.1 → 5.1에서 시작한다. 절차가 점검 → 나누기 → 확인 → 관찰의 순서로 이어지는
한 줄기라 각 장의 첫 절만 앞 장에 붙였다.

6장은 3.1에 붙였고, 7장은 각 절이 요약하는 장에 직접 붙였다(7.1·7.2는 3.1, 7.3은 2.7, 7.4는 4.5,
7.5는 5.7, 7.6은 2.3, 7.7은 7.2).

- 어느 후보 페이지도 선수 폐쇄가 11페이지를 넘지 않는다.
- 폐쇄 5페이지 이하인 후보 페이지가 여섯 개 장을 덮는다 (기준 3개 장).
- 후보 페이지 49개 전부가 폐쇄 15페이지 이하다 (기준 75%).

## 검증

`corpus_lib.validate_book()` → `validate_fragment.py` → `merge_fragments.py` → `validate_manifest.py`를
차례로 통과했다.

- 50페이지(48~72), 7개 장(최소 6), 내용 역할 5종 모두 사용
- `TEXT` 본문 45페이지가 345~377자(평균 359자, 합계 16,171자)
- `estimatedReadingSeconds`에 60초로 눌린 페이지가 하나도 없음
- `FRONT_MATTER`(목차 p1)와 `aiRouteCandidatePage=false`가 정확히 일치
- PDF 페이지 50개, 텍스트 46개, 이미지 4개(p7,13,20,26) — `pdfcheck.py`로 확인
- PDF 실제 SHA-256이 manifest의 `pdfSha256`과 일치 (656,399 bytes)
- 다른 권과 겹치는 일곱 어절이 하나도 없다

## 평가 케이스: 소장·DEEP 시나리오

| 필드 | 값 |
| --- | --- |
| `caseId` | `case-book-080` |
| `purpose` | 이 책을 소장하고 있는데, 올리기 전 점검부터 나눠 여는 방법과 올린 뒤 관찰까지 배포 절차 전체를 깊이 정리하고 싶다 |
| `owned` / `maxAdditionalInk` / `depth` | `true` / `null` / `DEEP` |
| `requiredConcepts` | 배포, 되돌리기, 배포 전 점검, 단계적 배포, 배포 상태 확인, 배포 후 관찰 |
| `helpfulConcepts` | 변경 범위, 점검표 구성, 부분 공개, 병행 운영, 관찰 기간 |
| `referencePageNumbers` | 2, 3, 4, 9, 10, 11, 12, 16, 17, 18, 23, 24, 30, 31, 32 |
| `allowedAlternativePageNumbers` | 5, 6, 13, 14, 19, 25, 27, 33 |
| `irrelevantPageNumbers` | 34(사용자 신고), 38·40·42·43(첫 단계·부분 공개 결과·관찰 결과·절차 개선) |

정답 경로는 선수 폐쇄와 같고 열다섯 페이지여서 DEEP 상한 15를 정확히 채운다. 1장의 도입 셋에서
2장 넷(점검·구성·주체·복구 계획), 3장 셋(단계·부분 공개·병행), 4장 둘, 5장 셋으로 갈라진다. 2장에
가장 많은 페이지를 배분한 것은 배포 절차에서 미리 정할 것이 점검 단계에 몰려 있기 때문이다.

**77과 함께 카테고리의 두 DEEP 사례를 이룬다.** 77은 네 갈래에 세 페이지씩 고르게 나눴고 80은 2장에
넷을 몰아 배분했다. 같은 상한 15에서도 개념의 무게가 어디에 실리느냐에 따라 경로 모양이 달라진다는
것을 두 권이 나란히 보인다.

대체 여덟은 모두 폐쇄가 여덟 이하다. 둘은 정답의 짝이고(5·6은 1장의 다른 절), 13·14는 점검표 도표와
저장 구조 변경, 19는 기능 전환, 25는 준비와 생존, 27은 성공 기준, 33은 지연 발현으로 들어가는 첫
페이지다.

무관은 절 단위로 골랐다. 5.5는 사용자 신고라는 관찰 보조 통로이고 6장의 넷은 한 배포의 진행 기록이다. 이 목적은 절차 전체를 정리하는 것이라 다섯 다 목적 밖이고,
필수·도움 개념을 primary로 달지 않으며, 정답·대체 어느 페이지도 이들을 선수로 거치지 않는다.

## 재현 조건

1. `python3 build080.py` — 원고와 조각 생성 (PDF SHA 없이 실행하면 자리표시자를 넣는다)
2. `python3 figures080.py pdfbuild080` — 도표 4개 SVG 생성
3. Chrome Headless로 각 SVG를 794×1123 PNG로 렌더링
4. `python3 build_pdf_generic.py 80 7,13,20,26 pdfbuild080` — 조판 HTML 생성
5. Chrome Headless `--print-to-pdf`로 PDF 출력, `pdfcheck.py`로 구성 확인
6. PDF를 `fixtures/content/ai-route-v2/pdfs/`에 두고 SHA-256을 인자로 `build080.py` 재실행
7. `merge_fragments.py 80`로 정본에 병합. 이미 병합한 뒤에 다시 만들 때는
   [도구 README의 되돌리기 절차](./tools/README.md#이미-병합한-도서를-다시-만들-때)를 먼저 따른다

## 검수

- 초고 45쪽 대부분이 344자에 못 미쳐 네 차례에 나눠 마지막 문단에 문장을 더했다. 345~377자로 맞췄다.
- 도표 네 장을 PNG로 렌더링해 눈으로 모두 확인했고 p26을 고쳤다. 맨 아래 점선 칸이 마무리 선과 겹쳐
  선을 아래로 내렸다.
- 초고에서 072·074·077과 일곱 어절이 겹치는 자리가 셋 나왔다. 도표 도입 문장 둘과 점검 항목 마무리
  문장이다. **교체 스크립트가 한 자리에서 실패했는데 그대로 병합까지 진행해, 겹침이 남은 판이 한 번
  정본에 들어갔다.** 문구를 고친 뒤 fixture를 되돌리고 다시 병합해 바로잡았다. 여러 명령을 한 줄로
  이을 때는 앞 단계 실패가 뒤 단계를 멈추게 해야 한다.
- 공개 가이드 주제와 비공개 분석 텍스트를 서로 다른 문장으로 적었고, 주제문에 숫자를 쓰지 않았다.
  50개 주제문과 50개 분석 텍스트에 중복이 없다.
- 본문·도표·평가 데이터에 실존 인물·작품·단체·제품이 등장하지 않는다.
- **리뷰 뒤 무관 페이지를 다시 골랐다.** 초고는 아홉 권이 모두 6장의 같은 다섯 페이지를
  무관으로 적어 평가 데이터가 권마다 구분되지 않았다. 이 권은 5장의 두 절과 6장의 세 절로
  바꿔 카테고리 안에서 겹치지 않는 세트가 되게 했다. 원고와 PDF는 바뀌지 않았다.
- 리뷰 뒤 7.7의 공개 주제문을 이 권의 것으로 바꿨다. 초고는 아홉 권이 같은 문장을 썼다.
- `ContentBatchConverterTest`의 코퍼스 재고 단언을 갱신했다. 도서 59→60, 페이지 2541→2591,
  이미지 280→284다.

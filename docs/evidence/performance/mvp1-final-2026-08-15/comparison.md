제품 성능 회귀·개선 판정에 사용하지 않는다. 전송량과 cache header는 같은 도구·경로·context에서 직접
비교 가능한 근거다.

## 남은 병목과 다음 용량 한계

1. 공개 정적 자산은 warm 탐색에도 329,581 bytes를 모두 재전송한다. 보호 콘텐츠의 `private, no-store`를
   유지하면서 fingerprinted 공개 자산에만 장기 cache를 적용하는 것이 다음 1순위 개선이다. 계획상 기대는
   공개 전송 bytes 20~70%와 LCP 10~30% 개선이며, 실제 채택은 같은 browser 조건의 반복 측정으로 판정한다.
2. 로그인 BCrypt는 CPU 집중 지점이지만 중복 호출이 없는 정상 보안 비용이다. strength를 낮추지 않는다.
3. 현재 첫 번째 포화 자원은 **확인되지 않았다**. Stress의 계획 상한 200 flow/s에서 앱 CPU 평균 17.16%,
   Hikari pending 0, Tomcat busy 최대 3, generator CPU 최대 4.18%였다. 확인된 다음 용량 경계는 특정
   resource가 아니라 “200 flow/s보다 높은 미측정 구간”이다. 실제 사용자 트래픽 분포가 생기기 전에는
   더 높은 숫자만 탐색하지 않는다.

## 단정적 최종 판정

- **현재 첫 번째 용량 한계:** 계획한 200 flow/s 안에서는 특정 자원 포화를 확인하지 못했다. 다음 한계는
  200 flow/s 초과 미측정 구간이며 무한 용량을 뜻하지 않는다.
- **잠정 품질 게이트:** 통과. 유효 Average·Peak·Stress·Spike·Soak와 동시성 4종에서 기능·오류·dropped·
  Hikari·도메인 불변식 게이트를 모두 만족했다.
- **기준선 대비 변화:** Average p95 4.4%, p99 0.6% 개선, 실제 HTTP RPS 0.014% 증가다. Peak p95 3.3%,
  p99 7.5% 악화, RPS 0.0002% 감소다. Stress RPS는 0.011% 감소했다. 모두 고정 arrival rate의 변동
  범위이며 지속 처리량 1.5배 증거가 아니다.
- **Redis:** Caffeine 효과와 다중 인스턴스 공유 필요가 모두 없어 제외했다.
- **다중 인스턴스·Spring Session Redis:** 단일 앱 포화와 배포 요구가 없어 제외했고 기존 세션 구조를
  유지했다.
- **가상 스레드:** 큰 I/O 대기 근거가 없고 Hikari pending도 0이어서 제외했다.
- **Kafka:** 채택 게이트가 없고 원자 동기 업무 경로의 순서·재시도·멱등 운영 비용만 늘려 제외했다.
- **운영 해석 금지:** 단일 개발자 호스트의 Docker Desktop 자원 제한, 합성 `mvp` 데이터와 고정 비율,
  비활성 외부 서비스, 짧은 측정 창에는 실제 운영의 동시 사용자·네트워크·AZ·RDS·장애·장기 데이터 성장·
  배포 변동이 포함되지 않았다.
- **다음 1순위:** fingerprinted 공개 정적 자산 cache를 프론트엔드 범위에서 실험한다. 예상 효과는 전송
  bytes 20~70%, LCP 10~30% 개선이며 보호 콘텐츠 `private, no-store`는 유지한다.

성능 목표는 “30% 지연 단축 또는 1.5배 지속 처리량 증가”로는 달성하지 못했다. 그러나 기준선이 이미
정확성·잠정 지연 게이트를 만족했고 근거 없는 상태 인프라를 추가하지 않았으므로 Runbook의 대체 완료 판정인
**기준선 충족으로 단순 구성 유지**에 해당한다.

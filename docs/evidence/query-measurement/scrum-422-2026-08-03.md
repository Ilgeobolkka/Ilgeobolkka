# SCRUM-422 핵심 경로 쿼리 측정 근거

> 도서 목록·페이지 열기·서재의 쿼리 수·파사드 처리 시간을 실제 MySQL 8.4에서 측정해 명백한 N+1
> 유무를 근거로 확인합니다. 측정 코드는
> `src/test/java/com/example/ilgeobolkka/perf/CoreQueryMeasurementMySqlIntegrationTest.java`입니다.

## 실행 조건

- 실행일: 2026-08-03 KST
- 데이터베이스: Compose `mysql:8.4`, `docker compose up -d --wait`의 healthy 상태
- 런타임: Java 21.0.11, Spring `test` 프로필
- 측정 방법: `EntityManagerFactory` → `SessionFactory.getStatistics()`의
  `getPrepareStatementCount()`로 파사드(BookFacade, LibraryFacade, ReadingFacade) 호출당
  실제 JDBC 쿼리 수를 집계. "파사드 처리 시간"은 같은 호출만 감싼 `System.nanoTime()` 경과
  시간이며, 컨트롤러·시큐리티·직렬화를 포함한 HTTP API 응답 시간이 아닙니다
- 데이터 규모: 도서 100권(고정 카테고리 5종 순환), 서재 30건(소장 10·활성 대여 10·만료 대여 10).
  도서 목록 측정은 이 100권의 제목에만 있는 키워드로 조회를 격리해, 오래 쓴 `_test` DB에 남은 다른
  테스트 데이터가 섞여도 "100권 중" 조건이 깨지지 않게 했습니다(격리 전에는 크기만 비어 있지 않은지
  검사해 다른 행이 섞여도 통과할 수 있었습니다)

## 측정 결과

| 경로 | 쿼리 수 | 파사드 처리 시간 |
| --- | ---: | ---: |
| 도서 목록 1페이지(100권 중) | 2건 | 2ms |
| 도서 목록 2페이지(100권 중) | 2건 | 10ms |
| 서재 조회(30건) | 1건 | 13ms |
| 페이지 열기(신규 대여) | 14건 | 97ms |

## 판정

도서 목록은 `BookRepository.findByKeyword` 한 번 호출로 처리되지만, `@Query`에 선언한
`countQuery`가 함께 실행되어 컨텐츠·카운트 쿼리 2건이 나갑니다(`countByKeyword`는 오프셋이
`Integer.MAX_VALUE`를 넘는 예외 경로에서만 별도로 쓰이며 이번 측정에는 관여하지 않습니다). 서재
조회는 `LibraryEntryRepository.findEntriesByReaderId` native SQL 한 문장으로 처리되어 100권·30건
규모에서도 쿼리 수가 늘지 않았습니다. 페이지 열기의 14건은 소장 확인 → 활성 대여 확인 → 잉크 계정
잠금 → 재확인 → 신규 대여·차감·서재 기록이라는 정책상 고정된 순서(`ReadingFacade#openPage`)에서
나온 것으로, 이 역시 데이터 규모와 무관합니다.

세 경로 모두 데이터 규모와 무관한 고정 쿼리 수를 보여 **명백한 N+1은 확인되지 않았고, 그에 따라
별도 코드 보정은 하지 않았습니다.** 각 측정에는 이 쿼리 수 상한을 그대로 회귀 assertion으로 걸어
두어, 향후 N+1이 도입되면 테스트가 실패하도록 했습니다.

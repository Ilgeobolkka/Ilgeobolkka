# SCRUM-422 핵심 경로 쿼리 측정 근거

> 도서 목록·페이지 열기·서재의 쿼리 수·응답 시간을 실제 MySQL 8.4에서 측정해 명백한 N+1 유무를
> 근거로 확인합니다. 측정 코드는
> `src/test/java/com/example/ilgeobolkka/perf/CoreQueryMeasurementMySqlIntegrationTest.java`입니다.

## 실행 조건

- 실행일: 2026-08-03 KST
- 데이터베이스: Compose `mysql:8.4`, `docker compose up -d --wait`의 healthy 상태
- 런타임: Java 21.0.11, Spring `test` 프로필
- 측정 방법: `EntityManagerFactory` → `SessionFactory.getStatistics()`의
  `getPrepareStatementCount()`로 파사드(BookFacade, LibraryFacade, ReadingFacade) 호출당
  실제 JDBC 쿼리 수를 집계. 응답 시간은 같은 호출을 감싼 `System.nanoTime()` 측정
- 데이터 규모: 도서 100권(고정 카테고리 5종 순환), 서재 30건(소장 10·활성 대여 10·만료 대여 10)

## 측정 결과

| 경로 | 쿼리 수 | 응답 시간 |
| --- | ---: | ---: |
| 도서 목록 1페이지(100권 중) | 2건 | 2ms |
| 도서 목록 2페이지(100권 중) | 2건 | 10ms |
| 서재 조회(30건) | 1건 | 13ms |
| 페이지 열기(신규 대여) | 14건 | 97ms |

## 판정

도서 목록과 서재 조회는 모두 native SQL 단일·이중 쿼리(`BookRepository.findByKeyword`+
`countByKeyword`, `LibraryEntryRepository.findEntriesByReaderId`)로 처리되어 100권·30건 규모에서도
쿼리 수가 늘지 않았습니다. 페이지 열기의 14건은 소장 확인 → 활성 대여 확인 → 잉크 계정 잠금 →
재확인 → 신규 대여·차감·서재 기록이라는 정책상 고정된 순서(`ReadingFacade#openPage`)에서 나온
것으로, 이 역시 데이터 규모와 무관합니다.

세 경로 모두 데이터 규모와 무관한 고정 쿼리 수를 보여 **명백한 N+1은 확인되지 않았고, 그에 따라
별도 코드 보정은 하지 않았습니다.** 각 측정에는 이 쿼리 수 상한을 그대로 회귀 assertion으로 걸어
두어, 향후 N+1이 도입되면 테스트가 실패하도록 했습니다.

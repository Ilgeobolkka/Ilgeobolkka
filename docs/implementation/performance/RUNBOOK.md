# MVP1 성능 측정·개선 순차 실행 Runbook

[성능 실행 계획](./README.md)으로 돌아갑니다. 이 문서는 계획의 수치·정책을 다시 정의하지 않고, 사람과
AI가 한 단계씩 실행하고 검증하기 위한 순서와 인계 규칙만 제공합니다. 계획과 이 문서가 다르면 계획을
우선하고, 어느 문서를 고칠지 사용자에게 확인합니다.

## 1. 완료 상태

다음 상태가 모두 확인돼야 이 runbook을 완료한 것입니다.

- 성능 계획의 완료 기준 10개가 각각 실제 근거와 연결됐습니다.
- 기준선과 최종 결과가 비교 대상 코드 변경 외에는 동일한 데이터·환경·워밍업 조건으로 비교됐고, 각
  코드와 JAR의 SHA-256이 기록됐습니다.
- 캐시와 JVM·DB 워밍업으로 뒤 실행이 빨라지는 효과가 cold와 warm 결과로 분리됐습니다.
- 모든 코드 변경에 대응 테스트가 있고 `test`, `check`, `build`, 패키징 애플리케이션 smoke가 통과했습니다.
- 잉크·원장·대여·소장·세션 불변식이 부하 뒤에도 유지됩니다.
- 실행 명령, 실패, 생략, 채택·폐기 근거와 큰 원시 artifact의 위치·SHA-256이 기록됐습니다.
- 커밋·push·PR 수정은 실행 결과와 별개의 승인으로 남아 있습니다.

성능 목표 수치에 도달하지 못해도 측정과 판정이 정확하면 runbook 실행은 끝낼 수 있습니다. 다만 그 결과를
“성능 목표 달성”으로 표현하지 않고, 미달 지표와 현재 첫 번째 용량 한계를 최종 보고서에 적습니다.

## 2. 사용하는 방법

사람은 아래 단계의 `AI에게 전달할 요청문`을 순서대로 대화창에 전달합니다. AI는 요청받은 단계만 실행하고,
종료 조건을 검증해 보고한 뒤 다음 단계로 넘어가지 않고 멈춥니다.

1. 처음에는 0단계만 요청합니다.
2. AI가 출력한 `사람 선행 준비 체크리스트`를 사람이 모두 처리합니다.
3. 사람은 “준비 완료”라고 답합니다. AI는 말만 믿지 않고 확인 가능한 항목을 직접 검증한 뒤 1단계를
   실행합니다.
4. 실행 중 AI가 직접 할 수 없는 일이 새로 생기면 AI가 이유·정확한 범위·확인 방법을 한 번에 요청하고
   멈춥니다. 사람이 완료했다고 답하면 AI가 검증한 뒤 같은 단계를 이어서 실행합니다.
5. 각 단계의 종료 보고를 사람이 확인한 뒤 다음 단계만 명시적으로 요청합니다.

AI가 터미널·파일·Git·로컬 브라우저 도구로 할 수 있는 일을 사람에게 대신 실행해 달라고 요청하지 않습니다.
사람의 역할은 물리적 환경 준비, 비밀값의 안전한 입력, 비용·권한·새 의존성·구조 변경 승인처럼 AI가
독자적으로 할 수 없거나 하면 안 되는 일로 제한합니다.

## 3. 역할과 승인 경계

| 작업 | AI | 사람 |
| --- | --- | --- |
| 저장소·문서·코드·환경 읽기 | 직접 수행 | 결과 확인 |
| 파일 수정, 로컬 명령, 테스트, 부하 실행 | 승인된 범위에서 직접 수행 | 장시간 실행 시간 확보 |
| `.env`의 비밀값 | 변수 존재 여부만 확인하고 값을 출력하지 않음 | Git 제외 파일이나 관리 화면에 직접 입력 |
| 새 Java 의존성·컨테이너 이미지 | 좌표·용도·버전 관리 방식과 image tag·digest를 제안하고 대기 | 추가 승인 또는 거부 |
| 전용 성능 DB·볼륨 초기화 | 정확한 대상과 삭제 범위를 재확인하고 실행 | 보존할 데이터가 없음을 확인 |
| 유료 클라우드·외부 계정·운영 데이터 | 이번 runbook 범위 밖으로 보고하고 실행하지 않음 | 별도 계획에서 결정 |
| 제품 정책·대규모 리팩터링·기존 죽은 코드 삭제 | 실행하지 않고 대안과 영향 보고 | 별도 결정 |
| ADR 작성·대체 | `adr` 스킬로 초안을 작성하되 채택 범위를 명시 | 되돌리기 비싼 결정 승인 |
| 커밋·push·PR 수정·merge | 각각 별도 요청 전 실행 금지 | 각각 별도 승인 |

다음 작업은 승인으로 묶지 않습니다. 예를 들어 새 의존성을 승인했다고 커밋·push까지 승인된 것이 아니며,
단계 진행을 승인했다고 유료 자원 생성이나 운영 데이터 접근까지 승인된 것도 아닙니다.

## 4. 모든 단계에 적용하는 실행 규칙

### 4.1 단계 시작 보고

AI는 매 단계 시작 시 다음을 먼저 대화창에 출력합니다.

```text
단계: <번호와 이름>
완료 기준: <한 문장>
브랜치 / HEAD / upstream: <현재 값>
작업 트리: <clean 또는 변경 파일 요약>
실행 환경: <로컬 Compose, 성능 DB, 애플리케이션 실행 방식>
이번 단계에서 하지 않는 일: <다음 단계·조건부 작업·GitHub 변경>
```

작업 트리가 예상과 다르면 기존 변경의 소유자를 추측하거나 덮어쓰지 않고 중단해 보고합니다. `git reset
--hard`, 강제 checkout, 광범위한 `git clean`으로 맞추지 않습니다.

### 4.2 사람에게 작업을 요청하는 형식

AI가 직접 완료할 수 없는 항목이 있으면 흩어서 묻지 말고, 현재 단계에서 미리 알 수 있는 항목을 다음
형식으로 모아 출력합니다.

```text
사람 작업이 필요합니다. 아직 다음 작업을 실행하지 않았습니다.

- [ ] 해야 할 일: <사람만 할 수 있는 정확한 작업>
  이유: <왜 필요한지>
  민감정보 경계: <채팅·Git에 넣지 않을 값>
  AI 확인 방법: <완료 답변 뒤 AI가 직접 확인할 비민감 상태>

완료 후 비밀값을 붙이지 말고 “준비 완료”라고 답해주세요.
```

사람이 완료했다고 답하면 AI는 파일 존재, 변수명 설정 여부, 서비스 상태, 권한 상태처럼 비민감 사실만
확인합니다. 확인에 실패하면 원문 오류와 한국어 해석을 보고하고 같은 요청을 반복하지 말고 대안을 찾습니다.

### 4.3 단계 종료 보고

AI는 종료 조건을 직접 확인한 뒤 다음 형식으로 보고하고 멈춥니다.

```text
단계 결과: 통과 / 조건부 통과 / 실패
종료 조건 검증: <항목별 근거>
생성·수정한 파일: <범위>
실행한 명령과 결과: <테스트 수, 부하 실행 수, 실패 포함>
보존한 근거: <저장소 경로 또는 artifact 위치·SHA-256>
생략한 검증과 이유: <없으면 없음>
남은 위험·결정: <없으면 없음>
다음 단계: <번호와 이름> — 아직 실행하지 않음
```

오류율이나 지연 게이트 미달은 숨기지 않습니다. 기준선 단계는 측정 근거가 완전하면 품질 게이트가
미달이어도 완료할 수 있지만, 최종 단계는 “runbook 실행 완료”와 “성능 목표 달성”을 분리해 판정합니다.

### 4.4 측정 공통 규칙

- 모든 정식 결과에 Git SHA, dirty 상태, JAR SHA-256, 버전, 호스트 자원, JVM·Tomcat·Hikari 설정,
  데이터 입력, 시작·종료 UTC를 기록합니다.
- 성능 DB 이름이 정확히 `ilgeobolkka_perf`인지 확인하고 `_test`, 개발·시연·운영 DB면 초기화를
  거부합니다.
- Compose를 사용하면 성능 전용 project와 volume 이름을 먼저 해석해 출력하고, 다른 project의 volume을
  삭제하지 않습니다.
- PortOne·OpenAI 외부 서비스에는 부하를 보내지 않습니다. 결제 경로가 필요하면 승인된 로컬 fake 또는
  stub만 사용합니다.
- 각 VU는 독립 cookie jar를 사용하고 CSRF·인가·세션 정책을 우회하지 않습니다.
- 워밍업 요청은 정식 통계에서 제외하고, cold와 warm 결과를 한 평균으로 합치지 않습니다.
- Average·Peak 3회는 매회 같은 업무 데이터와 애플리케이션 캐시 출발점으로 복원하고 같은 워밍업을
  수행합니다.
- 애플리케이션 cache off/on 비교에서는 DB buffer pool과 JVM JIT 상태를 같게 유지합니다. MySQL cold
  buffer pool 결과는 별도 진단으로만 기록합니다.
- Caffeine은 애플리케이션 재시작으로 비우고 Redis는 성능 전용 namespace만 초기화합니다. `FLUSHALL`은
  사용하지 않습니다.
- 브라우저는 새 context의 cold cache와 같은 경로 반복의 warm cache를 분리합니다. 보호 콘텐츠의
  `private, no-store`가 warm cache에 남으면 성능 개선이 아니라 계약 위반으로 판정합니다.
- 관측 on/off 오버헤드 측정과 JFR 진단 실행을 정식 3회 결과에 섞지 않습니다.
- 한 후보 실험에서는 독립 변수 하나만 바꿉니다.

## 5. 단계 상태표

이 표는 문서 자체의 진행 상태 정본이 아닙니다. 실제 진행 상태와 증거는 기준선·최종 evidence 폴더에
기록합니다.

| 단계 | 목적 | 다음 단계 진입 조건 |
| --- | --- | --- |
| 0 | 읽기 전용 사전 점검과 사람 준비 일괄 요청 | 준비 항목 검증 완료 |
| 1 | 측정 장치와 재현 환경 구현 | smoke·보안·구성·전체 빌드 게이트 통과 |
| 2 | 기준선과 병목 확정 | 같은 조건 3회 근거와 병목 목록 보존 |
| 3 | 새 상태 인프라 없는 1차 개선 | 후보별 채택·폐기 근거와 결합 검증 완료 |
| 4 | 조건부 캐시·Redis·다중 인스턴스·가상 스레드 실험 | 진입 조건 판정과 실행 후보의 채택·폐기 완료 |
| 5 | 깨끗한 최종 재측정과 비교 보고 | 최종 부하·불변식·전체 빌드·부팅 검증 완료 |
| 6 | 완료 감사와 로컬 인계 | 완료 기준·diff·문서·민감정보 경계 확인 |

## 6. 0단계 — 읽기 전용 사전 점검과 사람 준비

완료 기준: 실행 전제와 사람만 할 수 있는 준비를 한 번에 식별하고, 사람이 완료한 뒤 AI가 비민감 상태를
검증한 상태입니다.

### AI가 먼저 할 일

1. `AGENTS.md`, 성능 계획, 이 runbook, PRD 색인, 배포 가이드, 테스트·ADR 스킬을 읽습니다.
2. 현재 브랜치, `HEAD`, upstream, 원격과의 차이, staged·unstaged·untracked 파일, 다른 worktree를
   읽기 전용으로 확인합니다.
3. Java 21, Gradle wrapper, Docker·Compose, `curl`, `jq`, SHA-256 도구, `jcmd`, `jfr`, 브라우저 자동화
   가능 여부와 버전을 확인합니다. 이 단계에서는 설치·업데이트·이미지 pull을 하지 않습니다.
4. 호스트 OS·CPU·메모리·여유 디스크를 기록하고, 장시간 측정 중 결과를 흔들 백그라운드 부하 여부를
   확인합니다.
5. `.env`의 필요한 변수명이 설정됐는지만 값 없이 확인합니다. 비밀번호·토큰·JDBC 자격 증명을 출력하지
   않습니다.
6. 기존 Compose project·container·volume을 나열하고 성능 전용 환경과 충돌할 이름이 있는지 확인합니다.
7. 계획의 고정 날짜가 실제 실행일과 다르면 evidence 폴더 날짜를 임의로 바꾸지 않고 사용자에게 이름과
   일정 갱신 여부를 묻습니다.
8. 1~5단계에서 필요한 Java 의존성·컨테이너 이미지를 필수와 조건부로 나눕니다. Java 의존성은 정확한
   좌표·용도와 명시 버전 또는 Spring Boot BOM 관리 여부를, image는 tag와 pull 없이 확인 가능한 경우
   digest까지 제시합니다. 조건부 항목은 승인돼도 진입 조건 전에는 추가하지 않습니다.
9. 기준선 약 3시간, 최종 약 4시간을 시작점으로 실제 스크립트 시간을 다시 계산해 사람이 확보해야 할
   전용 시간대를 제시합니다.

### AI가 한 번에 출력할 사람 선행 준비 체크리스트

읽기 전용 점검 결과에 해당하는 항목만 출력합니다.

- 전원 연결과 자동 잠자기 방지, 기준선·최종 측정 동안의 컴퓨터 전용 사용 시간 확보
- UI 승인이 필요한 경우 Docker Desktop과 브라우저 자동화 권한 준비
- 누락된 로컬 비밀값을 Git에서 제외된 `.env`에 직접 입력
- 필수 관측 의존성·고정 container image 승인
- 조건부 Caffeine·Redis·Spring Session 의존성과 Redis image의 사전 승인 또는 “조건 충족 시 다시
  승인” 선택
- 정확한 성능 전용 DB·Compose volume을 반복 초기화해도 보존할 데이터가 없다는 확인

이번 runbook은 로컬 Compose 코드 회귀 검증만 실행합니다. AWS 용량 검증은 범위에서 제외하며 관련
자원·권한·비밀값 준비나 승인을 요청하지 않습니다.

AI는 사람에게 패키지 설치 명령이나 점검 명령을 대신 실행해 달라고 요청하지 않습니다. 비밀값이 누락된
경우에도 값 자체를 질문하지 않고 설정할 변수명과 안전한 입력 위치만 알려줍니다.

### 종료 조건

- 저장소와 작업 트리의 안전한 시작점이 확인됐습니다.
- 필수 도구가 실행 가능하거나, 사람이 준비할 정확한 항목이 확인됐습니다.
- 필요한 승인과 전용 측정 시간이 확보됐습니다.
- 성능 DB·volume 삭제 범위가 다른 환경과 구분됐습니다.
- 아직 파일 수정, dependency download, build, container 생성은 수행하지 않았습니다.

### AI에게 전달할 요청문

> `docs/implementation/performance/RUNBOOK.md`의 0단계만 실행해줘. 읽기 전용으로 현재 상태를 확인하고,
> 1~5단계 전에 사람이 미리 할 수 있는 준비를 한 체크리스트로 출력한 뒤 멈춰. 비밀값은 읽거나 출력하지
> 말고, 파일 수정·설치·빌드·컨테이너 생성은 하지 마.

사람이 체크리스트를 완료한 뒤에는 다음처럼 답합니다.

> 0단계 준비를 모두 완료했어. 비민감 상태를 직접 검증하고 문제가 없으면 1단계만 실행해줘.

## 7. 1단계 — 측정 장치와 재현 환경

완료 기준: 외부 서비스와 다른 DB를 건드리지 않는 결정적 성능 환경에서 smoke·관측·결과 저장이
재현되고, 코드 변경 완료 게이트가 통과한 상태입니다.

### 선행 조건

- 0단계 준비와 필수 의존성·이미지 승인이 완료됐습니다.
- 현재 브랜치가 직접 작업 가능한 브랜치이고 작업 트리 변경 범위를 알고 있습니다.
- 성능 DB와 container가 개발·테스트·시연 환경과 분리됩니다.

### AI 실행 순서

1. 시작 SHA와 dirty 상태를 성능 환경 문서 초안에 기록합니다.
2. 관측 스택이 로컬 성능 진단 도구인지 운영 표준 채택인지 구분합니다. 운영 표준 채택이면 구현 전에
   `adr` 스킬을 실행하고, 로컬 도구뿐이면 그 판단 근거를 기록합니다.
3. 승인된 Actuator·Micrometer Prometheus 의존성과 성능 전용 profile을 최소 범위로 추가합니다.
4. management `health`·`prometheus`를 애플리케이션 공개 포트와 분리하고 사설 Compose network 또는
   loopback에서만 접근 가능하게 합니다. 사용자·도서·페이지·세션·요청 본문을 metric label에 넣지
   않습니다.
5. 성능 전용 Compose에 MySQL 8.4, Prometheus, Grafana를 구성하고 버전 또는 digest를 고정합니다.
   Redis는 4단계 진입 조건 전에는 추가하지 않습니다.
6. `ilgeobolkka_perf`만 허용하는 결정적 `mvp` 데이터 준비기와 복원 절차를 만듭니다. DB 이름 guard와
   예상 행 수 검증이 실패하면 초기화를 거부하게 합니다.
7. k6의 공통 로그인·CSRF·cookie 처리와 Smoke, Warm-up, Average, Peak, Stress, Spike, Soak,
   contention 진입점을 구현합니다. PortOne·OpenAI 호출은 비활성화하거나 승인된 로컬 fake로 격리합니다.
8. 각 실행의 summary JSON, 환경 metadata, 시작·종료 UTC와 관측 시간 범위를 저장하는 요약 절차를
   구현합니다. 큰 로그·시계열·JFR은 Git 제외 위치에 두고 SHA-256·크기·위치만 문서화합니다.
9. Grafana dashboard 정의를 저장하고 JVM·Tomcat·HikariCP·HTTP·MySQL 지표를 같은 시간축에서 확인합니다.
10. management endpoint 노출, 민감 label, 성능 DB guard, 데이터 예상 행 수, 외부 호출 차단에 대응하는
    테스트를 먼저 작성해 통과시킵니다.
11. `performance/README.md`에 실제로 존재하는 준비·시작·중지·초기화·각 시나리오·요약 명령을 기록합니다.
    placeholder 명령이나 아직 없는 Gradle task를 적지 않습니다.
12. 관측 off/on Average를 각 1회 실행해 Prometheus scrape의 오버헤드를 기록합니다. JFR 진단 결과와
    정식 결과를 섞지 않습니다.
13. 테스트 스킬에 따라 대상 테스트, `./gradlew test`, `./gradlew check`, `./gradlew build`, 실행 설정에
    맞는 부팅 확인을 수행합니다. Compose는 실제 파일 조합으로 `docker compose ... config -q`를
    검증합니다.

### 중단 조건

- 승인되지 않은 새 의존성이나 image가 필요합니다.
- 성능 DB guard가 `_test`, 개발·시연·운영 DB를 구분하지 못합니다.
- management endpoint가 공개 애플리케이션 포트에 노출됩니다.
- 실제 외부 결제·OpenAI 호출 없이는 smoke를 통과할 수 없습니다.
- 정본을 바꾸거나 대규모 리팩터링해야만 측정 장치를 만들 수 있습니다.

### 종료 조건

- Smoke가 핵심 흐름의 계약·CSRF·세션·데이터를 검증합니다.
- k6 summary와 같은 시간대의 애플리케이션·DB 지표를 연결할 수 있습니다.
- 데이터 생성·초기화가 성능 DB 밖에서는 실패합니다.
- 관측 보안 테스트와 on/off 오버헤드 결과가 있습니다.
- 변경 테스트와 전체 test·check·build·부팅 검증이 통과했습니다.

### AI에게 전달할 요청문

> 0단계 종료 보고를 확인했어. Runbook 1단계만 실행해줘. 승인한 의존성과 image만 사용하고, 외부
> PortOne·OpenAI 및 성능 DB 밖의 데이터는 건드리지 마. 종료 조건을 검증해 보고한 뒤 2단계는 실행하지
> 말고 멈춰.

## 8. 2단계 — MVP1 기준선과 병목 확정

완료 기준: 고정한 패키징 JAR과 환경에서 기준선 3회, cold·warm 브라우저 결과, 동시성 불변식과 진단
근거가 보존되고 근거 있는 병목이 최대 3개로 정리된 상태입니다.

### 선행 조건

- 1단계 종료 조건이 통과했습니다.
- 사람이 기준선 측정 전용 시간을 확보했습니다.
- 성능 전용 DB·container·volume의 정확한 삭제 범위가 다시 확인됐습니다.

### AI 실행 순서

1. 코드와 설정을 고정하고 패키징 JAR을 한 번 빌드해 SHA-256을 기록합니다. 기준선 도중 코드를 바꾸지
   않습니다.
2. 성능 전용 환경만 깨끗하게 만들고 `mvp` 데이터를 결정적으로 생성합니다. 예상 행 수와 DB 크기를
   확인합니다.
3. 앱 시작 직후의 애플리케이션 cold 상태, JVM JIT·DB buffer pool 상태와 첫 요청 시간을 기록합니다.
   이 값을 steady-state 결과에 합치지 않습니다.
4. 각 정식 실행마다 업무 데이터와 애플리케이션을 같은 출발점으로 복원하고 Smoke 후 고정 Warm-up을
   실행합니다. Warm-up 표본은 버립니다.
5. Average 3회와 Peak 3회를 실행합니다. 매회 실제 RPS, p50·p95·p99, 오류율, dropped iterations,
   generator CPU와 JVM·Tomcat·HikariCP·MySQL 지표를 같은 시간대로 보존합니다.
6. Stress 1회를 중단선까지 실행하고 실제 중단 단계와 첫 번째 포화 자원을 기록합니다.
7. 동시성 특화 흐름 4종을 각각 독립 계정·페이지 pool로 실행한 뒤 잔액·원장·대여·소장·마지막 위치·세션
   불변식을 SQL 또는 MySQL 통합 검증기로 대조합니다.
8. 새 브라우저 context의 첫 탐색을 cold cache, 같은 context에서 동일 경로를 반복한 탐색을 warm
   cache로 묶어 3쌍 측정합니다. 보호 콘텐츠와 공개 정적 자산의 캐시 결과를 분리합니다.
9. `history-heavy` 생성 시간을 재고 10분·2GB 경계 안의 고정 행 수를 결정합니다. 생성 입력·행 수·시간·
   DB 크기를 기록하고 이후 바꾸지 않습니다.
10. 정식 실행과 분리한 진단 실행에서 JFR, Performance Schema, slow query log를 수집합니다. 느린 SQL은
    `EXPLAIN ANALYZE`의 actual rows·loops·iterator time과 사용 index를 저장합니다.
11. 관측값으로 설명할 수 있는 병목을 최대 3개까지 우선순위화합니다. 병목이 3개보다 적으면 수를 맞추기
    위해 추측을 추가하지 않습니다.
12. `docs/evidence/performance/mvp1-baseline-2026-08-12/`에 환경, summary, dashboard, `result.md`와 큰
    artifact의 SHA-256·크기·보존 위치를 기록합니다.

### 중단·무효 조건

- JAR, 데이터 입력, CPU·메모리 제한, MySQL 버전이 실행 사이 바뀌었습니다.
- generator CPU 포화나 dropped iterations 때문에 설정한 도착률을 만들지 못했습니다.
- 앞 실행의 대여·세션·cache 상태가 다음 실행에 섞였습니다.
- 실제 외부 서비스 요청이나 성능 DB 밖의 쓰기가 관측됐습니다.
- secret·cookie·세션 ID·DB 접속 문자열이 artifact에 포함됐습니다.

무효 실행은 좋은 값만 골라 남기지 않고 무효 이유를 기록한 뒤 같은 조건으로 다시 실행합니다.

### 종료 조건

- Average·Peak 각각 유효한 3회와 중앙값·범위가 있습니다.
- Stress와 동시성 4종, cold·warm 브라우저 3쌍이 기록됐습니다.
- 각 부하 결과가 같은 시간대의 JVM·Tomcat·HikariCP·MySQL 지표와 연결됩니다.
- JFR 또는 동등한 프로파일과 느린 SQL 실행 계획이 있습니다.
- 부하 뒤 도메인 불변식 결과가 있습니다.
- 병목 목록은 모두 관측 근거를 가지며 근거 없는 개선 후보가 3단계로 넘어가지 않습니다.

### AI에게 전달할 요청문

> 1단계 종료 보고를 확인했고 기준선 측정 시간도 확보했어. Runbook 2단계만 실행해줘. 캐시·JIT·DB
> 워밍업의 cold와 warm 결과를 분리하고, 매 정식 실행을 같은 출발점에서 시작해. 기준선 근거와 병목을
> 보존한 뒤 3단계는 실행하지 말고 멈춰.

## 9. 3단계 — 새 상태 인프라 없는 1차 개선

완료 기준: 기준선 병목만 대상으로 후보를 하나씩 검증하고, 채택 하한을 넘은 최소 변경만 결합해 정확성·
Average·Peak 재검증을 마친 상태입니다.

### AI 실행 순서

1. 2단계 근거에서 위험이 낮고 효과 가능성이 큰 후보를 정렬합니다. 인덱스·SQL·쿼리 왕복·로그·풀·JVM
   중 실제 병목과 연결되지 않은 후보는 실행하지 않습니다.
2. 후보 하나마다 다음 반복을 완료한 뒤 다음 후보로 갑니다.
   1. 현재 코드·JAR·환경과 재현 지표를 기록합니다.
   2. 기능·동시성·쿼리 수 회귀 테스트를 먼저 작성합니다. Flyway 인덱스는 새 migration으로만 추가하고
      `V1`을 수정하지 않습니다.
   3. 독립 변수 하나만 최소 변경합니다.
   4. 대상 테스트와 관련 MySQL 통합 테스트를 실행합니다.
   5. 같은 데이터·warm-up으로 Average 1회를 실행하고 기준선의 대응 실행과 비교합니다.
   6. 채택 하한, 정확성, 복잡도, 자원 사용량을 판정합니다.
   7. 미달 후보는 AI가 이번 후보에서 추가한 코드·설정만 제거하고 회귀 테스트를 다시 실행합니다.
      기존 사용자 변경이나 다른 후보의 채택 변경은 되돌리지 않습니다.
   8. 전후 수치와 유지·폐기 이유를 결과 표에 기록합니다.
3. 승인되지 않은 의존성, 대규모 리팩터링, 기존 죽은 코드 삭제가 필요하면 적용 전에 멈춰 질문합니다.
4. 채택 후보를 합친 패키징 JAR을 고정하고 전체 `test`, `check`, `build`와 부팅 smoke를 수행합니다.
5. 결합 결과를 같은 출발점에서 Average 3회·Peak 3회 실행하고 후보 단독 효과와 상호작용을 기록합니다.
6. 정확성·잠정 품질 게이트를 이미 만족하고 어떤 후보도 하한을 넘지 않으면 코드를 억지로 바꾸지 않고
   “단순 구성 유지”로 판정합니다.

### 종료 조건

- 각 후보에 재현 테스트, 독립 변수, 전후 수치, 정확성 결과와 유지·폐기 이유가 있습니다.
- 채택 변경만 남고 폐기 후보의 dependency·config·dead code가 남지 않았습니다.
- 결합 후보의 전체 test·check·build·부팅 검증이 통과했습니다.
- 결합 Average·Peak 각 3회가 기준선과 같은 조건으로 비교됐습니다.

### AI에게 전달할 요청문

> 2단계 종료 보고와 병목 근거를 확인했어. Runbook 3단계만 실행해줘. 관측된 병목 후보를 하나씩
> 재현 테스트→최소 변경→동일 Average 비교 순서로 검증하고, 채택 하한 미달은 제거해. 전체 게이트와
> 결합 Average·Peak를 확인한 뒤 4단계는 실행하지 말고 멈춰.

## 10. 4단계 — 조건부 캐시·Redis·다중 인스턴스·가상 스레드

완료 기준: 각 조건부 후보의 진입 조건을 먼저 판정하고, 조건을 만족한 후보만 cold·warm·정확성·장애
경계까지 비교해 유지 또는 제거한 상태입니다.

### 진입 판정표

| 후보 | 실행 조건 | 반드시 비교할 결과 | 채택 전 추가 경계 |
| --- | --- | --- | --- |
| Caffeine | 반복 공개 조회의 DB 읽기가 병목 | cache off, cold miss, warm 3회, hit ratio, DB statement rate, memory | 공개 저변경 데이터만, 권한·잔액·원장 제외 |
| Redis cache | Caffeine 효과가 있고 여러 인스턴스의 공유 필요가 있음 | Caffeine 대비 cold·warm·네트워크·장애·DB rate | 전용 namespace, 장애 시 MySQL fallback, ADR 판정 |
| Spring Session Redis | 단일 인스턴스 포화 또는 실제 다중 인스턴스 요구 | 1개 대비 2개 인스턴스 Peak, 로그인·CSRF·로그아웃·장애 | 공유 세션 채택 ADR |
| 가상 스레드 | I/O 대기가 크고 HikariCP·DB에 여유가 있음 | on/off Peak 3회, p95, RPS, pending, JFR pinning | daemon·keep-alive 부팅 검증 |
| Kafka | 진입 게이트 없음 | 실행하지 않음 근거만 기록 | 이번 계획 제외 |

### AI 실행 순서

1. 3단계 결과로 각 후보의 진입 조건을 `충족` 또는 `미충족`으로 판정하고 지표를 연결합니다.
2. 미충족 후보는 코드·dependency·container를 추가하지 않고 근거만 기록합니다.
3. 충족 후보에 승인되지 않은 의존성·image가 필요하면 좌표·용도·버전 관리 방식과 image tag·digest를
   제시하고 사람 승인을 기다립니다. 0단계에서 정확히 승인된 항목은 다시 묻지 않습니다.
4. Caffeine은 이전 단계의 기준선만 대조군으로 쓰지 않고 같은 측정 구간에서 cache off와 on을 각각 3회
   실행합니다. 실행 순서는 번갈아 배치하고, 매회 앱을 재시작한 뒤 cold miss·채움 시간을 기록하고 같은
   prefill·warm-up 뒤 warm Average를 측정합니다. 첫 요청 지연·채움 시간·hit ratio·p95·p99·DB rate·
   memory를 별도 열로 기록합니다.
5. Redis cache는 성능 전용 instance와 run namespace만 사용합니다. `FLUSHALL`, 권한·잔액·원장·대여·
   소장·결제 상태 캐시를 금지하고, 단절 때 인가 우회 없이 cache miss 또는 명시적 실패로 동작하는지
   테스트합니다.
6. Spring Session Redis는 두 인스턴스 사이 요청을 번갈아 보내 로그인 성공의 session ID 교체, CSRF,
   로그아웃 즉시 무효화와 Redis 재시작·단절 동작을 확인합니다.
7. 가상 스레드는 on/off 외의 코드·설정을 같게 유지하고 JFR pinning과 Hikari pending을 함께 봅니다.
8. 각 후보는 계획의 채택 하한과 정확성 게이트를 모두 통과해야 유지합니다. 미달이면 이번 실험에서 추가한
   dependency·config·container·코드만 제거하고 테스트를 다시 실행합니다.
9. 운영 캐시·공유 세션·다중 인스턴스·운영 관측 구조를 채택할 때만 `adr` 스킬로 기존 결정과 대안을
   비교해 기록합니다. 로컬 실험만으로 운영 표준이라고 표현하지 않습니다.
10. 최종 후보 조합으로 Spike 1회와 부하 뒤 불변식 검증을 수행합니다.

### 종료 조건

- 모든 조건부 후보에 진입 조건 판정과 근거가 있습니다.
- 실행 후보에는 cold·warm 분리 결과와 정확성·장애 경계 결과가 있습니다.
- 미실행 후보에는 측정값을 꾸며내지 않고 진입 조건 미충족 근거가 있습니다.
- 유지하지 않는 dependency·container·config가 남지 않았습니다.
- 운영 구조를 채택했다면 ADR이 있고, 실험뿐이면 운영 표준으로 표현하지 않았습니다.

### AI에게 전달할 요청문

> 3단계 종료 보고를 확인했어. Runbook 4단계만 실행해줘. 먼저 각 조건부 후보의 진입 조건을 지표로
> 판정하고, 충족한 후보만 승인 경계 안에서 실험해. 캐시는 cold miss와 고정 warm 상태를 분리하고,
> 미달 후보는 추가물을 제거해. 종료 보고 뒤 5단계는 실행하지 말고 멈춰.

## 11. 5단계 — 깨끗한 최종 재측정과 보고

완료 기준: 채택 후보만 포함한 깨끗한 동일 환경에서 최종 시나리오·불변식·브라우저·전체 빌드·패키징
smoke가 완료되고 기준선과 비교 보고서가 작성된 상태입니다.

### 선행 조건

- 4단계의 채택·폐기와 ADR 판정이 끝났습니다.
- 사람이 최종 측정 전용 시간을 확보했습니다.
- 기준선의 데이터 생성 입력, 환경 설정과 관측 조건을 다시 사용할 수 있습니다.

### AI 실행 순서

1. 현재 코드와 채택 설정을 고정하고 패키징 JAR SHA-256을 기록합니다.
2. 실행 중인 process·container·port를 확인한 뒤 성능 전용 Compose project만 중지합니다. 초기화 전
   삭제 대상 container·network·volume의 해석된 이름을 출력하고 다른 환경과 겹치지 않는지 확인합니다.
3. 성능 전용 환경을 깨끗하게 만들고 기준선과 같은 `mvp`·`history-heavy` 입력을 복원합니다. 예상 행 수,
   DB 크기와 snapshot 식별자를 대조합니다.
4. 채택 캐시가 있으면 앱 시작 직후 cold miss·채움 시간을 기록합니다. 이 값은 warm 정식 통계와
   합치지 않습니다.
5. Average 3회와 Peak 3회를 각각 다음 순서로 실행합니다.
   1. 업무 데이터와 애플리케이션·성능 cache를 고정 출발점으로 복원합니다.
   2. Smoke를 통과시킵니다.
   3. 같은 Warm-up을 수행하고 표본을 버립니다.
   4. 정식 시나리오를 실행하고 summary·관측 시간 범위·불변식을 저장합니다.
6. Stress 1회, Spike 1회, Soak 1회를 계획의 부하·중단선으로 실행합니다. 중단선을 넘으면 값을 낮춰
   다시 성공처럼 만들지 않고 실제 한계를 기록합니다.
7. 동시성 특화 4종을 실행하고 잔액·원장·대여·소장·마지막 위치·세션 불변식을 전부 대조합니다.
8. 새 브라우저 context의 첫 탐색 cold cache와 같은 context의 반복 탐색 warm cache를 3쌍으로 묶어
   기준선과 같은 경로·도구·viewport로 측정합니다. 보호 콘텐츠의 no-store 계약도 확인합니다.
9. 진단이 필요한 남은 병목만 정식 실행과 분리해 JFR·Performance Schema·`EXPLAIN ANALYZE`로
   확인합니다.
10. 테스트 스킬에 따라 변경 대상 테스트, `./gradlew test`, `./gradlew check`, `./gradlew build`를 각각
    실행하고 통과·실패 테스트 수를 기록합니다.
11. 패키징 JAR을 실제 설정으로 부팅하고 제한 시간 안에 `/api/smoke`의 HTTP 204를 확인한 뒤 정상
    종료합니다. 이 smoke는 DB·Flyway·JPA 전체 준비나 브라우저 수용 검증과 별도 사실로 보고합니다.
12. `docs/evidence/performance/mvp1-final-2026-08-15/`에 최종 summary·dashboard·artifact metadata와
    `comparison.md`를 작성합니다. 기준선, 후보별 효과, 최종값, 남은 병목, 다음 용량 한계를 구분합니다.

### 종료 조건

- 최종 Average·Peak 각 3회, Stress·Spike·Soak 각 1회가 유효하거나 중단선 결과가 정확히 기록됐습니다.
- cold·warm cache와 브라우저 결과가 분리됐습니다.
- 동시성 4종과 부하 뒤 불변식이 전부 검증됐습니다.
- 전체 test·check·build와 패키징 JAR smoke가 통과했습니다.
- 비교 보고서가 성능 계획의 표와 단정적 판정 항목을 모두 포함합니다.
- 모든 성능 결과가 로컬 코드 회귀 기준선이며 운영 용량 증거가 아니라고 명확히 표시됐습니다.

### AI에게 전달할 요청문

> 4단계 종료 보고를 확인했고 최종 측정 시간도 확보했어. Runbook 5단계만 실행해줘. 성능 전용 환경만
> 깨끗하게 복원하고, 각 정식 실행을 같은 출발점과 warm-up으로 반복해. cold·warm과 진단 실행을 섞지
> 말고 전체 검증·comparison까지 완료한 뒤 6단계는 실행하지 말고 멈춰.

## 12. 6단계 — 완료 감사와 로컬 인계

완료 기준: 계획의 완료 기준, 저장소 변경, 검증·증거·민감정보·승인 경계를 모두 감사하고 다음 사람이
재현할 수 있는 로컬 상태로 인계한 상태입니다.

### AI 실행 순서

1. 성능 계획의 완료 기준 1~10을 하나씩 근거 경로와 연결합니다. 근거가 없으면 완료로 표시하지 않고
   필요한 이전 단계로 돌아갈 항목을 적습니다.
2. `git status`, 전체 diff와 untracked 파일을 확인해 허용 범위 밖 변경, 생성된 secret, cookie, session
   ID, JDBC credential, 큰 raw artifact가 Git 대상에 없는지 검사합니다. 민감값 자체를 출력하지 않습니다.
3. `git diff --check`, Markdown code fence, 로컬 상대 링크와 실제 명령 존재 여부를 검사합니다.
4. 테스트·부하·브라우저 실행 수, 실패·무효·생략과 이유, 중앙값·범위 계산을 evidence 원본과 대조합니다.
5. JAR·image·큰 artifact의 SHA-256, 크기, 보존 위치, 시간 범위가 실제 파일과 일치하는지 확인합니다.
6. 품질 게이트, p95·p99·지속 RPS 변화, 첫 번째 로컬 용량 한계, Redis·다중 인스턴스·가상 스레드·Kafka의
   유지·제외 이유, 운영 용량으로 해석할 수 없는 이유, 다음 1순위 개선을 최종 요약합니다.
7. 실행 완료 뒤 container는 안전하게 중지할 수 있지만, 성능 volume과 원시 artifact 삭제는 정확한
   대상을 다시 보여주고 사용자에게 보존 여부를 확인한 뒤 수행합니다.
8. 로컬 작업 완료를 먼저 보고합니다. 커밋, push, PR 수정, merge는 각각 요청받은 경우에만 대응 스킬을
   읽고 별도로 실행합니다.

### 최종 판정

다음 세 문장을 분리해 보고합니다.

- `Runbook 실행`: 완료 / 미완료
- `정확성·품질 게이트`: 통과 / 미달
- `성능 목표`: 달성 / 미달 / 기준선 충족으로 단순 구성 유지

### AI에게 전달할 요청문

> 5단계 종료 보고를 확인했어. Runbook 6단계만 실행해줘. 계획 완료 기준과 실제 evidence·diff·민감정보
> 경계를 전부 감사하고 로컬 완료 상태를 보고해. 성능 volume 삭제, 커밋, push, PR 수정, merge는 하지
> 말고 각각 필요한 승인으로 남겨.

## 13. 중단 후 재개

대화나 프로세스가 중단되면 완료했다고 기억에 의존하지 않습니다. 새 세션의 AI는 다음 순서로 재개합니다.

1. `AGENTS.md`, 성능 계획과 이 runbook을 다시 읽습니다.
2. 현재 브랜치·HEAD·upstream·작업 트리와 실행 중 process·container를 확인합니다.
3. 가장 최근 evidence의 `environment.md`, `result.md` 또는 `comparison.md`, summary와 artifact SHA-256을
   확인합니다.
4. 단계 종료 조건이 모두 증명된 마지막 단계까지만 완료로 인정합니다.
5. 실행 도중 중단된 부하 결과는 정식 결과에 포함하지 않고 중단 이유를 기록합니다.
6. 데이터·cache·애플리케이션 출발점을 복원한 뒤 중단된 실행 단위부터 다시 수행합니다.
7. 사람 작업 대기 중이었다면 비밀값을 다시 요구하지 않고 비민감 완료 상태만 검증합니다.

재개 요청문:

> `docs/implementation/performance/RUNBOOK.md`를 기준으로 현재 저장소와 evidence를 읽기 전용으로 확인해줘.
> 마지막으로 종료 조건이 증명된 단계와 중단된 실행 단위를 찾아 보고하고, 아직 어떤 변경이나 다음 단계도
> 실행하지 말고 멈춰.

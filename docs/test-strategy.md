# 읽어볼까 MVP 테스트 전략

## 1. 목적

이 문서는 [기능 요구사항](./prd/requirements.md)과 [MVP 성공 조건](./prd/mvp-goals.md#성공-판정)을
어떻게 검증할지 정의합니다. 가격·기간과 상태 전이의 정본은 [제품 정책](./prd/product-policy.md)이며,
이 문서의 수치는 테스트 입력과 기대 결과입니다.

## 2. 검증 우선순위

1. 잉크 잔액과 변경 불가능한 내역의 일치, 사용 기한 없음
2. 활성 대여 재사용과 만료 후 재대여의 시간 경계
3. 새 대여 1건과 1잉크 차감 1건의 원자성
4. 도서 원가 결제와 온라인 소장 기록의 일치
5. 소장 결제와 잉크 잔액·내역의 완전한 분리
6. 소장 도서의 기간·잉크 제한 없는 페이지 접근
7. 동시·중복·재시도 요청의 중복 차감·중복 소장 방지
8. 원본 PDF 페이지 번호와 텍스트·이미지 콘텐츠의 정합성
9. 인증·열람 세션과 페이지 콘텐츠 접근제어
10. 카테고리 우선 목록, 검색, 내 서재와 접근성
11. PortOne V2 테스트 채널의 서버 재조회, 웹훅 서명과 멱등 완료

빠른 도메인 테스트부터 MySQL 통합 테스트, 브라우저 기반 사용자 흐름 테스트 순으로 실행합니다.

## 3. 공통 테스트 데이터

공통 시연 데이터의 정본은 [MVP 초기 데이터](./prd/mvp-goals.md#초기-데이터)입니다. 아래 이름은 테스트
시나리오에서 해당 데이터를 짧게 참조하기 위한 별칭입니다.

### 사용자

- Reader A: 정상 대여 검증 참가자 전용 100잉크 계정
- Reader B: 잉크 부족 검증 참가자 전용 0잉크 계정
- Reader C: 온라인 소장 검증 참가자 전용 계정이며, 0잉크이고 Book A를 온라인 소장
- Reader A의 잉크 내역: 테스트 이용권 지급 +100잉크
- Reader C의 소장 결제 내역: Book A 도서 원가의 원화 결제 완료
- 일반 회원가입 사용자: 0잉크, 지급·소장 내역 없음
- 세 검증 계정의 공통 비밀번호: `DEMO_VALIDATION_PASSWORD` 환경변수로 주입하고 테스트와 저장소에
  원문 기록 금지

### 도서와 콘텐츠

- AI가 작성하고 제목·저자·카테고리가 서로 다른 가상 더미 도서 100권
- 모든 도서에 0보다 큰 고정 도서 원가
- 카테고리 우선 정렬과 같은 카테고리의 `title ASC, id ASC` 동률 정렬을 확인할 수 있는 데이터
- 제목 검색 일치, 저자 검색 일치, 검색 불일치, `%`와 `_`가 포함된 데이터
- 영문 대소문자와 앞뒤·내부 공백 보존을 확인할 제목·저자 데이터
- 원본 PDF 페이지 수와 변환 콘텐츠 수가 같은 도서
- 문단·글자 순서를 확인할 텍스트 페이지
- 표·수식·삽화와 원본 배치를 확인할 이미지 페이지
- 첫·중간·마지막 페이지 번호 연결을 확인할 표본

### 시간

- 주입한 고정 `Clock`과 UTC `Instant`
- 활성 대여: `rentedAt=2026-07-25T05:00:00Z`, `expiresAt=2026-08-24T05:00:00Z`
- 페이지마다 시작 시각이 다른 대여 데이터
- 잉크 무기한 보존 검증용 수년 뒤의 고정 시각

## 4. 핵심 불변식

### INV-001 잉크 보존

현재 잉크 잔액은 모든 잉크 지급에서 모든 페이지 대여 차감을 뺀 값과 같아야 합니다. 잉크에는 만료
이벤트가 없고 시간이 지난다는 이유로 잔액이나 내역이 바뀌지 않습니다.

### INV-002 활성 대여 중복 차감 금지

`serverNow < expiresAt`인 독자·도서·페이지에는 재열람 횟수와 관계없이 새 잉크 차감과 대여 기록을
만들지 않습니다.

### INV-003 차감과 대여의 원자성

새 대여에서는 잉크 1개 차감, 잉크 내역, `PageRental` 기록과 마지막 열람 위치가 모두 성공하거나 모두
실패해야 합니다. 페이지 콘텐츠는 트랜잭션 성공 뒤에만 제공합니다.

### INV-004 음수 잔액 금지

어떤 동시 요청과 재시도에서도 잉크 잔액은 0 아래로 내려가면 안 됩니다.

### INV-005 변경 불가능한 잉크 내역

생성된 잉크 지급과 차감 내역은 수정하거나 삭제하지 않습니다.

### INV-006 대여 기간 경계

대여는 서버 시각 기준 `rentedAt <= serverNow < expiresAt`에서만 활성입니다. `expiresAt`은
`rentedAt + 30일`이며 정확히 만료 시각부터 새 대여가 필요합니다.

### INV-007 페이지별 독립 기간

한 페이지의 대여 시작·재열람·만료가 다른 페이지의 `rentedAt`과 `expiresAt`을 바꾸지 않습니다.

### INV-008 원본 PDF 페이지 정합성

`Book.totalPageCount`는 원본 PDF 페이지 수와 같고, 각 서비스 페이지 번호는 같은 번호의 변환 콘텐츠
하나와 연결됩니다. 표시 배율과 글자 크기는 이 연결과 잉크 차감 단위를 바꾸지 않습니다.

### INV-009 콘텐츠 권한 선행

인증과 현재 열람 세션을 확인한 뒤, 온라인 소장 또는 활성·신규 대여 중 하나가 성립해야만 텍스트·이미지
콘텐츠를 제공합니다. 내부 저장소 주소와 원본 PDF는 제공하지 않습니다.

### INV-010 잉크 사용 기한 없음

구매하거나 지급받은 잉크는 보유 기간과 마지막 사용 시각에 관계없이 유지됩니다. 페이지 대여
`expiresAt`, 로그인 세션 만료와 잉크 잔액은 서로 영향을 주지 않습니다.

### INV-011 도서 원가 결제와 잉크 분리

온라인 소장은 도서 원가와 일치하는 원화 결제 성공으로만 생성합니다. 소장 결제는 잉크 잔액과 잉크
내역을 바꾸지 않고, 페이지 대여에 사용한 잉크도 도서 원가에서 공제하거나 소장 금액으로 누적하지 않습니다.

### INV-012 온라인 소장 권한

온라인 소장한 도서는 모든 페이지를 잉크 잔액, 활성 대여와 만료 시각에 관계없이 제공합니다. 같은
독자·도서의 소장 기록은 하나이며 기간 만료 상태를 갖지 않습니다.

### INV-013 결제 검증과 멱등 완료

잉크 이용권과 소장 결제는 서버가 만든 `PENDING` 시도에서 시작합니다. 브라우저 완료와 서명 검증된
웹훅은 PortOne V2 결제를 다시 조회하며, 상태·식별자·금액·통화가 모두 맞는 첫 요청만 `PAID` 전이와
잉크 또는 소장 권한을 같은 트랜잭션에서 한 번 반영합니다.

## 6. 경계값과 실패 주입

### 시간

- 잉크 지급 후 수년 경과: 잔액·내역 유지
- `expiresAt - 1ms`: 활성 대여, 추가 차감 없음
- `expiresAt`: 만료, 새 1잉크 차감과 30일 대여
- 온라인 소장 후 임의 시간 경과: 소장 상태 유지
- 로그인 세션 마지막 활동 후 1시간 59분 59초: 유지
- 로그인 세션 마지막 활동 후 2시간 이상: 만료, 잉크·소장 상태 유지

애플리케이션이 판정하는 시간 경계 테스트는 실제 대기하지 않고 주입한 `Clock`을 사용합니다. 단, 애플리케이션
`Clock`을 사용하지 않는 서블릿 컨테이너의 `HttpSession` 비활성 만료는 테스트 세션에만 1초 제한을 적용하고
짧게 실제 대기한 뒤 보호 API의 `401` 응답을 확인합니다.

### 잉크와 동시성

- 잔액 0: 새 페이지 대여 차단, 활성 대여·소장 페이지 허용
- 잔액 1: 정확히 새 페이지 한 개 대여 가능
- 같은 페이지 동시 요청 10회: 총 1잉크와 대여 1건
- 서로 다른 페이지 동시 요청, 잔액 1: 한 페이지만 대여되고 잔액은 0
- 같은 도서의 소장 완료와 새 페이지 대여 동시 요청: 같은 `InkAccount` 잠금으로 순서화하고 선행 결과에
  따라 0 또는 1잉크 차감, 이미 완료된 대여는 환급하지 않음
- 응답 유실 후 재시도: 기존 활성 대여 반환, 추가 차감 없음

### 소장 결제

- 도서 원가 0과 음수: 거부
- 도서 원가와 결제 금액 정확히 일치: 소장 성공
- 1원 부족·초과, 다른 도서 결제 결과: 소장 거부
- 같은 결제 식별자 동시 요청: 결제 반영과 소장 각각 1건
- 이미 소장한 도서의 결제 준비: `409 BOOK_ALREADY_OWNED`
- 같은 독자·도서의 기존 `PENDING`: 기존 결제 준비 정보 재사용
- 같은 독자·도서에 `FAILED`만 존재: 새 `paymentId` 생성
- 소장 처리 중 DB 오류: 결제 결과 처리 상태와 소장 기록의 부분 반영 없음

### PortOne V2 결제 완료

- `PENDING` 생성 뒤 브라우저 완료와 웹훅 도착 순서 교차
- 웹훅 서명 누락·불일치: `400`, 상태 변경과 도메인 효과 없음
- 정상 서명의 미지원 이벤트: `200`, 상태 변경과 도메인 효과 없음
- `Transaction.Failed`: 서버 재조회로 최종 실패를 확인한 경우만 `FAILED`
- PortOne 조회 일시 장애: 재시도 가능한 `5xx`, `PENDING` 유지
- PortOne 조회 결과 미완료 상태: 정상 응답, `PENDING` 유지
- 금액 1원 부족·초과, `KRW` 외 통화, 다른 `paymentId`: `FAILED`, 지급 거부
- 같은 완료 요청 동시 10회: 결제 `PAID` 전이와 잉크·소장 효과 각각 1건
- 완료 트랜잭션 실패: 결제 상태와 도메인 효과 모두 롤백
- 실패 후 재시도: 이전 시도 보존, 새 `paymentId` 사용

### 콘텐츠와 네트워크

- 원본 PDF의 첫·중간·마지막 페이지 매핑
- 텍스트 추출 순서 오류와 이미지 렌더링 누락
- 유효 범위 밖 페이지 번호와 조작한 도서 ID
- 이전 열람 세션의 지연 요청
- 페이지 이동 후 이전 페이지 콘텐츠의 지연 응답
- 잉크 내역·`PageRental`·온라인 소장 기록 저장 직전 오류
- 연결이 끊긴 상태에서 새 페이지 또는 소장 결제 결과 요청

## 7. 보안 및 콘텐츠 전달 확인

- 비밀번호 원문과 DB 접속 정보·시연 계정 자격 증명이 코드, 문서, 로그, 오류 응답에 없어야 합니다.
- 비밀번호는 `DelegatingPasswordEncoder`의 BCrypt 형식으로 저장해야 합니다.
- 로그인 실패 응답은 이메일 존재 여부를 구분하지 않아야 합니다.
- 로그인 성공 시 세션 ID가 교체되고 로그아웃 시 로그인·열람 세션이 무효화되어야 합니다.
- Thymeleaf 폼은 CSRF hidden field를, `fetch`는 페이지의 `_csrf`, `_csrf_header` meta 태그를 사용해야
  하며 토큰 없는 상태 변경 요청은 처리되지 않아야 합니다.
- 로그인·로그아웃 뒤에는 새 페이지를 렌더링해 새 CSRF 토큰을 사용하고 별도 토큰 API를 두지 않아야 합니다.
- PortOne API secret과 웹훅 secret은 브라우저, 로그, 오류 응답에 노출되지 않아야 합니다.
- `/api/**` 응답의 `X-Request-Id`와 요청·실패 로그의 `requestId`가 같아야 합니다. 로그에는 요청 바디·쿼리·
  헤더·쿠키·예외 원문과 로그인 세션 ID·`viewerSessionId`·내부 저장소 경로가 없어야 합니다.
- 웹훅 서명과 PortOne 서버 재조회 검증 없이 이용권 지급과 온라인 소장을 만들지 않아야 합니다.
- 원본 PDF와 내부 저장소 주소를 직접 내려주는 공개 경로가 없어야 합니다.
- 애플리케이션은 본인의 소장 또는 대여 권한을 확인한 요청 페이지 외 콘텐츠를 제공하지 않아야 합니다.
- 다른 사용자의 페이지 대여, 온라인 소장, 내 서재와 잉크 내역을 조회할 수 없어야 합니다.
- DRM과 화면 캡처 방지는 검증 범위가 아닙니다.

### 공통 ES Module 브라우저 검증

공통 JavaScript는 별도 Node.js 테스트 런타임을 추가하지 않고 패키징한 애플리케이션의 실제 브라우저에서
검증합니다.
`.github/scripts/boot-smoke.sh`는 설치된 Chrome 또는 Chromium에서 `.github/browser-smoke`의 fixture를
실행합니다. fixture는 smoke 실행 중에만 정적 경로로 연결하고 운영 JAR에는 포함하지 않습니다.

1. `/books`에서 `request-json.js`를 동적 import하고 `/api/books?page=1`, `/api/smoke`를 호출해 JSON
   응답과 `204`의 `null` 반환을 확인합니다.
2. 다른 origin URL, JSON이 아닌 성공·실패 응답과 네트워크 실패를 호출해
   `CROSS_ORIGIN_REQUEST`, `INVALID_RESPONSE`, `NETWORK_ERROR`와 HTTP 상태·`X-Request-Id` 보존을
   확인합니다.
3. 상태 변경 요청에서 페이지의 `_csrf`, `_csrf_header`가 실제 요청 헤더에 포함되고, meta 태그를 제거한
   같은 요청은 `MISSING_CSRF_TOKEN`으로 전송 전에 중단되는지 확인합니다.
4. 로그아웃 성공과 서버 오류 응답을 각각 발생시켜 두 경우 모두 `/books`가 새로 렌더링되고, 내비게이션과
   CSRF 토큰이 서버의 실제 인증 상태와 일치하는지 확인합니다. 요청이 전송되지 않은 네트워크·CSRF 준비
   오류는 현재 화면에서 오류를 표시하고 다시 시도할 수 있어야 합니다.
5. 오류 안내가 `textContent`로 표시되고 공통 오류 영역으로 포커스가 이동하며, `401`·`403`만으로 자동
   이동하지 않는지 확인합니다.

## 8. 변환 품질 확인

구체적인 변환 명령, 표본 manifest와 보존된 근거는
[콘텐츠 변환과 품질 검증](./content-conversion.md)을 따릅니다.

- 공개 가능한 시연 PDF 100권과 manifest의 도서 항목 100개가 전체 400페이지를 구성하고 `bookId`,
  PDF SHA-256과 페이지 수가 실제 파일과 일치해야 합니다.
- 반복 변환은 고정한 시연 PDF에서 시작하고 기존 합성 페이지 규칙으로 PDF를 다시 만들지 않아야 합니다.
- `Book.totalPageCount`, 원본 PDF 페이지 수와 변환 콘텐츠 수가 일치해야 합니다.
- 모든 서비스 페이지 번호가 1부터 중복·누락 없이 원본 PDF의 같은 페이지 번호에 연결되어야 합니다.
- 모든 페이지는 `TEXT` 또는 `IMAGE` 중 정확히 하나이며, `TEXT` 본문과 `IMAGE` 경로·파일 중 선택된
  산출물이 비어 있지 않아야 합니다. 빈 텍스트 추출 결과는 `IMAGE`로 변환해야 합니다.
- 텍스트 페이지는 문단, 문장과 글자 순서가 원본의 읽기 순서와 맞아야 합니다.
- 이미지 페이지는 표, 수식, 삽화와 원본 배치가 잘리지 않고 읽을 수 있어야 합니다.
- 자동 검증을 모두 통과하기 전에는 DB를 변경하지 않으며 실패 후 기존 시연 콘텐츠가 유지되어야 합니다.
- 적재 전후 같은 `(bookId, pageNumber)`의 `BookPage.id`가 유지되고 없는 페이지만 추가되어야 합니다.
  예상하지 않은 기존 페이지가 있으면 삭제하지 않고 전체 적재가 실패해야 합니다.
- 100권 전체의 위험 요소를 고려해 카테고리별 대표 도서 한 권씩 총 10권을 선정하고, 선정한 10권의
  첫·중간·마지막과 위험 페이지를 수동 검수해 파일 크기를 기록합니다.
- 시연 PDF·manifest와 변환 산출물이 `bootJar`와 배포 이미지에 포함되지 않아야 합니다.
- 최초 동결이 끝난 뒤 합성 페이지 생성 코드와 기존 페이지 PNG가 런타임 classpath에 남지 않아야 합니다.
- 실제 데스크톱 뷰어 크기의 표시 품질은 SCRUM-406에서 같은 표본으로 확인합니다.

## 9. 사용자 이해 검증

구현 완료 후 사용자 3명에게 참가자별 전용 검증 계정으로 새 페이지 대여, 활성 대여 재열람과 도서 소장
흐름을 수행하게 합니다.
참가자가 “잉크는 만료되지 않는 프로그램 화폐이고 페이지는 1잉크로 30일 대여하며, 소장은 잉크가 아닌
도서 원가를 원화로 직접 결제한다”는 차이를 자신의 말로 설명하면 통과로 기록합니다. 3명 모두 통과해야
합니다.

## 10. 출시 게이트

구현 완료 판정에는 최소한 다음 증거가 필요합니다.

1. `docker compose config -q` 통과
2. `docker compose up -d --wait`로 MySQL 8.4 준비
3. 모든 핵심 불변식과 필수 시나리오 테스트 통과
4. `./gradlew test`, `./gradlew check`, `./gradlew build` 통과
5. 패키징한 애플리케이션을 MySQL 8.4에 실제로 연결해 부팅하고 `GET /api/smoke`의 `204`와 민감정보 없는
   부팅 로그 확인
6. 잉크 무기한 보존과 잔액·내역 합계 대조 통과
7. 활성·만료 대여 시간 경계, 중복·동시 요청과 실패 주입 검증
8. PortOne V2 테스트 채널의 준비·서버 재조회·웹훅 서명·멱등 완료와 소장·잉크 분리 검증
9. 원본 PDF 페이지 번호, 텍스트·이미지 변환 품질과 접근제어 검증
10. 브라우저에서 로그인부터 잉크 구매·대여·재열람·원가 결제 소장까지 핵심 흐름 통과
11. 사용자 이해 검증 3명 모두 통과

부팅 smoke는 CI에서 애플리케이션·DB·HTTP 경계를 확인하는 검사이며 운영 관측 기능이 아닙니다. 이 검사를
위해 Actuator 의존성을 추가하지 않습니다. 운영 환경의 health·readiness·metrics가 필요해지면 노출 경로와
보안 정책을 포함해 별도 결정합니다.

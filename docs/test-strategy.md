# 읽어볼까 MVP 테스트 전략

## 1. 목적

이 문서는 [기능 요구사항](./prd/requirements.md), [초기 MVP 성공 조건](./prd/mvp-goals.md#성공-판정)과
[AI 잉크 경로 2차 MVP 성공 조건](./prd/ai-ink-route.md#품질과-출시-기준)을 어떻게 검증할지 정의합니다.
가격·기간과 상태 전이의 정본은 [제품 정책](./prd/product-policy.md)이며, 이 문서의 수치는 테스트 입력과
기대 결과입니다.

## 2. 검증 우선순위

1. 잉크 잔액과 변경 불가능한 내역의 일치, 사용 기한 없음
2. 활성 대여 재사용과 만료 후 재대여의 시간 경계
3. 새 대여 1건과 1잉크 차감 1건의 원자성
4. 도서 원가 결제와 온라인 소장 기록의 일치
5. 소장 결제와 잉크 잔액·내역의 완전한 분리
6. 소장 도서의 기간·잉크 제한 없는 페이지 접근
7. 동시·중복·재시도 요청의 중복 차감·중복 소장 방지
8. 원본 PDF 페이지 번호와 텍스트·이미지 콘텐츠의 정합성
9. 인증·열람 세션과 페이지 콘텐츠 접근제어
10. 카테고리 우선 목록, 검색, 내 서재와 접근성
11. PortOne V2 테스트 채널의 서버 재조회, 웹훅 서명과 멱등 완료
12. AI 경로 생성·미리보기·저장의 무과금과 서버 생성 결과 신뢰 경계
13. AI 생성 횟수의 동시성·멱등성, 외부 전송과 공개 가이드의 콘텐츠 보호
14. 개발·회귀 데이터와 잠금 holdout을 분리한 추천 품질과 응답 시간

빠른 도메인 테스트부터 MySQL 통합 테스트, 브라우저 기반 사용자 흐름 테스트 순으로 실행합니다.

## 3. 공통 테스트 데이터

공통 시연 데이터의 정본은 [MVP 초기 데이터](./prd/mvp-goals.md#초기-데이터)입니다. 아래 이름은 테스트
시나리오에서 해당 데이터를 짧게 참조하기 위한 별칭입니다.

### 사용자

- Reader A: 정상 대여 기술 검증 전용 100잉크 계정
- Reader B: 잉크 부족 기술 검증 전용 0잉크 계정
- Reader C: 온라인 소장 기술 검증 전용 계정이며, 0잉크이고 Book A를 온라인 소장
- AI 품질 평가 Reader 01~27: 각각 15잉크 이상이고 당일 생성 기록이 없는 계정. 잠금 holdout 270개 목적을
  `(bookId ASC, purposeId ASC)` 순번을 27로 나눈 나머지로 계정별 10개씩 배정하고 같은 독자·도서에는
  목적을 하나만 허용하며 목적별 소장·활성 대여는 코퍼스의 7개 평가 시나리오에 맞춰 준비
- Reader A의 잉크 내역: 테스트 이용권 지급 +100잉크
- Reader C의 소장 결제 내역: Book A 도서 원가의 원화 결제 완료
- 일반 회원가입 사용자: 0잉크, 지급·소장 내역 없음
- 세 검증 계정의 공통 비밀번호: `DEMO_VALIDATION_PASSWORD` 환경변수로 주입하고 테스트와 저장소에
  원문 기록 금지

### 도서와 콘텐츠

- AI가 작성하고 제목·저자·카테고리가 서로 다른 가상 더미 도서 100권
- 모든 도서에 0보다 큰 고정 도서 원가
- 카테고리 우선 정렬과 같은 카테고리의 `title ASC, id ASC` 동률 정렬을 확인할 수 있는 데이터
- 제목 검색 일치, 저자 검색 일치, 검색 불일치, `%`와 `_`가 포함된 데이터
- 영문 대소문자와 앞뒤·내부 공백 보존을 확인할 제목·저자 데이터
- 원본 PDF 페이지 수와 변환 콘텐츠 수가 같은 도서
- 문단·글자 순서를 확인할 텍스트 페이지
- 표·수식·삽화와 원본 배치를 확인할 이미지 페이지
- 첫·중간·마지막 페이지 번호 연결을 확인할 표본
- `ai-route-v2`의 비소설 90권은 각각 48~72페이지이고 소설 10권은 초기 PDF·SHA-256·페이지 수를
  유지하는 콘텐츠
- AI 경로 지원 페이지의 비공개 분석 텍스트와, 원문·결론·수치·사례 결과가 없는 검수된 공개 가이드 주제
- 지원 도서별 개발·회귀 목적 1개인 전체 90개와, 개발자가 `holdoutDatasetVersion`·`holdoutDatasetHash`·
  `generationArtifactHash`·`generationConfigHash`·`evaluationSourceHash`·`evaluationGitRevision`을 사전
  봉인하기 전까지 볼 수 없는 도서별 대표 목적 3개인 잠금 holdout 270개. 두 세트의 런타임 입력과 분리된
  정답 평가 데이터
- 도서·콘텐츠 버전별 `UNSUPPORTED`, `EVALUATABLE`, `PUBLIC` 상태와 적용할 OpenAI 데이터 제어,
  비-ZDR 프롬프트 파생 캐시 최대 24시간 허용 여부, 평가 JAR의 `generationArtifactHash`, 공개 승인
  `generationConfigHash`와 `openAiPolicyHash`, 평가·공개 배포의 `latencyProfile`, 공개 승인 `evaluationGitRevision`,
  `holdoutDatasetVersion`·`holdoutDatasetHash`, 공개 후보 DB와 평가 DB의 `evaluationSourceHash` 및 별도
  `dataSharingDisabledEvidence`·`openAiHardSpendLimitEvidence`

### 시간

- 주입한 고정 `Clock`과 UTC `Instant`
- 활성 대여: `rentedAt=2026-07-25T05:00:00Z`, `expiresAt=2026-08-24T05:00:00Z`
- 페이지마다 시작 시각이 다른 대여 데이터
- 잉크 무기한 보존 검증용 수년 뒤의 고정 시각
- UTC 날짜 변경 전후, 생성 임시 결과 만료 15분 전후와 중단 예약 만료 1분 전후의 고정 시각
- OpenAI 프로젝트 원격 증명 만료 1시간 직전·정확한 만료 시각과 갱신 뒤의 고정 시각

## 4. 핵심 불변식

### INV-001 잉크 보존

현재 잉크 잔액은 모든 잉크 지급에서 모든 페이지 대여 차감을 뺀 값과 같아야 합니다. 잉크에는 만료
이벤트가 없고 시간이 지난다는 이유로 잔액이나 내역이 바뀌지 않습니다.

### INV-002 활성 대여 중복 차감 금지

`serverNow < expiresAt`인 독자·도서·페이지에는 재열람 횟수와 관계없이 새 잉크 차감과 대여 기록을
만들지 않습니다.

### INV-003 차감과 대여의 원자성

새 대여에서는 잉크 1개 차감, 잉크 내역, `PageRental` 기록과 마지막 열람 위치가 모두 성공하거나 모두
실패해야 합니다. 페이지 콘텐츠는 트랜잭션 성공 뒤에만 제공합니다.

### INV-004 음수 잔액 금지

어떤 동시 요청과 재시도에서도 잉크 잔액은 0 아래로 내려가면 안 됩니다.

### INV-005 변경 불가능한 잉크 내역

생성된 잉크 지급과 차감 내역은 수정하거나 삭제하지 않습니다.

### INV-006 대여 기간 경계

대여는 서버 시각 기준 `rentedAt <= serverNow < expiresAt`에서만 활성입니다. `expiresAt`은
`rentedAt + 30일`이며 정확히 만료 시각부터 새 대여가 필요합니다.

### INV-007 페이지별 독립 기간

한 페이지의 대여 시작·재열람·만료가 다른 페이지의 `rentedAt`과 `expiresAt`을 바꾸지 않습니다.

### INV-008 원본 PDF 페이지 정합성

`Book.totalPageCount`는 원본 PDF 페이지 수와 같고, 각 서비스 페이지 번호는 같은 번호의 변환 콘텐츠
하나와 연결됩니다. 표시 배율과 글자 크기는 이 연결과 잉크 차감 단위를 바꾸지 않습니다.

### INV-009 콘텐츠 권한 선행

인증과 현재 열람 세션을 확인한 뒤, 온라인 소장 또는 활성·신규 대여 중 하나가 성립해야만 텍스트·이미지
콘텐츠를 제공합니다. 내부 저장소 주소와 원본 PDF는 제공하지 않습니다.

### INV-010 잉크 사용 기한 없음

구매하거나 지급받은 잉크는 보유 기간과 마지막 사용 시각에 관계없이 유지됩니다. 페이지 대여
`expiresAt`, 로그인 세션 만료와 잉크 잔액은 서로 영향을 주지 않습니다.

### INV-011 도서 원가 결제와 잉크 분리

온라인 소장은 도서 원가와 일치하는 원화 결제 성공으로만 생성합니다. 소장 결제는 잉크 잔액과 잉크
내역을 바꾸지 않고, 페이지 대여에 사용한 잉크도 도서 원가에서 공제하거나 소장 금액으로 누적하지 않습니다.

### INV-012 온라인 소장 권한

온라인 소장한 도서는 모든 페이지를 잉크 잔액, 활성 대여와 만료 시각에 관계없이 제공합니다. 같은
독자·도서의 소장 기록은 하나이며 기간 만료 상태를 갖지 않습니다.

### INV-013 결제 검증과 멱등 완료

잉크 이용권과 소장 결제는 서버가 만든 `PENDING` 시도에서 시작합니다. 브라우저 완료와 서명 검증된
웹훅은 PortOne V2 결제를 다시 조회하며, 상태·식별자·금액·통화가 모두 맞는 첫 요청만 `PAID` 전이와
잉크 또는 소장 권한을 같은 트랜잭션에서 한 번 반영합니다.

### INV-014 AI 경로 생성 무과금

AI 경로 생성·미리보기·임시 보관·저장만으로 페이지 콘텐츠, `PageRental`, 잉크 차감과 잉크 내역을 만들지
않습니다. 기존 온라인 소장 또는 활성 대여 여부는 예상 비용만 바꿉니다.

### INV-015 생성 결과 신뢰 경계

모델 출력의 모든 페이지는 검색 후보와 서버가 같은 도서·콘텐츠 버전의 검증된 선수 그래프에서 계산한
전이적 선수 페이지 폐쇄의 합집합에 속해야 합니다. 같은 책에 존재해도 허용 집합 밖이면 전체 출력을
거부합니다. 클라이언트는 서버가 발급한 15분 유효 `generationId`만 저장 요청에 사용할 수 있습니다. 서버는 소유자,
도서, 콘텐츠 버전, 만료와 검증된 경로를 다시 확인하며 클라이언트가 만든 목적·페이지·순서·가이드 문구를
저장하지 않습니다. 임시 결과에는 정규화한 독서 목적과 페이지 구성을 함께 보관하고 생성 ID를 원자적으로 한
번만 소비해 둘을 저장 경로로 옮깁니다. 만료 시에는 목적과 페이지 구성을 함께 제거하고 입력 HMAC·HMAC 키
버전과 `EXPIRED` 상태만 남깁니다. 입력 HMAC는 배포 비밀키를 사용한 HMAC-SHA-256으로 계정·도서·콘텐츠
버전·정규화한 목적·mode·value를 PRD의 고정 순서와 4바이트 길이 접두로 직렬화한 값을 인증하고 멱등
상태와 함께 삭제합니다. 비밀키는 저장소·DB에 남기지 않고, 키 교체 시 참조 상태가 모두 삭제될 때까지 이전
키를 보존합니다. 같은 생성 ID의 재시도에는 기존 경로를 반환하며, 경로가 먼저 삭제된 뒤에는 임시
결과가 없으므로 되살리지 않습니다. 최초 저장한 새 경로는 현재 경로가 되며, 같은 생성 ID 재시도는 그 사이
독자가 바꾼 현재 경로를 다시 변경하지 않습니다. 같은 독자·도서의 현재 경로 변경은 직렬화해 현재 경로를
최대 하나만 유지합니다.
`NO_ROUTE`는 원문 목적 없이 입력 HMAC, `noRouteReason`과 최초 `minimumRequiredInk`를 함께 보관합니다.
현재 권한과 선택한 0 또는 양의 예산으로 유효 경로를 만들 수 없으면 선택 예산보다 큰 최소 추가 잉크를
기록하고, 대여·소장·잔액이 바뀐 뒤 같은 멱등 키를 재시도해도 최초 응답을 재현합니다.

### INV-016 생성 횟수 원자성과 멱등성

첫 슬롯 예약 시각의 UTC 날짜를 `quotaDate`로 고정하고 날짜별 정상 생성과 관련 경로 없음은 최대
10회입니다. 진행 중 슬롯은 원자적으로 예약하며 같은 UUID 멱등 키의 진행 중·경로·경로 없음 결과는 자정을
넘어도 한 번으로 처리합니다. 멱등 상태는 최소한 다음 UTC 날짜가 끝날 때까지 보존하고, 15분이 지난 경로
결과는 제거하되 `EXPIRED` 상태를 남겨 같은 키로 다시 실행하지 않습니다. 실제 OpenAI 호출을 시작한 외부
생성 실행은 성공 여부와 관계없이 계정·`quotaDate`당 최대 20회이며 실패한 같은 키의 재실행도 새 시도로
계산합니다. 외부 API·출력 검증·서버 오류와 1분 지난 중단 예약은 정상 결과 횟수를 소비하지 않지만 시작한
외부 실행 시도는 돌려주지 않습니다. `FAILED` 재실행은 정상 결과 슬롯을 다시 예약하고 단조 증가하는
`attemptVersion`으로 시작합니다. 결과 전이는 현재 `IN_PROGRESS` 상태와 작업 버전이 모두 일치할 때만
허용하며 복구 뒤 도착한 이전 버전 작업은 결과와 두 횟수를 바꾸지 못합니다. 서로 다른 계정의 일반 HTTP
외부 실행은 같은 공개 애플리케이션 DB의 `(quotaDate)`별 전역 카운터에 합산하고 MySQL에서 원자적으로
소비합니다. 같은 DB의 모든 인스턴스와 재시작·롤링 배포는 DB 승인 전역 한도 값과 카운터를 공유하고
초기화하지 않으며, 각 인스턴스의 주입값은 승인값과 같아야 합니다. 계정 또는 전역 외부 실행 슬롯이 부족하면
두 실행 슬롯을 모두 소비하지 않고 정상 결과 예약을 즉시 해제하며 현재 멱등 시도를 `FAILED`로 끝냅니다.
계정 정상 결과·계정 외부 실행·전역 외부 실행 한도는 각각 안정된 `429` 코드와 `Retry-After`를 반환하며,
공급자의 spend·usage limit과 선불 크레딧 소진 오류는 `503 AI_ROUTE_PROVIDER_BUDGET_UNAVAILABLE`로
변환합니다.

### INV-017 AI 페이지 가이드 콘텐츠 보호

외부 AI는 페이지 번호와 정해진 열거값만 반환합니다. 사용자에게 보이는 가이드는 검수된 공개 가이드 주제와
서버 템플릿으로만 만들며 비공개 분석 텍스트, 모델 자유 문구, 원문·요약·결론·수치·사례 결과를 포함하지
않습니다.

### INV-018 외부 AI 데이터 경계

콘텐츠 적재의 Embeddings API에는 합의된 보관 조건과 외부 전송 권리를 확인한 페이지 분석 텍스트만,
런타임 Embeddings API에는 독서 목적만 전달해 페이지 벡터와 같은 모델·차원의 요청 벡터를 만듭니다.
Responses API에는 독서 목적과 후보 분석 텍스트만 전달하며 요청은 `store=false`와
`service_tier=default`여야 합니다. `service_tier` 누락과 `auto`는 허용하지 않고 응답의 실효
`service_tier`도 `default`인지 검증합니다. 독자 식별·예산·잉크·결제·권한·세션 정보는 전송하지 않으며
목적과 외부 요청·응답 원문을 애플리케이션 로그에 남기지 않습니다. 기본 제어는 최대 30일 악용 모니터링과
최대 24시간 입력 파생 캐시를 모두 허용한 콘텐츠에만,
Modified Abuse Monitoring은 고객 콘텐츠의 악용 모니터링 제외와 최대 24시간 파생 캐시를 허용한 콘텐츠에만
사용합니다. 공급자 측 고객 콘텐츠 애플리케이션 상태 보관을 허용하지 않는 콘텐츠는 Zero Data Retention을
사용하며 GPT-5.6의 `prompt_cache_options.ttl`을 최대 보관 제한으로 간주하지 않습니다. explicit 모드와
명시적 breakpoint가 없는 요청은 2차 MVP의 무보관 근거로 사용하지 않습니다.

### INV-019 공개 승인 설정과 프로젝트 정책 결합

평가·배포에 공통으로 쓰는 실행 JAR의 `generationArtifactHash`와 경로 모델·추론 설정·Responses 요청의
명시적 `service_tier=default`·프롬프트·출력 스키마·후보 선택·서버 경로 정책을 결합한
`generationConfigHash`와 전용 OpenAI 프로젝트의 ID·실효 데이터 제어·캐시 정책을 원격 확인한
`openAiPolicyHash`를 평가 증거에 기록합니다. `PUBLIC` 전환은 평가한 두 해시를 같은 트랜잭션의 공개
승인값으로 저장합니다. 콘텐츠 적재는 정책 증명과 콘텐츠 요구 조건, 평가는 고정한 두 해시, 일반 생성은
현재 두 해시와 공개 승인값을 외부 호출 전에 대조하며 각 단계의 누락·불일치·원격 drift에는 실패
폐쇄합니다. 같은 프로젝트에서 정책만 바뀌면 새 증명과 데이터 공유 비활성 확인을 갖춘 비웹 작업이 모든
공개 콘텐츠의 권리·보관 조건을 다시 검증하고, 생성 설정이 그대로인 경우에만 승인 `openAiPolicyHash`를 한
트랜잭션에서 교체합니다. 실패하면 기존 승인값과 실패 폐쇄를 유지합니다. 생성 설정 변경은 재평가와 새 공개
승인을, 프로젝트 ID 변경은 새 프로젝트의 콘텐츠 적재·재평가·새 공개 승인을 요구합니다. 같은 프로젝트의
API 키 교체는 원격 상태 재검증과 새 증명을 요구합니다. 원격 증명은 확인 뒤 1시간만 유효하며 정확한 만료
시각부터 일반 생성은 OpenAI를 호출하지 않습니다. 공식 관리 API로 읽을 수 없는 학습용 데이터 공유 비활성은
조직 관리자가 적재·평가·공개 서버 시작과 키 교체 전에 `dataSharingDisabledEvidence`로 별도 확인합니다.
같은 단계에서 전용 프로젝트의 월간 hard spend limit 활성화를 `openAiHardSpendLimitEvidence`로 확인합니다.
두 증거 중 하나가 없거나 대상 프로젝트가 다르거나 hard limit이 꺼져 있으면 배포하지 않으며, 설정 변경
전에는 AI 경로를 비활성화합니다. 평가·공개 요청에서 `service_tier`를 누락하거나 `auto`로 지정하면 외부
호출 전에 실패 폐쇄합니다. 명시적으로 `default`를 요청했더라도 응답의 실효 `service_tier`가 다르면 해당
출력을 거부하고 임시 결과를 만들지 않으며, 시작한 외부 실행 시도는 유지하고 정상 결과 예약을 해제한 뒤 현재
멱등 시도를 `FAILED`로 전이합니다.

### INV-020 평가 데이터 격리와 공개 출처 동일성

평가용 계정·잉크·원장·대여·소장·결제와 런타임 상태는 공개 후보 DB를 트랜잭션 일관 스냅샷으로 복제한
접근 제한 평가 DB에만 만듭니다. 평가 DB와 공개 후보 DB는 같은 MySQL 버전·스키마 마이그레이션을 사용하고
콘텐츠 manifest SHA, 콘텐츠 배치 ID, 도서·페이지·분석 텍스트·분석 메타데이터·임베딩·선수 그래프의
정규화 해시와 마이그레이션 체크섬으로 만든 `evaluationSourceHash`가 일치해야 합니다. 평가 기록은
애플리케이션 삭제 경로로 개별
삭제하지 않고 정제 증거 보존 뒤 평가 DB 전체를 폐기합니다. 개발·회귀 목적 90개의 지표는 출시 지표와
분리합니다. 평가 코드·사람 판정 기준·PRD 품질 임계값 경로에 미커밋·미추적 변경이 없는 정확한 커밋 SHA를
`evaluationGitRevision`으로 기록합니다. 잠금 holdout을 처음 열기 전에 콘텐츠를 열지 않고 확인한
`holdoutDatasetVersion`·`holdoutDatasetHash`를 `generationArtifactHash`·`generationConfigHash`·
`evaluationSourceHash`·`evaluationGitRevision`과 함께 여섯 값으로 봉인하고 접근 증거를 남깁니다. holdout을
관측한 뒤 여섯 값 중 하나라도 바뀌면 기존 holdout의 결과와 증거를 폐기하고 새 미관측 holdout으로 전체
평가를 반복합니다.
`evaluationSourceHash` 변경에는 분석 텍스트·분석 메타데이터·임베딩·선수 그래프 변경이,
`evaluationGitRevision` 변경에는 평가 코드·사람 판정 기준·PRD 품질 임계값 변경이 포함됩니다. 공개 전환 시
평가 계약 경로의 현재
파일 내용, holdout 버전·해시, 현재 실행 JAR의 `generationArtifactHash`, 공개 후보 DB의
`evaluationSourceHash`, `generationConfigHash`와 `openAiPolicyHash`가 평가 증거와 같을 때만 `PUBLIC`으로
전환하며 평가 데이터가 들어간 DB는 공개하지 않습니다. 단일 요청 지연은 공개 배포와 같은
`latencyProfile`에서 명시적 `service_tier=default` 요청과 응답 270개의 실효 `service_tier=default`를
검증하며 새 프로세스·무워밍업·고정 순서·동시성 1로 270개를 측정합니다. 응답 티어·프로필·실행 조건이
하나라도 다르면 품질·지연 증거 전체를 폐기합니다. 270개 최종 상태가 모두 `ROUTE` 또는 `NO_ROUTE`가
아니거나 `FAILED`가 하나라도 있으면 지표와 정제 증거를 만들지 않습니다.

### INV-021 AI 경로 소유권

임시 생성 결과의 조회·저장과 저장 경로의 목록·상세·현재 경로 지정·삭제·진행 기록·피드백은 인증된 소유자만
조회하거나 변경할 수 있습니다. 목록은 인증된 독자의 경로만 반환합니다. 다른 독자의 식별자를 사용한 요청은

## 7. 보안 및 콘텐츠 전달 확인

- 비밀번호 원문과 DB 접속 정보·시연 계정 자격 증명이 코드, 문서, 로그, 오류 응답에 없어야 합니다.
- 비밀번호는 `DelegatingPasswordEncoder`의 BCrypt 형식으로 저장해야 합니다.
- 로그인 실패 응답은 이메일 존재 여부를 구분하지 않아야 합니다.
- 로그인 성공 시 세션 ID가 교체되고 로그아웃 시 로그인·열람 세션이 무효화되어야 합니다.
- 브라우저가 서버에 직접 제출하는 Thymeleaf 폼은 CSRF hidden field를,
  `fetch`는 페이지의 `_csrf`, `_csrf_header` meta 태그를 사용해야 하며 토큰 없는 상태 변경 요청은 처리되지 않아야 합니다.
- 로그인·로그아웃 뒤에는 새 페이지를 렌더링해 새 CSRF 토큰을 사용하고 별도 토큰 API를 두지 않아야 합니다.
- PortOne API secret과 웹훅 secret은 브라우저, 로그, 오류 응답에 노출되지 않아야 합니다.
- `/api/**` 응답의 `X-Request-Id`와 요청·실패 로그의 `requestId`가 같아야 합니다. 로그에는 요청 바디·쿼리·
  헤더·쿠키·예외 원문과 로그인 세션 ID·`viewerSessionId`·내부 저장소 경로가 없어야 합니다.
- 웹훅 서명과 PortOne 서버 재조회 검증 없이 이용권 지급과 온라인 소장을 만들지 않아야 합니다.
- 원본 PDF와 내부 저장소 주소를 직접 내려주는 공개 경로가 없어야 합니다.
- 애플리케이션은 본인의 소장 또는 대여 권한을 확인한 요청 페이지 외 콘텐츠를 제공하지 않아야 합니다.
- 다른 사용자의 페이지 대여, 온라인 소장, 내 서재와 잉크 내역을 조회할 수 없어야 합니다.
- AI 경로 저장은 서버가 발급한 본인 소유의 유효한 `generationId`만 받아야 하며 클라이언트가 보낸
  목적·페이지·순서·가이드 문구를 신뢰하지 않아야 합니다.
- 모델 출력 페이지는 검색 후보와 서버가 계산한 같은 콘텐츠 버전의 선수 페이지 폐쇄에 모두 속해야 하며,
  같은 책에 존재하는 유효한 페이지라도 이 허용 집합 밖이면 거부해야 합니다.
- 임시 결과의 조회·저장과 저장 경로의 목록·상세·현재 지정·삭제·진행·피드백은 인증된 소유자에게만
  허용해야 하며, 목록은 인증된 독자의 경로만 반환하고 다른 독자의 식별자에는 존재 여부와 경로 내용을
  노출하거나 상태를 변경하지 않아야 합니다.
- 멱등 입력 비교값은 배포 비밀키로 계산한 HMAC-SHA-256과 키 버전만 저장해야 합니다. PRD의 필드 순서·값
  표현·4바이트 길이 접두 직렬화를 정확히 적용하고 HMAC 비밀키와 원문 목적을 DB·로그에 남기지 않아야
  합니다. 키 교체 시 참조 멱등 상태가 모두 삭제되기 전에는 이전 키를 제거하지 않아야 합니다.
- `NO_ROUTE`의 사유와 최초 최소 필요 잉크는 HMAC과 함께 보존하고 권한 상태가 바뀐 같은 멱등 키에도 최초
  응답을 재현해야 합니다.
- 콘텐츠 적재의 OpenAI Embeddings 요청에는 권리·보관 조건을 확인한 페이지 분석 텍스트만, 런타임
  Embeddings 요청에는 정규화한 독서 목적만 있어야 하며 두 입력을 섞지 않아야 합니다. 런타임 모델·차원은
  콘텐츠 버전의 페이지 벡터와 같아야 합니다. Responses 요청은 `store=false`와 독서 목적·후보 분석
  텍스트만 포함하고 독자 식별·예산·잉크·결제·권한·세션 정보를 포함하지 않아야 하며 외부 요청·응답 원문은
  애플리케이션 로그에 없어야 합니다. 독서 목적은 고정 지시문·구조화 출력 스키마와 분리된 사용자 입력
  블록에만 있어야 하며 명령형 목적도 시스템·개발자 지시문을 바꾸지 않아야 합니다. 데이터 제어와 비-ZDR
  파생 캐시 허용 조건이 콘텐츠 메타데이터와 일치하지 않으면 외부 호출 전에 거부해야 합니다.
- 공개 서버의 JAR 바이트에서 계산한 `generationArtifactHash`를 포함한 `generationConfigHash`와 프로젝트
  소속 서비스 계정 키·원격 상태를 확인한 `openAiPolicyHash`가 공개 승인값과 일치해야 합니다. 평가 JAR과
  바이트가 다르거나 두 증거 중 하나가 없으면 `PUBLIC`이어도 OpenAI를 호출하지 않아야 합니다. 원격 증명은
  확인 뒤 1시간 안에서만 유효하며 정확한 만료 시각부터 갱신 전까지 OpenAI 호출이 없어야 합니다.
- 학습용 데이터 공유 비활성은 자동 정책 해시와 분리해 조직 관리자가 같은 조직·프로젝트를 확인한
  `dataSharingDisabledEvidence`로 적재·평가·공개 서버 시작과 키 교체를 통제해야 합니다. 증거 누락·대상
  불일치·공유 활성 값에는 해당 단계를 중단하고 데이터 공유 설정 변경 전에는 AI 경로를 비활성화해야 합니다.
- 같은 전용 프로젝트의 월간 hard spend limit을 `openAiHardSpendLimitEvidence`로 확인하고 필수 양수
  애플리케이션 전역 외부 실행 한도의 DB 승인값·주입값 일치를 검증한 뒤 MySQL에서 원자적으로 적용해야
  합니다. 신규 계정을 여러 개 만들거나 서로 다른 한도 값을 가진 인스턴스를 띄워도 전역 한도를 넘지 않고,
  실행 슬롯 거부는 정상 결과 예약을 남기지 않으며 공급자 비용 한도 오류에 조직·프로젝트·비용·크레딧 정보를
  노출하지 않아야 합니다.
- AI 페이지 가이드는 검수된 공개 주제와 서버 템플릿에서만 생성되고 모델 자유 문구나 비공개 분석 텍스트를
  포함하지 않아야 합니다.
- `PUBLIC`이 아니거나 외부 전송 권리·데이터 보관 조건이 누락·거부된 콘텐츠는 일반 생성의 OpenAI 호출
  전에 거부되어야 하며, 적재·활성화도 외부 호출이나 부분 변경 없이 실패해야 합니다.
- DRM과 화면 캡처 방지는 검증 범위가 아닙니다.

### 공통 ES Module 브라우저 검증

공통 JavaScript는 별도 Node.js 테스트 런타임을 추가하지 않고 패키징한 애플리케이션의 실제 브라우저에서
검증합니다.
`.github/scripts/boot-smoke.sh`는 설치된 Chrome 또는 Chromium에서 `.github/browser-smoke`의 fixture를
실행합니다. fixture는 smoke 실행 중에만 정적 경로로 연결하고 운영 JAR에는 포함하지 않습니다.

1. `/books`에서 `request-json.js`를 동적 import하고 `/api/books?page=1`, `/api/smoke`를 호출해 JSON
   응답과 `204`의 `null` 반환을 확인합니다.
2. 다른 origin URL, JSON이 아닌 성공·실패 응답과 네트워크 실패를 호출해
   `CROSS_ORIGIN_REQUEST`, `INVALID_RESPONSE`, `NETWORK_ERROR`와 HTTP 상태·`X-Request-Id` 보존을
   확인합니다.
3. 상태 변경 요청에서 페이지의 `_csrf`, `_csrf_header`가 실제 요청 헤더에 포함되고, meta 태그를 제거한
   같은 요청은 `MISSING_CSRF_TOKEN`으로 전송 전에 중단되는지 확인합니다.
4. 로그아웃 성공과 서버 오류 응답을 각각 발생시켜 두 경우 모두 `/books`가 새로 렌더링되고, 내비게이션과
   CSRF 토큰이 서버의 실제 인증 상태와 일치하는지 확인합니다. 요청이 전송되지 않은 네트워크·CSRF 준비
   오류는 현재 화면에서 오류를 표시하고 다시 시도할 수 있어야 합니다.
5. 오류 안내가 `textContent`로 표시되고 공통 오류 영역으로 포커스가 이동하며, `401`·`403`만으로 자동
   이동하지 않는지 확인합니다.
6. `/ink`에서 잔액과 `GRANT`·`DEDUCTION` 원장, 10건 고정 페이지 이동을 확인합니다. 결제 화면은
   PortOne 모듈 실패, 결제창 이탈, `PAID`·`PENDING`·`FAILED`·503을 각각 주입해 결제 영역 안내와
   재시도 경로를 검증하며, 결제창 이탈 시 완료 API를 호출하거나 새 `PENDING`을 만들지 않아야 합니다.
7. 결제가 활성화된 비운영 `/ink` 응답에는 PortOne 고정 출처를 허용한 결제 CSP 하나만, 일반 화면과
   결제 비활성·운영 `/ink`에는 외부 출처가 없는 기본 CSP 하나만 포함되는지 확인합니다.

## 8. 변환과 AI 경로 품질 확인

구체적인 변환 명령, 표본 manifest와 보존된 근거는
[콘텐츠 변환과 품질 검증](./content-conversion.md)을 따릅니다.

- 초기 버전은 공개 가능한 시연 PDF 100권과 manifest의 도서 항목 100개가 전체 400페이지를 구성하고
  `bookId`, PDF SHA-256과 페이지 수가 실제 파일과 일치해야 합니다.
- `ai-route-v2`는 비소설 90권이 각각 48~72페이지이고 소설 10권의 PDF·SHA-256·페이지 수가 초기 버전과
  같으며, manifest 합계와 실제 전체 페이지 수가 일치해야 합니다.
- `ai-route-v2`의 모든 지원 페이지에는 분석 텍스트, 검수된 공개 가이드 주제, 예상 독서 시간 입력값과
  콘텐츠 버전에 묶인 모델·차원의 임베딩이 정확히 하나씩 있어야 합니다. 선수 관계와 중복 그룹 소속 목록
  필드도 페이지마다 하나씩 있어야 하지만 구성원은 각각 0개 이상이고, 루트·고유 페이지의 빈 목록을
  허용해야 합니다. 이 데이터는 `BookPage`와 같은 적재 트랜잭션에서 반영되어야 합니다.
- 모든 선수 관계는 같은 도서·콘텐츠 버전의 존재하는 페이지를 `선수 페이지 -> 의존 페이지` 방향으로만
  참조해야 합니다. 다른 도서·콘텐츠 버전 참조, 자기 참조와 방향 순환은 위상 정렬 검증에서 외부 호출과 DB
  변경 전에 거부되어야 합니다.
- `ai-route-v2` 입력 manifest에는 임베딩 모델·차원과 분석 입력 SHA-256이 있어야 합니다. 이 결정적 입력이
  바뀌면 manifest SHA와 출력 경로가 바뀌고, 실행별 `openAiPolicyHash`·`dataSharingDisabledEvidence`·
  `openAiHardSpendLimitEvidence`는 결정적 결과가 아닌 별도 `runId` 적재 증거와 DB 메타데이터에 기록되어야
  합니다.
- 반복 변환은 고정한 시연 PDF에서 시작하고 기존 합성 페이지 규칙으로 PDF를 다시 만들지 않아야 합니다.
- `Book.totalPageCount`, 원본 PDF 페이지 수와 변환 콘텐츠 수가 일치해야 합니다.
- 모든 서비스 페이지 번호가 1부터 중복·누락 없이 원본 PDF의 같은 페이지 번호에 연결되어야 합니다.
- 모든 페이지는 `TEXT` 또는 `IMAGE` 중 정확히 하나이며, `TEXT` 본문과 `IMAGE` 경로·파일 중 선택된
  산출물이 비어 있지 않아야 합니다. 빈 텍스트 추출 결과는 `IMAGE`로 변환해야 합니다.
- 텍스트 페이지는 문단, 문장과 글자 순서가 원본의 읽기 순서와 맞아야 합니다.
- 이미지 페이지는 표, 수식, 삽화와 원본 배치가 잘리지 않고 읽을 수 있어야 합니다.
- 자동 검증을 모두 통과하기 전에는 DB를 변경하지 않으며 실패 후 기존 시연 콘텐츠가 유지되어야 합니다.
- 적재 전후 같은 `(bookId, pageNumber)`의 `BookPage.id`가 유지되고 없는 페이지만 추가되어야 합니다.
  예상하지 않은 기존 페이지가 있으면 삭제하지 않고 전체 적재가 실패해야 합니다.
- 100권 전체의 위험 요소를 고려해 카테고리별 대표 도서 한 권씩 총 10권을 선정하고, 선정한 10권의
  첫·중간·마지막과 위험 페이지를 수동 검수해 파일 크기를 기록합니다.
- 시연 PDF·manifest와 변환 산출물이 `bootJar`와 배포 이미지에 포함되지 않아야 합니다.
- 최초 동결이 끝난 뒤 합성 페이지 생성 코드와 기존 페이지 PNG가 런타임 classpath에 남지 않아야 합니다.
- 실제 데스크톱 뷰어 크기의 표시 품질은 SCRUM-406에서 같은 표본으로 확인했으며,
  결과는 `docs/evidence/content-quality/quality-samples.json`의 `viewerInspection`에 기록했습니다.

AI 경로 품질 평가는
[AI 경로 콘텐츠 코퍼스의 잠금 holdout 조건](./ai-route-content-corpus.md#잠금-holdout-품질-평가-조건)을
따릅니다. 저장소의 개발·회귀 90개 지표는 `developmentDatasetGitRevision`·목적 수와 함께 별도 보고하고
출시 임계값에 합산하지 않습니다.

- HTTP 트래픽을 받지 않는 공개 후보 시연 DB에서 비소설 90권은 `EVALUATABLE`, 소설 10권은
  `UNSUPPORTED`여야 합니다. 공개 후보 DB를 트랜잭션 일관 스냅샷으로 접근 제한 평가 DB에 복제하고 같은
  MySQL 버전·스키마 마이그레이션을 사용해야 합니다. 콘텐츠 manifest SHA, 콘텐츠 배치 ID, 도서·페이지·
  분석 텍스트·분석 메타데이터·임베딩·선수 그래프의 정규화 해시와 마이그레이션 체크섬으로 만든
  `evaluationSourceHash`가 두 DB에서 같아야 합니다. 평가 DB의 비웹 `ai-route-evaluation` 배치가 평가 계정
  27명에게 목적 10개씩을 고정
  배정하고 콘텐츠를 열지 않고 확인한 `holdoutDatasetVersion`·`holdoutDatasetHash`와
  `generationArtifactHash`·`generationConfigHash`·`evaluationSourceHash`·`evaluationGitRevision` 여섯 값을
  봉인한 뒤 처음 연 잠금 holdout 대표 목적 270개를 운영 생성 서비스에서 모두 실행해야 합니다.
  `(bookId ASC, purposeId ASC)`
  순번을 27로 나눈 배정은 `(readerId, bookId)`가 유일해야 하며 배정 목적 수와 초기 권한 상태를 OpenAI
  호출 전에 자동 검증해야 합니다. 목적은 같은 안정 정렬 순번에 따라
  비소장 예산 0·5·10·15와 소장 깊이 5·10·15의 7개 시나리오에 배정하며 각 시나리오는 최소 38개 목적을
  가져야 합니다. 예산 0은 정답 데이터가 지정한 활성 대여, 소장은 일관된 평가용 테스트 결제와 소장 권한을
  사용해야 합니다. 배치는 평가 DB에서 `PUBLIC` 상태 검사만 우회하며 두 DB의 일반 HTTP 생성은 계속
  거부해야 합니다. 평가용 금융·권한·런타임 기록은 평가 DB에만 있어야 하며 평가용 애플리케이션 전역 외부
  실행 한도를 우회하지 않아야 합니다.
- 필수 개념 포함률은 전체 필수 개념 수를 분모로 사용합니다. 무관·중복 비율은 전체 추천 페이지 수를
  분모로 하고, 무관한 추천 페이지와 각 의미 중복 그룹에서 추천 순서상 첫 페이지를 제외한 추가 페이지의
  합집합을 분자로 사용해 같은 페이지를 두 번 세지 않습니다. 선수 순서 위반률은 정답 데이터의 모든 필수
  선수 관계 수를 분모로 사용하고 의존 개념 누락, 필수 선수 개념 누락·후순위 배치를 각각 위반으로
  계산해야 합니다. 관련 경로 없음은 해당 목적의 모든 필수 선수 관계를 위반한 것으로 계산합니다. 세 비율의
  분모는 모두 1 이상이어야 하며 하나라도 0이면 평가 실패로 처리하고 `PUBLIC` 전환을 중단해야 합니다.
- 목적 유용성은 두 명의 독립 판정과 불일치에 대한 세 번째 검수 결과로 계산하고, 전체와 7개 시나리오별
  비율을 모두 산출해야 합니다.
- 관련 경로 없음은 필수 개념 포함 0개와 `유용하지 않음`으로 계산합니다. 단일 요청 지연은 공개 시연 배포와
  같은 `latencyProfile`에서 평가 JAR을 새 프로세스로 시작하고 인위적 워밍업이나 다른 AI 요청 없이 명시적
  `service_tier=default`·고정 순서·동시성 1로 실행하며 응답 270개의 실효 `service_tier=default`를 검증한
  결과만 사용합니다. 요청 티어·실효 응답 티어·실행 조건·프로필 중 하나라도 다르면 품질·지연 측정 전체를
  무효화해야 합니다. 270개가 모두 최종 `ROUTE` 또는 `NO_ROUTE`여야 하며 공급자·서버·시간 제한 원인과
  관계없이 `FAILED`가 하나라도 있으면 지표와 정제 증거를 만들지 않아야 합니다. 유효한 서버 처리 시간을
  오름차순으로 정렬한 257번째 값을 95백분위로 산출하며 10초 이하이고 20초 초과 실패는 0건이어야 합니다.
- 평가 데이터가 런타임 후보 검색·경로 구성 입력에 포함되지 않았음을 자동 검사해야 합니다.
- 콘텐츠·임베딩 모델·경로 모델·추론 설정·Responses 요청의 명시적 `service_tier=default`·응답 270개의
  실효 `service_tier`·프롬프트·출력 스키마·후보 선택·서버 경로 정책,
  `evaluationGitRevision`, `holdoutDatasetVersion`, `holdoutDatasetHash`, holdout 접근 증거,
  `latencyProfile`, `evaluationSourceHash`, `generationArtifactHash`, `generationConfigHash`, `openAiPolicyHash`,
  평가용 전역 외부 실행 한도의 주입값·DB 승인값·일치 검증 결과, `dataSharingDisabledEvidence`와
  `openAiHardSpendLimitEvidence` 식별자 및 실행 시각을 결과에 기록해야 합니다.
- 계산한 도서별·전체 지표가 단일 정본인
  [AI 잉크 경로 PRD의 품질과 출시 기준](./prd/ai-ink-route.md#품질과-출시-기준)을 모두 통과해야 합니다.
- 배치는 잠금 holdout 목적과 표시 경로만 담고 OpenAI 요청·응답 원문과 비공개 분석 텍스트가 없는 접근 제한
  임시 검수 산출물을 만들어야 합니다. 두 명의 독립 판정과 필요한 세 번째 판정을 코퍼스에 정한 보관 기한 안에
  마치지 못하면 산출물을 삭제하고 평가 DB 전체를 폐기한 뒤 새 평가 DB에서 전체 평가를 다시 실행해야 합니다.
- 90권 모두가 PRD 기준을 통과한 뒤 목적 ID·시나리오·표시 페이지·자동 지표·최종 검수 판정을 담고 원문
  목적·OpenAI 원문·비공개 분석 텍스트·평가 계정 식별자가 없는 정제 평가 증거에 `evaluationGitRevision`,
  `holdoutDatasetVersion`, `holdoutDatasetHash`, `evaluationSourceHash`, `generationArtifactHash`, 요청
  `service_tier=default`와 응답 270개의 실효 `service_tier`를 포함해
  접근 제한 저장소에 보존하고 다시 읽어 검증합니다. 임시 검수 산출물을 삭제하고 평가 DB 전체를 폐기하되
  평가용 원장과 결제를 애플리케이션 삭제 경로로 개별 삭제하지 않습니다. 임시 파일과 평가 DB의 부재를
  확인하고 평가 계약 경로의 현재 파일 내용이 `evaluationGitRevision`과 같으며 잠금 holdout 버전·해시,
  공개 배포와 평가 증거의 `latencyProfile`, 현재
  실행 JAR의 `generationArtifactHash`, 공개 후보 DB의 `evaluationSourceHash`, `generationConfigHash`와
  `openAiPolicyHash`가 평가 증거와 같은 경우에만 같은 후보 DB 트랜잭션에서 평가 Git 리비전, holdout 버전·
  해시와 두 승인 해시를 저장하고 비소설 90권을 `PUBLIC`로 활성화합니다. 평가한
  JAR을 다시 빌드하지 않고 공개 서버에 그대로 배포해야 합니다. 한 권이라도 실패하거나 평가 Git 리비전·
  holdout 버전·해시·`generationArtifactHash`·`evaluationSourceHash`·`generationConfigHash`·
  `openAiPolicyHash` 중 하나라도 다르거나 평가 DB가 남으면 일괄 활성화하지 않으며 소설 10권은
  `UNSUPPORTED`를 유지해야 합니다. 평가 데이터가 들어간 DB는 공개하지 않습니다.

## 9. 출시 게이트

### 초기 MVP

초기 MVP 구현 완료 판정에는 최소한 다음 증거가 필요합니다.

1. `docker compose config -q` 통과
2. `docker compose up -d --wait`로 MySQL 8.4 준비
3. `INV-001`~`INV-013`과 AI 경로를 제외한 필수 시나리오 테스트 통과

   부팅 로그 확인

### AI 잉크 경로 2차 MVP

AI 잉크 경로 2차 MVP 구현 완료 판정에는 초기 MVP 게이트의 회귀 검증과 함께 다음 증거가 필요합니다.

1. `INV-014`~`INV-021`과 모든 `T-AIR-*` 필수 시나리오 통과
2. 개발·회귀 90개 지표의 분리 보고와 `ai-route-v2` 콘텐츠 완전성, holdout 버전·해시를 포함한 여섯 값을
   사전 봉인한 뒤 처음 연 잠금 holdout 270개를 7개 사용 시나리오로 고정 배정하고 모든 최종 상태가
   `ROUTE` 또는 `NO_ROUTE`인 AI 경로 품질 게이트 통과
3. `evaluationGitRevision`·`holdoutDatasetVersion`·`holdoutDatasetHash`·`evaluationSourceHash`를 포함해
   최종 판정을 감사할 수 있는 정제 평가 증거의
   보존·읽기 검증, 임시 산출물 삭제와 평가 DB 전체 폐기·부재 확인
4. 평가 계약 경로의 현재 파일 내용과 `evaluationGitRevision`, 잠금 holdout 버전·해시, 평가·배포 JAR의
   `generationArtifactHash`, 공개 후보 DB의 `evaluationSourceHash`·`generationConfigHash`·

   `service_tier=default` 일치 및 평가 Git 리비전, holdout 버전·해시와 두 승인 해시를 포함한 깨끗한 공개
   후보 DB의 `PUBLIC` 원자적 전환

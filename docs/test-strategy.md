# 읽어볼까 MVP 테스트 전략

## 1. 목적

이 문서는 MVP가 지켜야 할 검증 계약을 정의합니다. 가장 중요한 대상은 화면 완성도가 아니라 포인트
차감과 90% 소장 전환의 정확성, 중복 방지, 열람 확정 페이지 수, 잔액과 내역의 일치입니다.

## 2. 검증 우선순위

1. 포인트 잔액과 원장의 불변식
2. 열람 확정 페이지 수와 90% 소장 판정
3. 사용자·도서·페이지별 최초 1회 50P 차감
4. 소장 도서의 추가 차감 금지
5. 서버 기준 6초 열람 확정
6. 잔액 부족과 차감 실패 처리
7. 단일 열람 세션과 페이지 이미지 접근제어
8. 인증·CSRF와 본인 자원 인가
9. 내 서재와 이어 읽기
10. 목록, 검색, 상세 화면과 접근성

빠른 도메인 테스트부터 MySQL 통합 테스트, 브라우저 기반 사용자 흐름 테스트 순으로 실행합니다.

## 3. 공통 테스트 데이터

### 사용자

- Reader A: 로컬·시연 환경의 10,000P 계정
- Reader B: 로컬·시연 환경의 0P 계정
- Reader A의 포인트 내역: 테스트 포인트 지급 +10,000P
- 일반 회원가입 사용자: 0P, 지급 내역 없음
- 시연 계정 비밀번호: 환경변수 주입, 테스트와 저장소에 원문 기록 금지

### 도서

- AI가 작성하고 제목과 저자가 서로 다른 가상 더미 도서 100권
- 제목 정렬과 동률 `id` 정렬을 확인할 수 있는 데이터
- 제목 검색 일치, 저자 검색 일치, 검색 불일치, `%`와 `_`가 포함된 데이터
- 페이지 수가 다른 PDF와 변환된 페이지 이미지
- Book A: 전체 10페이지, 소장 기준 9페이지
- Book B: 전체 11페이지, 소장 기준 10페이지
- Book C: 전체 101페이지, 소장 기준 91페이지

## 4. 핵심 불변식

### INV-001 포인트 보존

현재 잔액은 모든 포인트 지급 합계에서 모든 페이지 차감 합계를 뺀 값과 같아야 합니다.

### INV-002 중복 차감 금지

소장 전 한 사용자·도서·페이지 조합에는 50P 차감 내역이 최대 하나만 존재해야 합니다. 소장 후 열람
확정에는 차감 내역을 만들지 않습니다.

### INV-003 차감과 열람 확정의 원자성

차감이 필요한 열람 확정에서는 포인트 50P 차감, 차감 내역 생성, 열람 확정 페이지 기록,
`confirmedPageCount` 증가와 마지막 열람 위치 갱신이 모두 성공하거나 모두 실패해야 합니다.

### INV-004 음수 잔액 금지

어떤 동시 요청과 재시도에서도 포인트 잔액은 0P 아래로 내려가면 안 됩니다.

### INV-005 변경 불가능한 내역

생성된 포인트 지급과 차감 내역은 수정하거나 삭제하지 않습니다.

### INV-006 열람 확정 페이지 수 일치

`LibraryEntry.confirmedPageCount`는 같은 독자·도서의 `ConfirmedPage` 행 수와 같고 0 이상
`Book.totalPageCount` 이하여야 합니다. 중복 요청은 이 값을 증가시키지 않습니다.

### INV-007 소장 판정과 소장 후 추가 차감 금지

`confirmedPageCount >= ceil(totalPageCount × 0.9)`이면 소장 상태이고, 미만이면 소장 전 상태입니다.
소장 상태에서는 새 페이지를 확정해도 포인트 잔액과 포인트 내역이 바뀌지 않습니다.

## 6. 경계값과 실패 주입

### 시간

- 서버 기준 5.999초: 거절
- 서버 기준 6.000초 이상: 승인 가능
- 페이지 이동 직전과 확정 요청이 겹치는 경우: 유효한 현재 페이지에만 처리
- 로그인 세션 마지막 활동 후 1시간 59분 59초: 유지
- 로그인 세션 마지막 활동 후 2시간 이상: 만료

### 페이지 수와 포인트

- 전체 1페이지: 소장 기준 1페이지
- 전체 10페이지: 소장 기준 9페이지
- 전체 11페이지: 소장 기준 10페이지
- 전체 101페이지: 소장 기준 91페이지
- 소장 전 잔액 0P, 49P: 미확정 페이지 차단
- 소장 전 잔액 50P: 정확히 한 페이지 확정 가능
- 같은 페이지 중복 요청 10회: 총 50P만 차감하고 카운트 1 증가
- 소장 상태에서 잔액 0P: 모든 페이지 열람 가능, 차감 0P, 새 확정 진도 기록

### 세션과 네트워크

- 이전 열람 세션의 지연 요청
- 페이지 이동 후 이전 페이지 번호를 담은 이미지 API 요청
- 응답 유실 후 같은 확정 요청 재시도
- 차감 내역 저장 직전 오류
- `ConfirmedPage` 저장 직전·직후 오류
- `confirmedPageCount` 갱신 직전 오류
- 마지막 열람 위치 갱신 직전 오류
- 연결이 끊긴 상태에서 새 페이지 요청

## 7. 보안 및 콘텐츠 전달 확인

- 비밀번호 원문과 DB·시연 계정 자격 증명이 코드, 문서, 로그, 오류 응답에 없어야 합니다.
- 비밀번호는 `DelegatingPasswordEncoder`의 BCrypt 형식으로 저장해야 합니다.
- 로그인 실패 응답은 이메일 존재 여부를 구분하지 않아야 합니다.
- 로그인 성공 시 세션 ID가 교체되고 로그아웃 시 로그인·열람 세션이 무효화되어야 합니다.
- 상태 변경 요청은 CSRF 토큰 없이는 처리되지 않아야 합니다.
- 원본 PDF와 S3 주소를 직접 내려주는 공개 경로가 없어야 합니다.
- 애플리케이션 이미지 API는 현재 인증 독자의 현재 세션·페이지 외 이미지를 제공하지 않아야 합니다.
- 다른 사용자의 열람 확정 페이지, 서재와 포인트 내역을 조회할 수 없어야 합니다.
- 만료되거나 교체된 열람 세션으로 확정 요청을 처리하지 않아야 합니다.
- DRM과 화면 캡처 방지는 검증 범위가 아닙니다.

## 8. 사용자 이해 검증

구현 완료 후 사용자 5명에게 최초 페이지 확정과 같은 페이지 재열람 흐름을 수행하게 합니다. 참가자가
“처음 열람 확정한 페이지에만 50P가 차감되고 같은 페이지 재열람은 무료”임을 자신의 말로 설명하면
통과로 기록합니다. 5명 중 4명 이상이 통과해야 합니다.

90% 소장 전환과 소장 후 무료 열람은 시간이 오래 걸리는 사용자 과제로 만들지 않고 자동화 테스트로
검증합니다.

## 9. 출시 게이트

구현 완료 판정에는 최소한 다음 증거가 필요합니다.

1. `docker compose config -q` 통과
2. `docker compose up -d --wait`로 MySQL 8.4 준비
3. 모든 핵심 불변식과 필수 시나리오 테스트 통과
4. `./gradlew test`, `./gradlew check`, `./gradlew build` 통과
5. 100권 목록·검색·10권 페이지네이션과 포인트 내역 10개 페이지네이션 검증
6. 중복·동시 요청과 실패 주입 검증
7. 브라우저에서 로그인부터 90% 소장 전환과 소장 후 열람까지 핵심 흐름 통과
8. 현재 잔액과 포인트 내역 합계 대조 통과
9. `confirmedPageCount`와 `ConfirmedPage` 행 수 대조 통과
10. 사용자 이해 검증 5명 중 4명 이상 통과
